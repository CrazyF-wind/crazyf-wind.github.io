从零实现一个哈希表，理解它的每一个设计决策

发表于 2026-10-30

从数据结构选择到扩容、删除与工程边界

引言

写一个能跑的哈希表不难。难的是，每到一个设计分叉路口，你都得做出选择：哈希函数用什么、冲突怎么解、扩容何时触发、删除如何处理、遍历应该遵守什么规则。

标准库替你做完了这些选择，所以平时使用 map 时，很容易只看到接口，看不到背后的权衡。自己从零实现一遍，这些问题才会逐个浮现。

本文按“设计决策”的顺序展开：先提出问题，再比较可选方案，最后说明本文的选择及其代价。代码使用 Go，但核心思路与语言无关。

本文实现的是一个用于学习的数据结构，不追求替代 Go 原生 map。它采用字符串 key、链地址法和全量扩容，目标是让关键机制清楚、可验证。

下面三张图分别对应「整体结构」「key 怎么落到桶」「桶满了怎么搬」这三个最容易被标准库遮住的部分。

图 1：桶数组只负责给出入口，链表负责承担冲突——所以查找成本是「1 次索引计算 + 一条链的长度」，而不是全表扫描；代价是每个元素都要多一次指针和内存分配。

决策一：底层用什么结构？

问题：哈希表要保存 key-value，底层容器应该怎么选？

常见方案有三类：

  1. 纯链表：所有元素放在一条链上，查找需要逐个比较，平均查找成本随元素数量增长，不能发挥哈希索引的优势。
  2. 数组 + 链地址法：数组中的每个位置称为桶；映射到同一个桶的元素，通过链表或其他小型容器组织起来。
  3. 数组 + 开放寻址：所有元素都保存在数组中；遇到冲突时，按一定的探测序列继续寻找位置。

本文选择数组 + 链地址法。原因是它实现直观，删除时可以通过修改链表指针移除节点；负载因子也可以超过 1。不过，链表会引入额外指针和内存分配，冲突链过长时，查找仍可能退化到 O(n)。

开放寻址通常具有更紧凑的内存布局，但删除需要处理墓碑等状态，且性能对装载程度更敏感。这里选择链地址法，是为了突出哈希表的基本机制，而不是宣称它在所有场景中更优。

决策二：哈希函数与桶索引怎么设计？

问题：如何把字符串 key 映射到桶数组中的一个位置？这里其实包含两个独立步骤：先计算哈希值，再把哈希值映射为有效的桶索引。

哈希函数负责将 key 转换为一个固定宽度的数值；索引计算则根据当前桶数量，把这个数值映射到 [0, bucketCount) 范围内。扩容会改变桶数量，因此索引可能变化，但哈希函数本身不必改变。

常见选择包括使用语言或运行时提供的哈希函数，使用 FNV-1a、MurmurHash、xxHash 等现成算法，或者为特定数据设计哈希函数。直接对 key 取模并不能替代哈希函数：字符串需要先转换成数值，才能计算桶索引。

本文选择 FNV-1a，主要是因为算法短小、容易手写，适合教学。它不是加密哈希，也不能抵御恶意碰撞攻击；生产系统应优先考虑运行时或经过充分评估的哈希实现。

桶数量采用 2 的幂，例如 8、16、32。此时可以用 h & (m-1) 计算索引，而不是 h % m。对于 m 为 2 的幂的情况，两种计算在数学上等价；位掩码只是索引计算方式更直接，并不会自动改善哈希分布。由于它只使用哈希值的低位，哈希函数低位的分布质量仍然重要。

这个选择也约束了后续扩容：桶数量需要保持为 2 的幂。本文采用翻倍扩容，不采用增加任意素数或乘以 1.5 的策略。

图 2：哈希函数和索引计算是两步，扩容只改第二步。把桶数定成 2 的幂，换来的是「取模变位与」，代价是分布质量全部压在哈希值的低位上。

决策三：冲突怎么解决？

问题：不同 key 可能映射到同一个桶。链地址法把这些元素放在同一条链表中，查询时遍历链表并比较 key。

本文将新节点插入链表头部。头插只需要修改新节点的 next 指针和桶头指针，代码简单，也不需要遍历到链表尾部。它不保证查询更快：只有在新插入元素更容易被访问等特定访问模式下，头插才可能带来平均查找收益。哈希表本身也不承诺遍历顺序。

这里先查找已有 key。若 key 已存在，只更新 value，不增加元素数量，也不触发扩容；只有新增 key 才会增加 size。

决策四：负载因子与扩容时机怎么定？

负载因子定义为 α = n / m，其中 n 是元素数量，m 是桶数量。链地址法允许 α 超过 1，但负载因子越高，平均每个桶中的元素通常越多。

本文将扩容阈值设为 0.75，超过阈值后桶数翻倍。这是一个便于教学的经验值，不是链地址法的理论常数。阈值过低会占用更多桶数组空间；阈值过高则可能增加冲突链长度。实际系统应结合内存、访问模式、哈希分布和性能目标选择阈值。

为什么要先保存 next？因为后续会重写 e.next，把当前节点接到新桶链表中。如果不提前保存原来的 next，就会丢失旧链表中尚未迁移的后续节点。

当前实现会重新计算每个 key 的哈希值。由于桶数量翻倍，旧索引与新索引之间其实存在更简单的关系：元素只会留在原索引对应的桶，或者移动到旧索引加旧桶数量的位置。实现可以缓存哈希值或利用该关系优化迁移，但为了让示例聚焦核心逻辑，这里暂不优化。

扩容时机采用“先插入，再判断”。因此触发扩容的那次插入会先进入旧桶数组，再迁移到新数组。严格使用 > 0.75，也意味着负载因子在某次插入后可能暂时超过阈值。

图 3：桶数翻倍时，旧桶 i 的元素只会去新桶 i 或 i + m——这是 2 的幂增长带来的性质，而不是巧合。一次扩容要搬 O(m+n) 个节点，代价是一次明显的停顿；而「只去两个桶」本可以拿来优化迁移，本文为了突出核心逻辑没有这么做。

决策五：删除怎么处理？

链地址法删除节点时，需要找到目标节点，并修改桶头指针或前驱节点的 next 指针。删除头节点和删除链表中间节点是两个需要覆盖的边界情况。

如果 key 不存在，方法不修改任何状态。链地址法删除后不需要墓碑，因为从桶链表中移除节点不会影响其他节点的查找路径。开放寻址则不同：直接清空某个槽位可能切断后续探测路径，因此通常需要墓碑或其他删除修复机制。

本文没有实现缩容。大量删除后，桶数组可能比当前元素数量所需的空间更大。缩容可以减少空间占用，但也会带来重建成本；如果元素数量在阈值附近波动，还可能出现反复扩容和缩容。因此，缩容应作为独立设计决策，并通过不同的扩容、缩容阈值避免频繁抖动。

决策六：怎么遍历所有元素？

常见接口包括返回元素切片、提供按需推进的迭代器，或者提供回调式 Range。本文选择 Range：不必先创建包含所有元素的副本，并且可以通过回调返回 false 提前终止。

本文规定：Range 执行期间，不允许修改哈希表结构。原因是插入、删除和扩容都会改变桶或链表结构，可能导致元素遗漏、重复访问等问题。这个限制是本实现主动定义的 API 契约，并不是说 Go 原生 map 在遍历期间的所有写入都一律非法。

Go 原生 map 对遍历期间插入和删除有自己的语言规范语义；并发读写则是另一类问题。运行时可能检测到部分并发读写并触发 fatal error，但不能把它等同于普通的同 goroutine 遍历期间修改。

决策七：并发安全要不要支持？

本文选择不提供并发安全保证，并要求调用方自行同步访问。这样可以避免把锁管理引入基础实现，但并不意味着加锁一定会明显拖慢所有单线程场景；实际成本取决于实现、竞争程度和访问模式。

如果需要并发访问，可以在外层使用 sync.RWMutex 保护整个哈希表，也可以根据 key 分片加锁。不过，分片锁会增加实现复杂度，而且需要谨慎处理扩容、遍历以及跨分片操作。

Go 原生 map 同样不提供通用的并发读写安全保证。sync.Map 是针对特定并发访问模式设计的另一种类型，并不是所有场景下都能直接替代带锁的 map。

与 Go 原生 map 的差距

本文实现的目标是讲清楚基本机制，不是复刻 Go 运行时。比较时还必须注意 Go 版本差异：Go 1.24 起，内置 map 已采用基于 Swiss Tables 的新实现；Go 1.23 及以前的实现采用传统桶与溢出桶结构。不要把旧版实现细节直接描述为当前版本的内部机制。

  • 哈希与安全性：本文使用简单的 FNV-1a，适合教学但不是抗攻击的安全哈希。生产实现需要评估哈希碰撞攻击风险与输入特征。
  • 内存布局：本文每个 entry 都是独立节点，并通过 next 指针连接。当前 Go 原生 map 基于 Swiss Tables，采用开放寻址和分组查找，借助控制字筛选候选 key，以减少不必要的完整比较。
  • 扩容：本文一次性创建新桶数组并迁移全部元素，单次扩容可能带来较高延迟。具体运行时实现会随 Go 版本变化，应该以对应版本的官方资料为准。
  • 冲突处理：本文使用链地址法；当前 Go 原生 map 使用基于 Swiss Tables 的开放寻址方案。它们在空间布局、冲突处理、删除和增长策略上存在不同取舍。

可以阅读 Go 官方文章《Faster Go maps with Swiss Tables》，了解 Go 1.24 的实现变化。

结语：设计决策没有免费的午餐

哈希表的基本思想并不复杂：通过哈希函数把 key 映射到桶，再处理冲突。但工程实现中的每项选择都会带来约束。链地址法让删除简单，却引入指针和额外内存分配；桶数量取 2 的幂让索引计算直接，却要求扩容策略与之配合；全量扩容容易实现，却可能造成单次延迟尖峰；不提供并发安全降低了实现复杂度，却把同步责任交给调用方。

自己实现一次哈希表，真正要学会的不是背下某个阈值或某种结构，而是面对具体场景时，能说清楚：为什么选择它、它解决了什么问题、又把什么代价留给了后续。

这也是理解标准库的一个好方法。标准库里看起来复杂的实现，往往不是为了炫技，而是在性能、内存、延迟、安全性和兼容性之间做长期权衡。

线上服务在压测时挂了一次。日志里最显眼的是这一行：

它后面其实跟了一段堆栈，但那段堆栈只指向“发现冲突的那个 goroutine”——另一个对手是谁，它并不知道。也没有任何可以 recover 的 panic 信息，程序直接以 exit(2) 结束。更让人困惑的是，这段代码在本地跑了一周都没事，QPS 一上来几秒钟就崩了。

这篇文章不打算罗列“Go map 怎么加锁”的几种方式，而是回答一个更根本的问题：为什么 Go 选择让程序直接死掉，而不是像其他语言那样返回一个错误，或者至少让你 recover 一下？

答案藏在 runtime 的设计哲学里。

一、崩溃现场：一个典型的“看起来没问题”

出问题的结构大致是这样：

包级 map，HTTP handler 里同时调 Get 和 Set。本地单线程测试没问题，压测时多个 goroutine 同时进来，就炸了。

触发的是两种 fatal error 之一：

  • concurrent map read and map write：一个 goroutine 读，另一个在写；
  • concurrent map writes：两个 goroutine 同时写。

关键在于：它不是 panic，是 throw。

二、runtime 是怎么发现的：一个标志位

这里要先说清版本。Go 1.24 起，内置 map 换成了基于 Swiss table 的实现，代码在 internal/runtime/maps；在此之前是 runtime/map.go 里的 hmap + bucket。两代实现的检测思路一样，但细节不同，网上的分析经常混着讲。

现行实现（Go 1.24+）

Map 结构体里有一个 writing uint8 字段。写操作不是“上锁”，而是翻转这个标志位，并在进入和退出时各检查一次：

三个细节值得注意：

  • 用异或而不是置 1／清 0。 源码注释说得很直白：并发写者不止一个时，翻转能提高双方都发现竞争的概率。如果只是置位，后到的写者看到 1 就死了；异或让状态在 0/1 之间来回翻，两个写者都更容易撞见对方留下的痕迹。
  • 进入和退出各查一次。 退出时的 if m.writing == 0 很容易被忽略：如果另一个写者在中途把标志翻回去了，这里也能抓到。
  • 遍历有单独的报错。 mapiterinit 检查的是同一个字段，但报的是 concurrent map iteration and map write。

历史实现（Go 1.23 及更早）

旧实现是 hmap 结构体里的 flags 字段，其中一位叫 hashWriting，值是 4：

  • 写操作开始时 h.flags |= hashWriting，结束时 h.flags &^= hashWriting；
  • 读操作检查 h.flags & hashWriting != 0，发现有人在写就 fatal。

思路完全一样，只是位运算和异或的区别。所以后面讨论的“为什么是 throw”，对两代实现都成立。

图 1：runtime 用的是“一个标志位 + 检查”，不是锁。写者进入时翻转标志，另一个写者或读者撞见非零值就触发 fatal；两边的操作并没有被串行化。

注意：这只是一个检测，不是同步。 两个 goroutine 可能刚好错开，也可能刚好撞上。所以表现为“偶发”——本地不崩，压测崩；低流量不崩，高流量崩。

还有一个容易踩的坑：对非空 map，delete 即使 key 不存在，也会走写路径、设置写标志。遍历时如果另一个 goroutine 在删任何 key，遍历都可能触发 fatal。

三、为什么是 throw，而不是 panic

这是整个设计中最关键的问题。

普通的 panic 会创建一个 _panic 结构体，挂到当前 goroutine 上，然后逆向遍历调用栈，执行 defer。如果某个 defer 里调了 recover()，程序就能继续跑。

throw 完全绕过这套机制。它把 fatal error 和当前 goroutine 的堆栈打印到标准错误，然后 exit(2)。没有 defer，没有 recover，没有“恢复”这个选项。

它选择这么做的理由很直接：当 map 的并发冲突被检测到时，内部状态可能已经损坏了。

想象一下：一个 goroutine 正在扩容、把旧表里的槽位搬到新表，另一个 goroutine 同时在读旧表的指针。runtime 发现的时候，控制字和槽位可能已经被改得面目全非——而检测本身只是一个标志位，它只知道“有人撞车了”，并不知道撞坏了多少东西。如果允许你 recover，程序继续跑，后续可能出现更诡异的行为——读到错误的数据、写入丢失、甚至内存越界。

直接死掉，是比“带着损坏的状态继续运行”更负责任的选择。

对比一下 Java 的 ConcurrentModificationException：它允许你捕获，然后继续用那个已经被并发修改过的集合。很多时候你的程序不会立刻崩，但数据对不对，就不好说了。

Go 选择了另一条路：在检测到确定性错误的那一刻，终止进程。 用一次响亮的崩溃，换掉后续所有不可预测的 bug。

图 2：panic 与 throw 的分岔——panic 会走 defer 链，路上还有 recover 这个出口；throw 直接打印堆栈并 exit(2)，没有回头路。

四、sync.Map 不是万能解药

知道原因之后，修复方式看起来很简单：加锁，或者换成 sync.Map。

但 sync.Map 的适用场景很窄，而且它的内部实现这些年也变过。

Go 1.24 起，sync.Map 换成了并发哈希 trie（internal/sync.HashTrieMap）：读操作沿树做原子加载，通常无锁；写操作只在命中的中间节点上加锁并替换节点。官方发布说明强调的改进是——修改不相交的 key 集合时，大 map 上的争用明显变少，而且不再需要预热（老实现要先攒出 dirty map，才能进入低争用状态）。

Go 1.23 及更早，它是 read + dirty 两层结构：读大多走 read 这层无锁快照，写则先在 dirty 里累积，攒够次数再提升为新的 read。

两代实现的共同结论没变：它的优势都在读多写少、key 集合相对稳定的场景。写非常频繁时，sync.Map 的写路径（加锁、替换节点、分配）未必比一把 sync.RWMutex 便宜。而且无论哪一代，Range 都不保证一致性快照——遍历期间看到的可能是部分更新后的状态。

所以实际选型通常是：

场景 推荐
读多写少，key 稳定 sync.Map
读写均衡，或需要强一致遍历 sync.RWMutex 保护的普通 map
高并发，锁竞争严重 分片锁（按 key hash 分到 N 个 map，各一把锁）

分片锁的思路和 Redis 的渐进式 rehash 有相似之处：把一个大问题拆成 N 个小问题，让冲突概率降下来。

五、重新理解 runtime 的“不宽容”

这次崩溃之后，我对 Go runtime 的看法变了一点。

以前觉得 fatal error 太粗暴，为什么不能给个错误码，或者至少让我记录一下现场。后来想明白了：map 的并发冲突不是“可以优雅处理”的错误，它是一个已经发生的数据损坏事件。

runtime 在 writing（老版本是 hashWriting）标志上做的检测，本质是一种尽力而为的哨兵。它不保证一定能发现（两个写操作可能刚好错开标志位检查），但一旦发现，说明冲突已经真实发生了。这时候程序内部的状态是否还能安全使用，没有人能保证。

所以它选择 throw。用进程的死亡，阻止损坏状态的扩散。

这其实和 Redis 渐进式 rehash 的设计哲学形成了有趣的对照：Redis 用复杂度换可用性，因为它是单线程的，不能让主线程卡住；Go 用进程死亡换正确性，因为 map 的状态一旦损坏，继续运行比崩溃更危险。

两种选择，面对的是不同层面的“正确性”。

如果你也在线上遇到过这个崩溃，第一件事不是急着加锁，而是用 go test -race 或 go run -race 在测试环境复现一次。-race 能告诉你哪个 goroutine 在写、哪个在读、以及它们各自的调用栈。这比线上盲猜高效得多。

至于那个包级 map——修法很简单，难的是意识到：Go 的 map 从来没有承诺过并发安全，而 runtime 用最不宽容的方式，让这个承诺变得无法忽视。

Redis 字典与渐进式 rehash：为什么“慢慢搬”是合理的选择

发表于 2026-10-25

如果你用过 Redis，大概率知道它“快”。但“快”从来不是偶然的。Redis 字典的渐进式 rehash，就是一个典型的例子：它为了不阻塞，主动选择了一种“看起来更慢”的搬迁方式。

这个选择的本质，是在回答一个问题：当一次维护操作的耗时随数据量线性增长时，你愿意把它摊开，还是让它一次性砸下来？

一次性 rehash 的账很好算：1 亿个键值对、单个迁移约 100 纳秒，乘起来就是 10 秒。对一个标榜毫秒级延迟的服务来说，这 10 秒等于服务中断。渐进式 rehash 的答案是——不追求“搬得快”，只追求“永远不停”。它把搬迁拆成一个个桶，塞进每一次普通的增删改查里，让开销跟着请求量自然摊薄。

代价也很实在：迁移期间内存占用翻倍、每次操作要查两张表、所有字典操作都要多一条“是否在 rehash 中”的分支。

下面按问题拆开讲：一次性 rehash 到底会阻塞多久？两个哈希表怎么协作？迁移过程中增删改查各走哪条路？为什么是“每次操作顺带搬”而不是“分批定时搬”？以及——这个设计最终牺牲了什么、换来了什么。

一、字典的基本结构：两个哈希表

Redis 的字典 dict 内部有两个哈希表：ht[0] 和 ht[1]。

正常情况下，数据都在 ht[0] 里，ht[1] 是空的。只有当需要扩容或缩容时，ht[1] 才会被分配空间，然后数据从 ht[0] 逐渐迁移到 ht[1]。

为什么要两个表？

因为 Redis 是单线程的。如果只用一张表，扩容时你得原地把所有元素重新计算位置——这在单线程下意味着什么都干不了。两张表 + 一个 rehashidx 索引，让迁移可以“边干活边搬”。

每个哈希表底层是数组 + 链表，用链地址法解决冲突。dictEntry 就是链表节点，同一个桶里的元素用 next 指针串起来。

图 1：两张表怎么协作。上半部分画迁移进行中的状态——ht[0] 左侧几个桶已经搬空，游标 rehashidx 停在当前要处理的桶上，箭头表示这一次只搬这一个桶（桶内通常 1~5 个节点），搬完游标右移一格；ht[1] 是新分配的、容量翻倍的表，搬来的节点落在里面。下半部分把迁移期间四种操作的规则并排放：查找要先查 ht[0] 再查 ht[1]，删除和更新两张表都要动，而新增只写 ht[1]——最后这条是关键，它保证 ht[0] 的节点数只减不增，否则旧表永远清不空。

二、一次性 rehash 到底会阻塞多久？

这是核心问题。要回答它，先看数据量。

假设：一个字典有 1 亿个键值对。

关键数字：Redis 迁移一个键值对的典型耗时，保守估计在 100 纳秒左右。

那么：

10 秒。 在这 10 秒里，Redis 的主线程完全被占住。所有客户端请求全部排队等待。 对于一个标榜 P99 延迟在毫秒级的服务来说，这是灾难性的。

更极端的场景：如果 value 是大 key（比如一个几百 MB 的 List），单次迁移的耗时可能以秒为单位。有测试数据显示，迁移一个 600MB 的 list 类型 key 需要 6.7 秒。这还只是一个 key。

所以答案很明确：一次性 rehash 的阻塞时间与数据量成正比，在百万级以上的字典中，阻塞时间会达到秒级甚至更长。 对 Redis 来说，这等于服务中断。

图 2：两种搬法的差别只在“什么时候搬”。左边一次性 rehash 把全部工作压成一根长条——这 10 秒里主线程被占满，客户端请求只能排队，延迟曲线上出现一根 P99.9 尖刺；右边渐进式 rehash 用同样的总工作量，但把它切成一个个小格，和请求交替执行，单次操作只多搬一个桶，延迟曲线保持平稳。底部一行是这张图的重点：两者*总搬迁耗时相同（都是约 10 秒的 CPU 工作量），差别只在单次最大停顿——从 10 秒降到微秒级的单桶开销，代价是迁移期间内存占用翻倍。*

三、渐进式 rehash 到底“渐进”在哪里？

Redis 的解法是：不一次性搬完，而是把搬迁工作分摊到每一次操作里。

具体机制：

  1. 扩容时，为 ht[1] 分配新空间（通常是 ht[0].used * 2 向上取最近的 2 的幂）；
  2. 把 rehashidx 设为 0，表示 rehash 正式开始；
  3. 每次对字典执行增删改查时，顺带把 ht[0] 中 rehashidx 位置上的整个桶（链表上所有节点）迁移到 ht[1]；
  4. 迁移完成后，rehashidx 加一，指向下一个桶；
  5. 当所有桶都迁移完毕，把 ht[1] 设为新的 ht[0]，清空旧表，rehashidx 重置为 -1。

关键细节：一次迁移的是一个“桶”，不是“一个键值对”。因为一个桶可能是一个链表，上面挂着多个节点。但从实际数据看，由于负载因子控制在合理范围，平均每个桶通常只有 1 个节点，最多一般不超过 5 个。所以单次迁移的开销很小。

四、迁移过程中，增删改查怎么处理？

这是设计中最精妙的部分。两个表同时存在，但操作规则不同。

操作 规则
查找 先在 ht[0] 找，找不到再去 ht[1] 找
删除 两个表都要操作（因为 key 可能在任意一个表里）
更新 两个表都要操作（先找到，再更新）
新增 只往 ht[1] 里加，绝不往 ht[0] 加

新增只写 ht[1] 的原因很直接：保证 ht[0] 的节点数量只减不增。 如果新增还往旧表里写，那 ht[0] 永远清不空，rehash 永远结束不了。

这个规则带来的一个副作用是：迁移期间的查找可能比平时稍慢，因为最坏情况下要找两张表。但这是可接受的代价。

五、为什么是“每次操作顺带搬”，而不是“分批定时搬”？

Redis 其实两种都有。

  • 被动搬迁：每次增删改查时顺带迁移一个桶（_dictRehashStep）；
  • 主动搬迁：服务器定时任务（databasesCron）中调用 dictRehashMilliseconds，在1 毫秒内尽可能多地迁移。

为什么以被动为主、主动为辅？

因为纯定时搬迁有一个问题：如果客户端一直不发请求，定时任务也不一定能保证及时搬完。 而且定时任务的执行时机依赖于 Redis 的事件循环，在高负载时可能被推迟。

被动搬迁的好处是：搬迁的开销天然地跟随负载分布。 请求越多，搬迁越快；请求越少，系统本身也不忙，晚一点搬完也无所谓。这是一种自适应的节奏。

主动搬迁则作为兜底：当客户端闲下来了，没有后续指令来触发被动搬迁时，Redis 不会“置之不理”，而是通过定时任务主动推进。dictRehashMilliseconds 每次只花 1ms 的 CPU 时间做搬迁，然后让出控制权。

所以准确地说：不是“不做定时”，而是“被动为主、定时为辅”。 两者结合，既保证了有请求时搬迁不拖后腿，也保证了没请求时不会永远卡在半途。

六、这个设计牺牲了什么，换来了什么？

牺牲的：

  1. 单次操作略慢。 迁移期间，每次增删改查都可能附带一次搬迁，或者需要查两张表。但开销被控制在单个桶的粒度，通常只有 1~5 个节点，对响应时间的影响很小。
  2. 内存占用翻倍。 rehash 期间两个哈希表同时存在，内存使用量会上升。这是“空间换时间”的典型体现。
  3. 实现复杂度上升。 所有字典操作都必须考虑“是否处于 rehash 状态”，代码路径分叉，更容易出 bug。

换来的：

  1. 不阻塞。 这是最核心的收益。无论字典多大，Redis 主线程永远不会因为 rehash 而停下来。
  2. 平滑的延迟曲线。 一次性 rehash 会导致 P99.9 和 max 延迟飙升；渐进式 rehash 把开销摊薄，让延迟保持稳定。
  3. 自适应节奏。 搬迁进度跟随负载，忙时搬得快，闲时搬得慢，不浪费 CPU。

哈希表、跳表还是 B+ 树：怎么选

发表于 2026-10-23

选择哈希表、跳表还是 B+ 树，本质上不是在选“哪个数据结构更好”，而是在回答一个问题：你的数据放在哪里，以及你打算怎么查它。

如果数据全在内存里、只按 key 精确找，哈希表是首选；如果数据在内存里、既要按 key 找又要按顺序取一段，跳表是那个“刚刚好”的答案；如果数据在磁盘上、既要等值查又要范围扫还要排序，B+ 树是几十年工程实践筛选出来的默认选项——但“磁盘”本身还要再拆一层：机械硬盘（HDD）和固态硬盘（SSD）的瓶颈不同，选型结论也会随之松动。

下面按场景拆开讲。

一、哈希表：只解决“这一个 key 在哪”

哈希表的核心优势只有一个：等值查询期望 O(1)。给定一个 key，算个哈希，直接跳到数组对应位置。没有树高，没有指针跳转，没有页分裂。

但它的问题也同样明确：数据是无序的。哈希函数打散了顺序，你无法高效地回答“比这个 key 大的下一个是谁”或者“把 100 到 200 之间的都取出来”。

所以哈希表的适用边界很清晰：

  • 纯内存场景。哈希表依赖连续数组和指针跳转，放到磁盘上，一次查询可能对应多次随机 I/O；更关键的是它无法把多个 key 打包进一个页，扩容和冲突处理在磁盘上代价极高。磁盘哈希并非完全不存在（如某些 KV 引擎的哈希索引），但在需要范围/排序的场景下劣势明显，工程复杂度也高。
  • 只有等值查询。Memcached、Redis 的键值对空间、以及各种内存字典，都是这个场景。一旦业务需要 WHERE id > 100 或者 ORDER BY，哈希表直接出局。

一句话：如果你确定永远不需要范围查询和排序，哈希表是最快的。但真实业务里，“永远确定”往往不成立。

二、跳表：内存里的有序结构，用简单换确定性

跳表解决的是哈希表解决不了的问题：在保持期望 O(log n) 查找的同时，支持范围查询和有序遍历。

它的结构是在有序链表上建多级索引，查找时从高层往低层跳，最终落到目标区间，然后沿底层链表顺序扫过去。范围查询的代价是“定位起点 + 顺序遍历”，非常自然。

图 1：跳表的两件事。上半部分是一条三层索引链，查找 90 时从 L3 一路往右下跳，折线只比较 4 次就命中；下半部分是范围查询，先用索引定位到区间起点，再沿底层有序链表一路扫过去。

跳表真正的竞争力，不在理论复杂度，而在工程上的“刚刚好”：

  • 实现比平衡树简单得多。红黑树插入删除要旋转、变色，跳表只改指针加概率建层；范围查询上，跳表沿底层链表直接扫，平衡树要走中序遍历（递归或显式栈）。对于需要自己实现或维护数据结构的系统来说，这是一个被低估的优势。
  • 局部修改、读路径易无锁化。这在 ConcurrentSkipListMap 这类并发容器里是实打实的优势。不过要注意，Redis ZSet 和 LevelDB MemTable 选跳表的主因并不是并发——Redis 命令执行本身是单线程，LevelDB 的写入也由 mutex 保护——而是实现简单 + 范围遍历顺手 + 内存开销可控。
  • 内存场景下 B+ 树的优势用不上。B+ 树为磁盘 I/O 做的所有优化（大扇出、页对齐、减少树高）在内存里都失去了意义。内存里一次指针跳转和一次数组访问的差距，远小于磁盘寻道和顺序读的差距。

Redis 的 ZSet 选跳表而不是 B+ 树或红黑树，逻辑就在这里：数据在内存，需要按 score 排序和范围取，跳表实现简单、范围查询顺手、内存开销可控。

一句话：内存 + 有序 + 范围查询，跳表是那个“没有明显短板”的选择。

三、B+ 树：为磁盘 I/O 而生，但有前提

B+ 树的所有设计，都指向同一个目标：把磁盘 I/O 次数压到最低。

它的关键特征：

  1. 非叶子节点只存 key，不存数据。这让每个磁盘页（InnoDB 默认 16KB）能塞下几百上千个索引项，扇出极高，树很矮。几百万行数据，树高通常只有 3~4 层。
  2. 数据全在叶子节点，叶子之间用链表串起来。范围查询和全表扫描变成沿着叶子链表顺序读，磁盘顺序读的性能远高于随机读。
  3. 节点大小对齐磁盘页。每次读一个节点就是读一个页，不浪费，也不多读。

图 2：B+ 树为什么磁盘友好。非叶子节点只存 key，所以一个 16KB 的页能塞下几百上千个索引项，扇出极高、树只有三层。数据全部落在叶子层，叶子之间用链表串起来——等值查询沿左侧虚线走「根 → 内部节点 → 叶子」，范围查询则沿底部绿色箭头在叶子链表上顺序扫。右下角对比了跳表：节点零散分布、每节点只存一个 KV，放到磁盘上一次范围查询就是多次随机 I/O。

关于 I/O 次数还要补一句：B+ 树的根节点和上层节点通常常驻 buffer pool，实际查询的磁盘 I/O 往往只有 1 到 2 次，比“树高 3 到 4 层”更乐观——树高是上界，不是每次查询都要走满。

代价同样明确：随机写、页分裂、写放大。这正是 LSM-Tree 用“顺序写 + 后台合并”换“读放大”的动机——那是另一个话题，但说明 B+ 树不是没有代价的“最优解”，而是在读写之间平衡得最稳的默认选项。

为什么 MySQL 不用跳表？因为跳表是为内存设计的。它的节点零散分布，每个节点只存一个 KV，放到磁盘上，一次范围查询可能触发大量随机 I/O。B+ 树把多个 key 打包进一个页，一次 I/O 取回一批，这才是磁盘友好的做法。

一句话：B+ 树不是“最好的”，但它是在等值、范围、排序、写入之间平衡得最稳的那个——前提是瓶颈在机械寻道或页级读取代价，而这一点在 HDD 和 SSD 上并不完全相同。

四、磁盘要分 HDD 和 SSD：瓶颈变了，结论要微调

把“磁盘”笼统当成一个东西，会掩盖一个关键事实：HDD 的瓶颈是机械寻道，SSD 的瓶颈是闪存写放大和擦除块约束。B+ 树的大扇出和页对齐是为前者设计的；面对后者，它仍然可用，但需要正视新问题，而 LSM-Tree 在某些写入场景下更具优势。

4.1 HDD：B+ 树仍然是标准答案

机械硬盘的随机访问代价极高（寻道 5–50 ms，加上旋转延迟），而 B+ 树把几百上千个 key 打包进一个页，一次 I/O 取回一批，正好把“随机寻道”转化为“少量页读取 + 页内二分”。叶子链表让范围扫描变成顺序读，顺序读在 HDD 上远快于随机读。所以前面“B+ 树为磁盘 I/O 而生”的论述，主要就是针对 HDD 的，逻辑几乎不需要调整。

4.2 SSD：B+ 树可用，但有两个新问题

SSD 没有机械寻道，随机读的代价极低（页级读取只需几十微秒），这意味着“把数据打包进页以减少寻道”的收益变小了。但 SSD 有自己的麻烦：

第一，原地更新代价高。 闪存必须先擦除整个块（128–512 KB）才能覆写，而 B+ 树的节点更新往往是原地写。SSD 通过 FTL（闪存转换层）做重映射来掩盖这个问题，但代价是写放大和垃圾回收（GC）。在写入密集的场景下，B+ 树的随机小更新会持续触发 GC，拖累性能。

第二，ZNS SSD 等新形态让问题更尖锐。 传统 SSD 靠 FTL 隐藏闪存特性，而 ZNS SSD 把写入约束暴露给主机：只能顺序写、同时打开的 zone 数量有限。把未经改造的 B+ 树直接部署到 ZNS SSD 上，吞吐量会明显下降，写入次数增加——这说明 B+ 树“为块设备设计”的前提，在新型 SSD 上并不自动成立。

图 3：HDD 与 SSD 的瓶颈不在同一处。左边机械硬盘，代价大头是磁头寻道（5~50 ms）加旋转延迟，B+ 树把几百个 key 打包进一页，正好把随机寻道换成少量页读取；右边固态硬盘没有寻道，但闪存必须先擦除整个块才能覆写，原地更新经 FTL 重映射后留下写放大和 GC，于是要再按写入强度分岔：读多写少仍是 B+ 树，写密集则考虑 LSM-Tree 或改造后的 B+ 树。

4.3 选型判断：加一层“写入强度”

在原有三步选型（数据在哪 → 要不要顺序 → 实现成本）的基础上，磁盘场景可以拆成两条分支：

条件 推荐 理由
HDD，或读多写少的 SSD 场景 B+ 树 读路径依然高效，工程成熟度无可替代
SSD，写入密集，且能接受读放大 LSM-Tree 把随机写转为顺序写，避开 SSD 的原地更新痛点
SSD，写入密集，但需要稳定读延迟 改造后的 B+ 树（如 buffered B+ tree / 冷热分层） 用缓冲或分层存储减少对闪存的随机小写

LSM-Tree 在 SSD 上的优势来自它“顺序写 + 后台合并”的机制，这与闪存“顺序写友好、原地更新昂贵”的特性天然匹配。代价是读放大和空间放大，所以它不是无条件更优，只是在写密集场景下值得优先考虑。

所以“磁盘 → B+ 树”更准确的表述是：HDD → B+ 树；SSD → 看写入强度，读多写少选 B+ 树，写密集考虑 LSM-Tree 或对 B+ 树做闪存友好改造。

所以怎么选，顺序是：

  1. 先问数据在哪。内存 → 继续往下。磁盘 → 再问是 HDD 还是 SSD、写入强度如何：HDD 或读多写少的 SSD → B+ 树；SSD 写密集 → LSM-Tree 或闪存友好改造的 B+ 树（LSM 本身是另一个话题，但它是这个分支的自然候选）。
  2. 再问要不要顺序。不要 → 哈希表。要 → 跳表。
  3. 最后问实现和维护成本。在内存有序结构里，跳表比平衡树更容易写对、更容易并发，这是一个经常被忽略但很实际的加分项。

前两步根据数据特征圈定候选集，第三步在候选集内做最终取舍。

概念

Tesseract是一个光学字符识别引擎，支持多种操作系统。Tesseract是基于Apache许可证的自由软件，自2006 年起由Google赞助开发。 2006年，Tesseract被认为是最精准的开源光学字符识别引擎之一。【维基百科】

声明

在使用tesseract-ocr的过程中，我遇到了一些问题，并找到了一种适合我的使用方式，在这里给大家分享一下。

  1. 在Mac下使用Homebrew安装tesseract-ocr时，—with-training-tools参数取消，所以无法训练数据；如果使用github下载源码，然后编译安装的话，需要安装很多依赖，比较麻烦；
  2. 如果在ubuntu下使用apt-get安装，默认是携带各种训练工具的，但是我的ubuntu系统是server版，不支持桌面，所以在标注图片时很不方便。
