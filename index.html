如何绘制一幅《上海外滩》v1.0

发表于 2026-11-06

封面：v2.0 的默认机位。黄浦江从画面左侧远处流入，在陆家嘴北侧绕出一个大弯，再向右前方流出；四座地标落在弯道内侧的半岛上。

模型：DeepSeek-flash4.1；harness：Claude Code；能力来源：一组对齐 three.js r186 的 threejs-skills。

这篇文章复盘的是：同一个模型，为什么第一版只搭出「像外滩的元素」，第二版才搭出「能读出外滩的城」。下文把两份提示词称为「第一版」「第二版」，把产出称为「场景 v1」「场景 v2」，避免混淆。

引言：我要的是一座城，不是一张图

我想让模型替我搭一个可交互的 3D 场景，而不是生成一张图。

「可交互」三个字抬高了门槛。一张图只需要在某个角度成立；一个场景要在任意角度、任意时间状态下都成立。几何、材质、光照、后处理、镜头、性能，任何一项掉链子，画面都会立刻露馅。

我用了两版提示词。第一版要到了外滩的元素，第二版才要到外滩的空间。两版之间的差别，不是字数，而是先说什么。

先说结论：决定这类场景成败的，不是模型会不会写 Three.js，而是提示词有没有把空间关系写成可执行、可验收的约束。 skill 负责让 API 用对，提示词负责让世界成立。

一、工具链：13 个 skill，各管一段

我用的不是「一个 three.js 提示词」，而是一组按主题拆开的 skill。它们来自 cloudai-x/threejs-skills，在项目里由 skills-lock.json 锁定版本，安装后通过 .claude/skills 指向 .agents/skills 下的实体目录。

这一组 skill 都对齐 three.js r186，一共 13 个：

每个 skill 不是一段「帮我写代码」的咒语，而是一份可检索的领域知识：当前版本的 API 长什么样、哪些写法已经过时、性能上该注意什么。比如 threejs-performance 会先要求你读 renderer.info，再谈优化；threejs-geometry 会把 InstancedMesh 和合并几何放在同一个语境里讲。

这带来一个很重要的分工：skill 解决「怎么写对」，提示词解决「写什么」。

Claude Code 在这条链路里负责把判断落到文件系统和浏览器里：读项目、跑 npm run dev、看控制台报错、改文件、再验证。模型负责在上下文里做决策，harness 负责让决策真的运行起来。

二、第一版：一份「物件清单」

第一版提示词是这样的：

这份提示词写得不算差。它把「一个高质量 Three.js 城市景观」拆成了可以逐条勾选的要求。模型也逐条交付了：四座地标、反射水面、游船、车流、昼夜切换、Bloom、轨道控制器，一个都不缺。

问题出在条目之间没有关系。

河道被实现成 width = 420、length = 7600 的一条直江，水面是一张 PlaneGeometry(430, 7600, 1, 1) 的长方形；两岸是两块 PlaneGeometry(3800, 9000) 的大地，建筑按世界坐标摆上去。默认机位高 285 米，看向 200 米高的目标，视角更接近滨江平视。

于是画面里出现了三个症状：

  1. 没有骨架。 黄浦江是一条直的水带，不是一条河。外滩之所以是外滩，首先因为江水在那里拐了一个弯。
  2. 建筑是孤岛。 每栋楼都按坐标放对了位置，但楼与楼、楼与岸线之间没有生成关系。外滩建筑群像一排摆好的模型，而不是沿着岸线长出来的城市。
  3. 镜头替观众做了选择。 平视镜头能看清单栋楼和滨江步道，但看不到城市形态。读者第一眼看到的是「一排楼」，不是「一座城」。

这不是模型偷懒。提示词只说了「设置黄浦江」，没有说这条江怎么弯、陆家嘴在弯的哪一侧、镜头从哪里看。信息缺失时，模型只能选最省力的补全方式：直线、矩形、平视。它在每个局部都做对了，却在整体上做错了。

三、第二版：把地理写进第一节

第二版提示词换了一个开头：

相比第一版，真正的改动只有四处，但每一处都改变了模型的行为。

第一，把地理放到第一节，并标注「最重要」。 提示词里的顺序就是模型的注意力顺序。第一版把「地标」放在第 1 条，模型就先堆地标，再补河；第二版先定义河，地标只是河湾内侧的产物。

第二，把形容词换成可执行的几何。 「U 形」「从画面左侧远处延伸」「向中央区域大幅弯曲」「绕过陆家嘴区域向右侧远处延伸」「马蹄形」「真实城市地理尺度」——这些描述可以直接变成一条曲线上的控制点和一段宽度函数（实现时河宽落在 390–620 米之间），而不是一句「要有外滩的感觉」。

第三，给出实现路径。 「使用 CatmullRomCurve3 等曲线技术构建河流中心线和岸线，再生成连续水面网格」「建筑、道路、河岸、水面分别建模，保持空间关系一致」。这不是替模型写代码，而是告诉它：用一条曲线作为所有沿江构件的共同基准。

第四，写禁止项和验收标准。 「而不是直线河道或普通弧形滨江」「不采用地面平视视角」「不要只展示单栋建筑或局部滨江景观」——这三句排除错误解；「第一眼能够识别出上海陆家嘴和黄浦江」「从整体俯视视角能够清晰看到……U 形蜿蜒轮廓」——这两句给出可以被眼睛检查的通过条件。

这三层合起来，才是第二版真正有效的原因：约束可执行，结果可验收，优先级明确。

四、落到代码：河道成为唯一空间基准

提示词里那句「用 CatmullRomCurve3 构建中心线」，最后落成了一个 src/world/river.js。它只做一件事：把整条黄浦江变成一套可以查询的空间坐标。

29 个控制点定义了河道的走向，按弧长均匀采样 900 段，得到每个采样点的位置、切线、法线和半宽。这里用 centripetal 参数化，是为了减少急弯处的过冲——河道弯得越急，普通 Catmull-Rom 越容易在控制点之间甩出一段不自然的弧线。

紧接着是一段容易被忽略、但不写就会出事的逻辑：

岸线不是单独画的，而是中心线向两侧偏移「半宽」得到的。弯太急、河太宽，偏移后的内岸会自己穿过自己。所以急弯处必须收窄河宽，0.62 是给偏移留的安全余量；之后再跑两遍平滑，避免宽度在曲率突变处出现折角。

有了这套采样，river 对外只暴露几个查询：

然后，所有沿江构件都从这里取点：

  • 水面沿着中心线生成连续 ribbon，而不是一张矩形平面；边缘带 aEdge 属性，用来画贴岸泡沫。
  • 陆地是一整块 ShapeGeometry，河道作为 Path 孔洞挖掉，避免水面和地面互相穿插。
  • 岸墙、步道、滨江道路用 createRibbonGeometry / createBankWallGeometry 沿河生成。
  • 外滩 16 栋历史建筑沿着浦西一侧的 bankPoint 逐栋排布，并朝向江面。
  • 游船和货轮沿着中心线偏移出的航线航行，用 tangentAt 自动跟随弯道转向。

这套结构的价值不在「代码更优雅」，而在改一个地方，全场景跟着变。修改一个控制点，水面、岸线、道路、步道、建筑、船只航线会同时移动；而在场景 v1 里，想挪一下河，得分别改水面、岸墙、道路和建筑。

提示词把「河道是基准」说清楚之后，代码自然长成了「一个中枢 + 多个消费者」。这是我觉得这次迭代里最值得记下来的一点：好的提示词不只描述结果，还会暗示结构。

六、把这次迭代抽成六条写法

如果下次还要让模型搭一个「有地理关系」的场景，我会按这六条写提示词。

1. 先空间，后物件，再氛围。
先定义场景的骨架——哪条线决定其他一切；再列地标和物件；最后谈材质、灯光、后处理。顺序不是排版偏好，而是模型的注意力分配。

2. 把「像」翻译成可验证的关系。
「要有外滩的感觉」无法执行；「河道从左侧远处流入，绕过陆家嘴，再向右远处流出，形成马蹄形」可以。能变成控制点、宽度函数、相机坐标的描述，才是有效描述。

3. 给实现路径，但不锁死细节。
「用 CatmullRomCurve3 构建中心线和岸线」是在指定结构；「用 29 个控制点、900 段采样、三条正弦叠加河宽」就是过度干预。前者让模型少走弯路，后者会让它把注意力花在满足数字上。

4. 写禁止项。
「不要直线」「不要地面平视」「不要孤立建筑」比正面描述更能排除错误解。模型在信息不足时会选最省力的默认值，禁止项就是提前堵住那些默认值。

5. 验收标准要能被眼睛检查。
「第一眼能识别出陆家嘴和黄浦江」「俯视能看到 U 形轮廓」——这类标准可以在浏览器里直接判断。不要写「视觉质量高」这种说了等于没说的句子。

6. 一次只改一个维度。
第二版把主要精力放在空间关系上，材质、光照和后期沿用同一套方案。这样两版之间的差异才能归因：画面变好了，是因为河变了，不是因为同时加了十盏灯。

还有一条元规则：让 skill 管 API，让提示词管意图。 不要用提示词去重复 skill 里已经写好的 Three.js 用法；把提示词的篇幅留给「这个世界应该长什么样」。

七、边界：提示词能走多远

场景 v2 仍然是风格化还原，不是测绘。

四座地标是参数化近似：东方明珠的三根立柱和三个球体、上海中心的 120° 扭转三叶截面、环球金融中心的「开瓶器」顶部、金茂大厦的逐层收分，都是从真实形态里抽出来的几何特征，不是实测模型。河宽是正弦叠加出来的，岸线是曲线偏移出来的，不是从地理数据里读出来的。

再往前一步，问题就换了。第三版提示词要的是 1:1 真实地理：真实岸线、真实建筑位置和高度、统一坐标参考系、OSM/GIS/Cesium/Blender、以米为单位的世界比例，还要求「缺少真实数据时先报告缺失项，不得用虚构数据冒充真实城市模型」。这次工作暂时停在「数据源调研与坐标系统」这一步，没有继续往下做。

这不是提示词写坏了，而是提示词能提高上限，但不能替代数据。当目标从「像外滩」变成「是外滩」时，主要的工程量在数据获取、坐标转换、缺失值标注和精度验收上，不在措辞上。

还有一层边界是视觉终检。构建可以通过、产物可以非空、图片可以被解析，但「像不像外滩」最终仍然要人眼看。工具能保证场景跑起来，不能保证它好看。

八、复现

场景 v1 和 v2 是两个相互独立的 Vite 项目，各自带 package.json 和构建配置。环境要求 Node.js ≥ 20.19，以及支持 WebGL 2 的桌面浏览器。

结语：先找到那条「河道」

「绘制」这个词有点误导。我们画的不是一张图，是一组关系：河道决定岸线，岸线决定道路和建筑，建筑决定天际线，镜头决定读者第一眼看到什么。

第一版提示词列全了物件，却没有定义关系，所以模型只能把它们并排放在一起；第二版只多说了几句关于河的话，整座城就跟着河长了出来。

下次让模型搭场景，先别急着列地标。先问自己：这个场景的「河道」是什么？哪一条线一旦定了，其他东西都得跟着它走？

把那条线写进第一节。

《Attention Is All You Need》论文深度拆解：从数学原理到 Transformer 工程实现

这篇论文是现代大语言模型技术体系中最值得深入研究的基础论文之一。它提出的 Transformer 架构，改变了自然语言处理的发展方向，并成为后来 GPT、BERT 以及众多大语言模型架构的重要基础。

如果只是了解 Attention、Multi-Head Attention、Positional Encoding 等概念，很容易出现一种情况：每个模块都知道是什么，却不清楚为什么需要它们、它们之间如何协作，以及这些设计究竟解决了什么问题。

因此，我会以你上传的论文原文为主要依据，按照以下思路展开：

  1. 研究背景与核心问题：Transformer 为什么会出现？它究竟解决了什么问题？
  2. 整体架构：Encoder、Decoder 分别承担什么职责？
  3. 核心数学原理：从 Q、K、V 开始，逐步推导 Scaled Dot-Product Attention。
  4. Multi-Head Attention：为什么需要多个注意力头？它们如何协作？
  5. 位置编码：没有 RNN 和 CNN，模型如何理解词语顺序？
  6. 完整网络结构：残差连接、Layer Normalization、FFN、Mask 分别发挥什么作用？
  7. 训练机制与实验结果：论文如何证明 Transformer 的有效性？
  8. 局限性与后续演进：从原始 Transformer 到现代 GPT，哪些设计被保留、修改或舍弃？
  9. 动手实现：通过代码和张量维度变化，真正理解模型如何运行。

分析时，我会区分三类内容：论文明确提出的结论、根据数学原理展开的解释，以及结合现代大模型发展的延伸分析，避免把今天的技术倒推成论文当年的结论。

一、论文究竟讲了什么？

1.1 论文基本信息

论文名称：Attention Is All You Need

  • 作者：Ashish Vaswani 等人
  • 发表会议：NIPS 2017，即今天的 NeurIPS
  • 论文编号：arXiv:1706.03762
  • 核心贡献：提出完全基于 Attention、摆脱循环网络和卷积网络的序列转换架构 Transformer。

你上传的论文第 1 页明确提出：Transformer 完全依赖 Attention 机制，不再使用传统的循环结构和卷积结构；实验表明，它在机器翻译任务中取得了更好的效果，同时具有更强的并行训练能力和更短的训练时间。Attention Is All You Need(2)

1.2 这篇论文真正解决的是什么问题？

先暂时忘掉 Transformer 的所有术语。

假设我们要让计算机翻译下面这句话：

用 Attention 建立全局依赖，用矩阵运算实现高效并行。

Transformer 并不是完全消除了所有顺序计算。原始论文中的 Decoder 在生成目标序列时仍然采用自回归方式，需要逐 Token 生成；主要的并行化优势体现在训练阶段，以及 Encoder 内部对整个输入序列的处理上。

模型需要一种机制，完成三个步骤：

  1. 判断哪些位置值得关注。
  2. 计算每个位置的重要程度。
  3. 按照这些权重整合其他位置的信息。

Attention 就是为此设计的。

3.2 Query、Key、Value 的直觉解释

可以用信息检索系统来理解。

假设有一个数据库：

当你提出一个查询时：

  • Query（Q）：当前需要什么信息。
  • Key（K）：每条信息用于匹配查询的特征。
  • Value（V）：真正需要提取的信息内容。

模型比较 Query 和各个 Key，计算相关程度，然后对 Value 进行加权组合。

这里的类比只是帮助建立直觉。神经网络中的 Q、K、V 并不是人工定义的标签，而是通过可训练的线性变换得到的向量。

[

得到每个位置的相关性分数。

随后，通过 Softmax 将分数转换为权重：

[
\alpha_{\text{it},j}

\frac{\exp(s_{\text{it},j})}

[
z_{\text{it}}=\sum_j \alpha_{\text{it},j}V_j
]

于是，it 的新表示就融入了其他 Token 的信息。

核心理解：Attention 并不是简单地给每个词打分，而是根据当前 Query 动态地选择和整合其他位置的信息。

3.3 从数学角度推导 Attention

论文提出的 Scaled Dot-Product Attention，其公式是：

[
\boxed{
\operatorname{Attention}(Q,K,V)

\operatorname{softmax}
\left(
\frac{QK^\top}{\sqrt{d_k}}
\right)V
}
]

这是理解 Transformer 必须掌握的公式。论文第 4 页正式给出了这一表达式。Attention Is All You Need(2)

我们逐步拆解。

第一步：计算 Query 和 Key 的点积

[
S=QK^\top
]

假设输入序列有 3 个 Token，每个向量维度为 2。

为了方便理解，先假设：

[
Q=
\begin{bmatrix}
1&0\
0&1\
1&1
\end{bmatrix}
]

[
K=
\begin{bmatrix}
1&0\
0&1\
1&1
\end{bmatrix}
]

那么：

[
K^\top=
\begin{bmatrix}
1&0&1\
0&1&1
\end{bmatrix}
]

因此：

[
S=QK^\top

\begin{bmatrix}
1&0&1\
0&1&1\
1&1&2
\end{bmatrix}
]

矩阵中每个元素表示一个 Query 与一个 Key 的点积。

例如：

[
S_{1,3}=1\times1+0\times1=1
]

表示第一个 Query 与第三个 Key 的点积为 1。

这一步相当于为每一对 Token 计算一个匹配分数。

如果输入序列有 (n) 个 Token，就会得到一个 (n\times n) 的分数矩阵。

第二步：为什么要除以 (\sqrt{d_k})？

这是公式中最容易被忽略、但非常重要的设计。

原始点积为：

[
q\cdot k=\sum_{i=1}^{d_k}q_i k_i
]

假设 (q) 和 (k) 的各个分量相互独立、均值为 0、方差为 1。

那么：

[
\operatorname{Var}(q\cdot k)=d_k
]

也就是说，随着向量维度增加，点积的方差也会增加。

当点积的绝对值很大时，Softmax 的输出容易变得极端。

例如：

[
\operatorname{softmax}([1,2,3])
\approx [0.09,0.24,0.67]
]

而：

[
\operatorname{softmax}([10,20,30])
\approx [0,0,1]
]

第二种情况下，Softmax 几乎将全部权重集中在一个位置上。

这种过度集中的分布可能导致梯度变小，不利于训练。

因此，论文引入缩放因子：

[
\boxed{\frac{1}{\sqrt{d_k}}}
]

将点积除以 (\sqrt{d_k})，以控制分数的尺度。

例如，原始模型中：

[
d_k=64
]

因此：

[
\sqrt{d_k}=8
]

Attention 分数会先除以 8，再进入 Softmax。

这里有个值得深入理解的细节：

缩放并不是为了让每个分数都变小，而是为了让分数的尺度在不同向量维度下更适合 Softmax 和梯度优化。

实际训练中的分布未必满足上述独立、单位方差的理想假设，因此这是一种设计动机，而不是对任意网络状态都严格成立的保证。

第三步：Softmax 将分数转换成权重

计算：

[
A=
\operatorname{softmax}
\left(
\frac{QK^\top}{\sqrt{d_k}}
\right)
]

Softmax 默认沿每个 Query 对应的 Key 维度计算。

也就是说，对矩阵的每一行分别归一化。

得到：

[
A_{ij}\geq 0
]

并且：

[
\sum_j A_{ij}=1
]

在没有 Mask 的情况下，每一行的权重和为 1。

因此，每个 Query 都会得到一组针对所有 Key 的注意力权重。

例如：

[
A_1=[0.2,0.3,0.5]
]

意味着第一个 Query 对应的三个位置，其权重分别为 0.2、0.3 和 0.5。

但需要注意：权重只能直接表示模型在这一步计算中分配的信息混合比例，不能简单等同于人类意义上的重要性或因果解释。

第四步：利用权重整合 Value

最终计算：

[
O=AV
]

假设：

[
A_1=[0.2,0.3,0.5]
]

对应三个 Value：

[
V_1=[1,0]
]

[
V_2=[0,1]
]

[
V_3=[1,1]
]

那么第一个输出向量就是：

[
O_1=0.2V_1+0.3V_2+0.5V_3
]

展开：

[
O_1

0.2[1,0]+0.3[0,1]+0.5[1,1]
]

因此：

[
\boxed{O_1=[0.7,0.8]}
]

这个结果就是三个 Value 按照注意力权重混合之后的向量。

在实际 Transformer 中，Value 是通过可学习的线性变换获得的，而不是人工定义的语义标签。

将整个过程串起来

到这里，Attention 的数学核心就已经完整了：匹配、归一化、加权聚合。

接下来需要回答一个更关键的问题：为什么要有三个不同的向量 Q、K、V，而不是直接对输入向量做点积？

3.4 为什么 Q、K、V 需要分别学习？

假设输入矩阵为：

[
X\in\mathbb{R}^{n\times d_{\text{model}}}
]

Transformer 使用三个可学习的投影矩阵：

[
W_Q,\quad W_K,\quad W_V
]

分别得到：

[
Q=XW_Q
]

[
K=XW_K
]

[
V=XW_V
]

对于单头 Attention，可以将三个矩阵的形状理解为：

[
W_Q\in\mathbb{R}^{d_{\text{model}}\times d_k}
]

[
W_K\in\mathbb{R}^{d_{\text{model}}\times d_k}
]

[
W_V\in\mathbb{R}^{d_{\text{model}}\times d_v}
]

那么：

[
Q\in\mathbb{R}^{n\times d_k}
]

[
K\in\mathbb{R}^{n\times d_k}
]

[
V\in\mathbb{R}^{n\times d_v}
]

为什么要分别投影？

因为模型需要学习两类不同的能力：

  1. 匹配能力：哪些 Token 之间应该建立联系。
  2. 信息表达能力：建立联系之后，应该从其他 Token 中提取什么信息。

Q 和 K 决定注意力权重，而 V 决定加权聚合的内容。

如果只使用原始输入向量计算相似度，模型在如何匹配以及传递什么信息方面就会受到更多限制。

通过学习不同的投影矩阵，模型能够在训练过程中调整这两个方面。

需要注意，这并不意味着 Q 只负责一种语义、K 只负责另一种语义、V 只负责第三种语义。它们是功能上的区分，不是人为规定的语义分类。

四、Multi-Head Attention：为什么不能只用一个注意力头？

理解单头 Attention 后，第二个问题就出现了：

既然一个 Attention 已经可以计算任意两个 Token 之间的关联，为什么论文还要设计 Multi-Head Attention？

原论文第 4～5 页指出，多个注意力头可以让模型同时关注不同表示子空间中的信息，而单头 Attention 的信息聚合可能限制模型同时表达多种关系的能力。Attention Is All You Need(2)

4.1 单头 Attention 的局限

假设有一句话：

The cat chased the mouse because it was hungry.

模型需要同时处理不同类型的信息，例如：

  • it 与前面名词之间的关系。
  • 动词与主语之间的关系。
  • 动词与宾语之间的关系。
  • 其他与语义理解有关的关系。

如果只有一个注意力头，所有这些信息都要通过同一组注意力权重进行聚合。

当然，单头 Attention 并非只能学习一种关系；它也可以学到复杂的关联。

但多个头能够提供更丰富的并行表示方式。

4.2 多头机制的核心思路

假设输入向量维度为 512。

Transformer Base 使用 8 个注意力头，每个头的 Key 和 Value 维度都是 64。

因此，每个头可以独立执行 Attention：

[
head_i=
\operatorname{Attention}
\left(
XW_i^Q,
XW_i^K,
XW_i^V
\right)
]

其中：

[
i=1,2,\ldots,8
]

每个头都有自己的参数矩阵。

最终，将所有头的输出拼接：

[
H=\operatorname{Concat}
(head_1,head_2,\ldots,head_8)
]

因为每个头的输出维度为 64，所以：

[
H\in\mathbb{R}^{n\times512}
]

然后进行一次输出投影：

[
\boxed{
\operatorname{MultiHead}(Q,K,V)

\operatorname{Concat}(head_1,\ldots,head_h)W^O
}
]

其中：

[
W^O\in\mathbb{R}^{512\times512}
]

在原始 Transformer Base 中，8 个头各有 64 维输出，拼接后仍为 512 维，因此能够与残差连接所需的模型维度保持一致。

4.3 多头 Attention 的计算过程

需要特别注意：这并不是把 512 维向量机械切成 8 份，然后每份独立处理。

实际计算中，每个头都有自己学习得到的 Q、K、V 投影矩阵，因此每个头可以学习不同的表示子空间。

4.4 多头机制的真正价值

可以从三个角度理解。

第一，多个头可以学习不同的注意力分布。

不同头可能对不同位置分配不同权重。

第二，多个头可以在不同表示子空间中处理信息。

不同头的 Q、K、V 投影参数各不相同，因此它们处理的特征不必相同。

第三，多个头的结果可以组合。

Concat 和输出投影允许模型综合不同头提取的信息。

不过，不能简单地认为每个 Head 都对应一个清晰、独立的人类语义任务。

论文附录中的可视化确实观察到，一些注意力头呈现出与句法结构、远距离依赖或指代消解有关的行为；但这不意味着所有注意力头都具备固定、可解释的分工。

4.5 为什么每个 Head 的维度要缩小？

论文选择：

[
h=8
]

[
d_k=d_v=\frac{d_{\text{model}}}{h}=64
]

如果每个头都使用完整的 512 维，那么 8 个头会带来更高的投影计算成本。

缩小每个头的维度，使得多个头的总体计算量与相近规模的单头 Attention 保持在相似量级。

这并不意味着所有现代架构都必须采用这种配置，但它体现了 Transformer 的一个重要设计思想：

通过多个低维表示子空间并行计算，而不是让单个注意力操作承担全部表示任务。

5.2 Cross-Attention：让 Decoder 查询 Encoder

Cross-Attention 的计算不同。

设：

  • (H) 是 Decoder 当前层的输入。
  • (Z) 是 Encoder 的输出。

那么：

[
Q=HW_Q
]

[
K=ZW_K
]

[
V=ZW_V
]

可以看到：

  • Query 来自 Decoder。
  • Key 和 Value 来自 Encoder。

因此，Cross-Attention 可以理解为：

Decoder 根据当前的生成状态，向 Encoder 的输出表示中查询相关信息。

这和 Self-Attention 的区别不在于公式，而在于 Q、K、V 的来源。

它们都可以使用同样的 Scaled Dot-Product Attention 计算。

5.3 Masked Self-Attention：为什么需要掩码？

考虑目标序列：

在自回归生成时：

  • 生成第一个 Token 时，不能查看未来 Token。
  • 生成第二个 Token 时，可以利用第一个 Token。
  • 生成第三个 Token 时，可以利用前两个 Token。

因此，Decoder 的 Self-Attention 必须限制未来信息的流入。

常用方法是构造一个因果 Mask。

对于长度为 4 的序列，可以用矩阵表示允许访问的位置：

[
M=
\begin{bmatrix}
1&0&0&0\
1&1&0&0\
1&1&1&0\
1&1&1&1
\end{bmatrix}
]

其中：

  • 1 表示允许关注。
  • 0 表示禁止关注。

实际计算中，不是直接把这个 0/1 矩阵乘到注意力分数上，而是把禁止访问的位置设置为负无穷，再执行 Softmax。

可以写成：

[
A=
\operatorname{softmax}
\left(
\frac{QK^\top}{\sqrt{d_k}}+B
\right)
]

其中：

[
B_{ij}=
\begin{cases}
0,&j\leq i\
-\infty,&j>i
\end{cases}
]

因此：

[
\operatorname{softmax}(-\infty)=0
]

未来位置的注意力权重就变为零。

这就是 Causal Attention 的数学基础。

一个容易混淆的细节

训练时，原始 Transformer 的 Decoder 可以将完整的目标序列一次性输入网络，并行计算各个位置的预测。

这是因为因果 Mask 阻止了每个位置读取未来的目标 Token。

因此：

  • 训练时，可以并行计算不同目标位置的输出。
  • 推理时，如果使用自回归生成，下一步 Token 仍然依赖前一步已经生成的结果。

这正是 Transformer 能够同时兼顾自回归生成与高效训练的关键设计之一。

论文第 5 页明确说明，Decoder 使用 Mask 阻止当前位置的信息流向之前的位置所不允许访问的未来位置，从而维持自回归生成性质。Attention Is All You Need(2)

6.1 为什么 Self-Attention 本身不理解顺序？

假设有三个输入向量：

[
X=
\begin{bmatrix}
x_1\
x_2\
x_3
\end{bmatrix}
]

将它们的顺序打乱后：

[
X’=
\begin{bmatrix}
x_3\
x_1\
x_2
\end{bmatrix}
]

如果模型没有其他位置信息，那么 Self-Attention 的运算本身不会自动知道哪个 Token 原本位于句首、句中或句尾。

更严格地说，在不引入位置编码、位置相关 Mask 或其他顺序信号时，Self-Attention 对输入位置的置换具有等变性：输入位置被重新排列，输出也会以相同方式重新排列。

因此，Transformer 需要额外的位置机制。

[

这样，模型在后续层中处理的向量既包含 Token 的表示，也融入了位置信息。

七、Feed-Forward Network：为什么 Attention 后面还要接一个网络？

到目前为止，我们已经理解了 Attention 的作用：

每个 Token 根据相关性，从其他 Token 中提取信息。

但 Attention 本身主要通过加权聚合 Value 来整合信息。

Transformer 还需要一个模块，进一步对每个位置的表示进行非线性变换。

这就是 Feed-Forward Network，简称 FFN。

7.1 原始 FFN 的数学表达式

论文第 5 页给出的公式是：

[
\boxed{
FFN(x)=
\max(0,xW_1+b_1)W_2+b_2
}
]

其中：

[
d_{\text{model}}=512
]

[
d_{ff}=2048
]

因此：

[
W_1\in\mathbb{R}^{512\times2048}
]

[
W_2\in\mathbb{R}^{2048\times512}
]

第一层将向量从 512 维扩展到 2048 维，经过 ReLU 激活后，再投影回 512 维。Attention Is All You Need(2)

7.2 FFN 与 Attention 的区别

可以把 Transformer 的每一层理解成两个阶段：

阶段一：信息交互

Attention 让不同 Token 之间交换信息。

阶段二：位置内部的非线性变换

FFN 对每个位置分别进行处理。

原始论文明确指出，FFN 在每个位置分别、独立地应用，并且同一层中的不同位置共享相同的 FFN 参数。不同 Transformer 层之间则拥有不同的参数。Attention Is All You Need(2)

7.3 为什么需要先扩展维度？

以 512 → 2048 → 512 为例。

第一层执行：

[
h=\operatorname{ReLU}(xW_1+b_1)
]

得到：

[
h\in\mathbb{R}^{2048}
]

第二层执行：

[
y=hW_2+b_2
]

重新映射为：

[
y\in\mathbb{R}^{512}
]

通过这种扩展、非线性变换和压缩，网络可以学习比单一线性映射更丰富的特征变换。

从工程角度看，FFN 也是 Transformer 中重要的参数和计算来源。

现代大语言模型中的 FFN 往往进一步发展为 SwiGLU 等结构，维度配置也可能不同。

但其核心思想仍然可以追溯到原始 Transformer：

Attention 负责 Token 之间的信息交互，FFN 负责在每个位置上进一步变换表示。

八、残差连接与 Layer Normalization

原始 Transformer 每个子层都使用残差连接和 Layer Normalization。

论文采用的形式为：

[
\boxed{
LayerNorm(x+Sublayer(x))
}
]

也就是先将子层输入与子层输出相加，再进行 Layer Normalization。Attention Is All You Need(2)

8.1 为什么需要残差连接？

假设某一层的输入是：

[
x
]

经过 Attention 或 FFN 后，得到：

[
F(x)
]

如果直接使用：

[
y=F(x)
]

那么原始输入信息只能通过网络学习的变换继续传递。

残差连接则使用：

[
\boxed{y=x+F(x)}
]

它为输入信息提供了一条直接传递的路径。

这能够帮助深层网络优化，也让子层可以学习对输入表示的增量调整。

从直觉上说：

模型不必每一层都从头重新构造完整表示，而是可以在已有表示的基础上进行修正。

8.2 Layer Normalization 的作用

Layer Normalization 对单个样本的特征维度进行归一化。

给定一个向量 (x)，可以先计算均值：

[
\mu=\frac{1}{d}\sum_{i=1}^{d}x_i
]

再计算方差：

[
\sigma^2=
\frac{1}{d}
\sum_{i=1}^{d}(x_i-\mu)^2
]

然后：

[
\hat{x}_i=
\frac{x_i-\mu}{\sqrt{\sigma^2+\epsilon}}
]

最后使用可学习的缩放和偏移参数：

[
y_i=\gamma_i\hat{x}_i+\beta_i
]

其中 (\epsilon) 用于提高数值稳定性。

在原始 Transformer 的配置中，LayerNorm 位于残差相加之后。

需要区分两个概念：

  • 残差连接提供信息和梯度的直接通路。
  • LayerNorm 对特征进行归一化，以帮助稳定训练。

二者作用不同，因此不能简单地互相替代。

8.3 一个重要的现代架构差异

原始论文使用的是：

[
LayerNorm(x+F(x))
]

这通常称为 Post-LN。

许多现代大语言模型采用 Pre-LN 或其他归一化变体，例如先归一化，再进入子层：

[
y=x+F(LayerNorm(x))
]

这不是原始论文的公式，而是后续架构演进中的重要变化。

如果你准备自己实现 Transformer，需要特别注意这两种结构并不等价，不能只因为它们都包含残差连接和 LayerNorm，就认为可以随意互换。

九、把所有模块组合起来：一层 Transformer 究竟如何运行？

前面分别讲解了 Attention、FFN、位置编码、残差连接和 LayerNorm。现在把它们组合起来，观察数据在网络中的完整流动。

这是从理解理论走向阅读源码、实现模型的关键一步。

9.1 Encoder 单层的完整计算过程

假设输入矩阵：

[
X\in\mathbb{R}^{n\times512}
]

其中 (n) 是 Token 数量。

原始 Transformer Encoder 的一层可以写成：

第一步：Multi-Head Self-Attention

[
A=\operatorname{MHA}(X,X,X)
]

三个输入都来自同一个矩阵 (X)。

然后进行残差连接和 LayerNorm：

[
H=\operatorname{LayerNorm}(X+A)
]

如果考虑论文中的 Dropout，则更准确地写为：

[
H=\operatorname{LayerNorm}
\left(X+\operatorname{Dropout}(A)\right)
]

第二步：Feed-Forward Network

[
F=\operatorname{FFN}(H)
]

然后：

[
Y=\operatorname{LayerNorm}
\left(H+\operatorname{Dropout}(F)\right)
]

因此，Encoder 单层可以概括为：

[
\boxed{
H=\operatorname{LN}(X+\operatorname{Dropout}(\operatorname{MHA}(X,X,X)))
}
]

[
\boxed{
Y=\operatorname{LN}(H+\operatorname{Dropout}(\operatorname{FFN}(H)))
}
]

这里的 LN 是 LayerNorm。

注意，以上公式对应原始论文的 Post-LN 结构。实际训练时，Dropout 只在启用训练模式时生效。

9.2 Decoder 单层的完整计算过程

Decoder 比 Encoder 多一个 Cross-Attention 子层。

假设：

  • (X)：Decoder 当前层的输入。
  • (Z)：Encoder 的输出。

计算过程如下。

第一步：Masked Self-Attention。

[
H_1=
\operatorname{LN}
\left(
X+\operatorname{Dropout}
\left(
\operatorname{MHA}_{masked}(X,X,X)
\right)
\right)
]

第二步：Cross-Attention。

[
H_2=
\operatorname{LN}
\left(
H_1+\operatorname{Dropout}
\left(
\operatorname{MHA}(H_1,Z,Z)
\right)
\right)
]

第三步：FFN。

[
Y=
\operatorname{LN}
\left(
H_2+\operatorname{Dropout}
\left(
\operatorname{FFN}(H_2)
\right)
\right)
]

可以看到，Decoder 的三种子层各司其职：

子层 解决的问题
Masked Self-Attention 已生成的目标 Token 之间如何交互
Cross-Attention 当前生成状态需要从源序列中获取什么信息
FFN 如何进一步变换融合后的表示

9.3 为什么 Transformer 要堆叠多层？

原始论文将 Encoder 和 Decoder 各堆叠 6 层。

每一层都可以重新计算注意力权重，并进一步变换 Token 表示。

可以将其抽象为：

这并不意味着每一层都对应某个固定的认知阶段。

更准确地说，随着层数增加，模型可以反复进行信息交互和非线性变换，从而学习更复杂的表示。

理解 Transformer 的关键，不是孤立记住每个模块，而是理解这些模块如何反复作用于同一组 Token 表示。

十、从计算复杂度理解 Transformer 为什么更高效

原论文不仅提出了新架构，还系统比较了 Self-Attention、RNN 和 CNN 的计算复杂度。

这部分是理解 Transformer 工程优势的重要内容。

论文第 6 页的表格从三个角度进行比较：

  1. 每层的计算复杂度。
  2. 最少需要执行多少个顺序计算步骤。
  3. 任意两个位置之间的最长信息传递路径。Attention Is All You Need(2)

10.1 Self-Attention 的复杂度

假设：

  • 序列长度为 (n)。
  • 表示维度为 (d)。

Attention 的主要计算是：

[
QK^\top
]

其中：

[
Q\in\mathbb{R}^{n\times d}
]

[
K^\top\in\mathbb{R}^{d\times n}
]

矩阵乘法的计算复杂度为：

[
O(n^2d)
]

接着计算：

[
AV
]

其复杂度也是：

[
O(n^2d)
]

因此，单层全局 Self-Attention 的主要复杂度为：

[
\boxed{O(n^2d)}
]

另外，Q、K、V 的投影还需要约 (O(nd^2)) 的计算。

所以，更完整地考虑投影后，单层 Multi-Head Attention 的计算复杂度通常可以概括为：

[
O(nd^2+n^2d)
]

这里忽略了常数因子。

10.2 为什么长上下文会成为问题？

因为 Attention 分数矩阵的大小为：

[
n\times n
]

当序列长度增加时，矩阵元素数量以平方级增长。

例如：

序列长度 (n) Attention 分数矩阵元素数
128 16,384
512 262,144
1,024 1,048,576
2,048 4,194,304
4,096 16,777,216
8,192 67,108,864

序列长度从 1,024 增加到 8,192，是原来的 8 倍，但分数矩阵的元素数量增加到 64 倍。

这就是全局 Attention 的重要代价。

实际显存消耗还与 Batch Size、注意力头数、数据精度、反向传播和具体实现有关，不能仅凭矩阵元素数量直接得出整个模型的显存需求。

10.3 与 RNN 相比，Transformer 的优势是什么？

原论文给出的复杂度比较如下。

指标 Self-Attention Recurrent
每层主要复杂度 (O(n^2d)) (O(nd^2))
最少顺序计算步骤 (O(1)) (O(n))
任意两位置的最大路径长度 (O(1)) (O(n))

这些复杂度描述的是特定计算模型下的理论特征，并不意味着 Self-Attention 在所有序列长度和硬件环境下都比 RNN 更快。

论文还指出，当序列长度 (n) 小于表示维度 (d) 时，Self-Attention 的主要计算在相应假设下可能比循环层更有利。Attention Is All You Need(2)

这是一个容易忽略、但非常有价值的概念。

假设句子开头的 Token 要影响句尾的 Token。

这为模型学习长距离依赖提供了更直接的信息通路。

不过，路径更短不意味着模型必然能正确理解长距离关系。模型仍然需要通过训练学习适当的注意力分布和表示。

10.4 为什么现代模型仍然需要优化 Attention？

因为原始 Transformer 的全局 Attention 虽然提高了并行能力，但它的计算和内存成本仍然会随着序列长度快速增长。

后来出现的优化包括：

  • FlashAttention：通过更高效的分块计算和内存访问方式，减少 Attention 的中间数据读写。
  • Sliding Window Attention：限制每个 Token 能直接关注的局部范围。
  • Sparse Attention：只计算部分位置之间的注意力。
  • KV Cache：在自回归推理中缓存历史 Key 和 Value，避免重复计算。
  • Grouped-Query Attention：在多个 Query 头之间共享 Key、Value 头，降低 KV Cache 的内存开销。

这些都是后续发展，不能与原论文的原始设计混为一谈。

尤其需要注意：FlashAttention 主要优化计算实现和内存访问，并没有把标准全局 Attention 的理论计算复杂度从平方级改成线性级。

lrate\propto step^{-0.5}
]

学习率按照训练步数的平方根倒数逐渐衰减。

为什么要这么设计？

深层网络在训练初期的参数状态可能尚不稳定。先逐步增加学习率，再逐渐降低学习率，是一种兼顾训练稳定性与后期优化的策略。

需要注意，这个具体公式是原论文的训练方案，不是所有现代 Transformer 都必须使用的学习率调度。

十二、原始 Transformer 与现代 GPT 有什么区别？

这是理解这篇论文最重要的延伸问题之一。

很多人学习 Transformer 时，会把原始 Transformer、GPT、BERT 以及现代大语言模型都看成同一种架构。

实际上，它们存在重要差异。

12.1 三种典型架构

特征 原始 Transformer BERT 类模型 GPT 类模型
基本结构 Encoder + Decoder Encoder-only Decoder-only
主要注意力形式 Encoder 双向 Self-Attention；Decoder 因果 Mask + Cross-Attention 通常使用双向 Self-Attention 通常使用因果 Self-Attention
典型训练目标 条件序列生成，例如机器翻译 掩码语言建模等 自回归下一 Token 预测
典型用途 机器翻译、序列转换 文本理解、分类、抽取等 文本生成、对话、代码生成等

这里的“通常”很重要：不同模型可能使用不同的训练目标或结构变体。

12.2 GPT 为什么不需要原始 Transformer 的 Encoder？

原始 Transformer 的任务是：

[
\text{源语言}\rightarrow\text{目标语言}
]

因此，它需要：

  • Encoder 处理源语言。
  • Decoder 生成目标语言。
  • Cross-Attention 将源语言信息传递给 Decoder。

GPT 类模型的核心任务则是根据已有上下文预测下一个 Token：

[
P(x_t\mid x_1,x_2,\ldots,x_{t-1})
]

这种任务本身不需要一个独立的源序列 Encoder，因此可以采用 Decoder-only 架构。

在典型 GPT 模型中，输入 Token 经过 Embedding 和位置处理后，进入多层 Transformer Block。每个 Block 通过因果 Self-Attention 和 FFN 等组件更新表示，最终预测下一个 Token 的概率分布。

这里要注意：现代 GPT Block 往往采用 Pre-LN、不同的位置机制、不同的 FFN 结构和高效 Attention 实现，并不等同于原论文的原始 Block。

12.3 为什么现代 LLM 通常采用 Decoder-only？

一个重要原因是，自回归语言建模可以统一成一个简单目标：

[
\boxed{
\mathcal{L}

-\sum_{t=1}^{T}
\log P(x_t\mid x_{<t})
}
]

其中：

  • (x_t)：当前位置的目标 Token。
  • (x_{<t})：之前的 Token。
  • (P(x_t\mid x_{<t}))：模型预测当前位置 Token 的概率。

但推理时，如果采用逐 Token 自回归生成，仍然需要依赖前一步的生成结果。

12.4 原论文中哪些思想被现代 LLM 保留了？

很多现代大语言模型虽然已经不再使用原始 Encoder-Decoder 结构，但仍然保留了 Transformer 的核心思想：

  1. 通过 Attention 实现 Token 之间的信息交互。
  2. 使用多头机制进行并行表示学习。
  3. 通过残差连接支持深层网络训练。
  4. 使用 FFN 等模块进行非线性特征变换。
  5. 通过位置机制引入序列顺序信息。
  6. 利用大规模数据训练模型参数。

而以下内容在后续发展中出现了很多变化：

  • Encoder-Decoder、Encoder-only、Decoder-only 的结构选择。
  • Post-LN 与 Pre-LN 等归一化方式。
  • 正弦位置编码与 RoPE 等位置机制。
  • ReLU FFN 与 SwiGLU 等前馈结构。
  • 标准 Multi-Head Attention 与 Grouped-Query Attention。
  • 原始 Attention 的直接计算与 FlashAttention 等优化实现。

因此，学习原始论文时，需要区分两个层面：

第一层：理解原始 Transformer 的完整设计。

第二层：理解现代大语言模型为什么在此基础上做出了各种改进。

如果直接从现代 GPT 源码入手，很容易把大量不同年代、不同目的的设计混在一起，反而难以理解最初的原理。

十三、这篇论文有哪些局限？

经典论文并不意味着其方案在所有场景下都是最优的。

如果想真正理解 Transformer，就需要同时理解它的优势与代价。

13.1 全局 Attention 的二次复杂度

对于长度为 (n) 的序列，全局 Attention 的主要计算复杂度为：

[
O(n^2d)
]

当上下文长度非常大时，计算与内存成本会快速增长。

这是后续大量高效 Attention 研究的重要动机。

13.2 自回归生成仍然具有顺序依赖

虽然训练阶段可以并行处理多个位置，但 GPT 类模型在推理时通常仍然逐 Token 生成。

KV Cache 等技术能够减少重复计算，但不能消除下一 Token 对前面生成结果的依赖。

13.3 位置编码不能自动保证长上下文泛化

原论文选择正弦位置编码，一个原因是它可以在训练位置范围之外继续计算。

但这并不代表模型必然能够可靠地利用任意长度的上下文。

长上下文能力还受到训练数据、模型规模、位置机制、注意力实现和训练目标等多方面因素影响。

13.4 Attention 权重不等于完整的解释

原论文观察到，一些注意力头呈现出与句法关系、长距离依赖和指代消解有关的模式。

这为理解模型行为提供了有价值的线索。

但是，不能据此认为：

只要观察 Attention 权重，就可以完全解释模型为什么得出某个结论。

模型的最终输出还受到多层表示变换、残差连接、FFN 和输出投影等多种因素影响。

13.5 论文并没有解决今天所有的大模型问题

这篇论文提出的是一种序列建模架构，而不是一个完整的大语言模型训练与应用方案。

它并未直接解决今天大模型工程中的全部问题，例如：

  • 超大规模分布式训练。
  • 指令微调与偏好对齐。
  • 检索增强生成。
  • 工具调用与 Agent 编排。
  • 长上下文高效推理。
  • 多模态模型训练。
  • 模型安全与可靠性。

这些方向需要在 Transformer 基础上继续学习其他论文与技术。

从零实现一个哈希表，理解它的每一个设计决策

发表于 2026-10-30

从数据结构选择到扩容、删除与工程边界

引言

写一个能跑的哈希表不难。难的是，每到一个设计分叉路口，你都得做出选择：哈希函数用什么、冲突怎么解、扩容何时触发、删除如何处理、遍历应该遵守什么规则。

标准库替你做完了这些选择，所以平时使用 map 时，很容易只看到接口，看不到背后的权衡。自己从零实现一遍，这些问题才会逐个浮现。

本文按“设计决策”的顺序展开：先提出问题，再比较可选方案，最后说明本文的选择及其代价。代码使用 Go，但核心思路与语言无关。

本文实现的是一个用于学习的数据结构，不追求替代 Go 原生 map。它采用字符串 key、链地址法和全量扩容，目标是让关键机制清楚、可验证。

下面三张图分别对应「整体结构」「key 怎么落到桶」「桶满了怎么搬」这三个最容易被标准库遮住的部分。

图 1：桶数组只负责给出入口，链表负责承担冲突——所以查找成本是「1 次索引计算 + 一条链的长度」，而不是全表扫描；代价是每个元素都要多一次指针和内存分配。

决策一：底层用什么结构？

问题：哈希表要保存 key-value，底层容器应该怎么选？

常见方案有三类：

  1. 纯链表：所有元素放在一条链上，查找需要逐个比较，平均查找成本随元素数量增长，不能发挥哈希索引的优势。
  2. 数组 + 链地址法：数组中的每个位置称为桶；映射到同一个桶的元素，通过链表或其他小型容器组织起来。
  3. 数组 + 开放寻址：所有元素都保存在数组中；遇到冲突时，按一定的探测序列继续寻找位置。

本文选择数组 + 链地址法。原因是它实现直观，删除时可以通过修改链表指针移除节点；负载因子也可以超过 1。不过，链表会引入额外指针和内存分配，冲突链过长时，查找仍可能退化到 O(n)。

开放寻址通常具有更紧凑的内存布局，但删除需要处理墓碑等状态，且性能对装载程度更敏感。这里选择链地址法，是为了突出哈希表的基本机制，而不是宣称它在所有场景中更优。

决策二：哈希函数与桶索引怎么设计？

问题：如何把字符串 key 映射到桶数组中的一个位置？这里其实包含两个独立步骤：先计算哈希值，再把哈希值映射为有效的桶索引。

哈希函数负责将 key 转换为一个固定宽度的数值；索引计算则根据当前桶数量，把这个数值映射到 [0, bucketCount) 范围内。扩容会改变桶数量，因此索引可能变化，但哈希函数本身不必改变。

常见选择包括使用语言或运行时提供的哈希函数，使用 FNV-1a、MurmurHash、xxHash 等现成算法，或者为特定数据设计哈希函数。直接对 key 取模并不能替代哈希函数：字符串需要先转换成数值，才能计算桶索引。

本文选择 FNV-1a，主要是因为算法短小、容易手写，适合教学。它不是加密哈希，也不能抵御恶意碰撞攻击；生产系统应优先考虑运行时或经过充分评估的哈希实现。

桶数量采用 2 的幂，例如 8、16、32。此时可以用 h & (m-1) 计算索引，而不是 h % m。对于 m 为 2 的幂的情况，两种计算在数学上等价；位掩码只是索引计算方式更直接，并不会自动改善哈希分布。由于它只使用哈希值的低位，哈希函数低位的分布质量仍然重要。

这个选择也约束了后续扩容：桶数量需要保持为 2 的幂。本文采用翻倍扩容，不采用增加任意素数或乘以 1.5 的策略。

图 2：哈希函数和索引计算是两步，扩容只改第二步。把桶数定成 2 的幂，换来的是「取模变位与」，代价是分布质量全部压在哈希值的低位上。

决策三：冲突怎么解决？

问题：不同 key 可能映射到同一个桶。链地址法把这些元素放在同一条链表中，查询时遍历链表并比较 key。

本文将新节点插入链表头部。头插只需要修改新节点的 next 指针和桶头指针，代码简单，也不需要遍历到链表尾部。它不保证查询更快：只有在新插入元素更容易被访问等特定访问模式下，头插才可能带来平均查找收益。哈希表本身也不承诺遍历顺序。

这里先查找已有 key。若 key 已存在，只更新 value，不增加元素数量，也不触发扩容；只有新增 key 才会增加 size。

决策四：负载因子与扩容时机怎么定？

负载因子定义为 α = n / m，其中 n 是元素数量，m 是桶数量。链地址法允许 α 超过 1，但负载因子越高，平均每个桶中的元素通常越多。

本文将扩容阈值设为 0.75，超过阈值后桶数翻倍。这是一个便于教学的经验值，不是链地址法的理论常数。阈值过低会占用更多桶数组空间；阈值过高则可能增加冲突链长度。实际系统应结合内存、访问模式、哈希分布和性能目标选择阈值。

为什么要先保存 next？因为后续会重写 e.next，把当前节点接到新桶链表中。如果不提前保存原来的 next，就会丢失旧链表中尚未迁移的后续节点。

当前实现会重新计算每个 key 的哈希值。由于桶数量翻倍，旧索引与新索引之间其实存在更简单的关系：元素只会留在原索引对应的桶，或者移动到旧索引加旧桶数量的位置。实现可以缓存哈希值或利用该关系优化迁移，但为了让示例聚焦核心逻辑，这里暂不优化。

扩容时机采用“先插入，再判断”。因此触发扩容的那次插入会先进入旧桶数组，再迁移到新数组。严格使用 > 0.75，也意味着负载因子在某次插入后可能暂时超过阈值。

图 3：桶数翻倍时，旧桶 i 的元素只会去新桶 i 或 i + m——这是 2 的幂增长带来的性质，而不是巧合。一次扩容要搬 O(m+n) 个节点，代价是一次明显的停顿；而「只去两个桶」本可以拿来优化迁移，本文为了突出核心逻辑没有这么做。

决策五：删除怎么处理？

链地址法删除节点时，需要找到目标节点，并修改桶头指针或前驱节点的 next 指针。删除头节点和删除链表中间节点是两个需要覆盖的边界情况。

如果 key 不存在，方法不修改任何状态。链地址法删除后不需要墓碑，因为从桶链表中移除节点不会影响其他节点的查找路径。开放寻址则不同：直接清空某个槽位可能切断后续探测路径，因此通常需要墓碑或其他删除修复机制。

本文没有实现缩容。大量删除后，桶数组可能比当前元素数量所需的空间更大。缩容可以减少空间占用，但也会带来重建成本；如果元素数量在阈值附近波动，还可能出现反复扩容和缩容。因此，缩容应作为独立设计决策，并通过不同的扩容、缩容阈值避免频繁抖动。

决策六：怎么遍历所有元素？

常见接口包括返回元素切片、提供按需推进的迭代器，或者提供回调式 Range。本文选择 Range：不必先创建包含所有元素的副本，并且可以通过回调返回 false 提前终止。

本文规定：Range 执行期间，不允许修改哈希表结构。原因是插入、删除和扩容都会改变桶或链表结构，可能导致元素遗漏、重复访问等问题。这个限制是本实现主动定义的 API 契约，并不是说 Go 原生 map 在遍历期间的所有写入都一律非法。

Go 原生 map 对遍历期间插入和删除有自己的语言规范语义；并发读写则是另一类问题。运行时可能检测到部分并发读写并触发 fatal error，但不能把它等同于普通的同 goroutine 遍历期间修改。

决策七：并发安全要不要支持？

本文选择不提供并发安全保证，并要求调用方自行同步访问。这样可以避免把锁管理引入基础实现，但并不意味着加锁一定会明显拖慢所有单线程场景；实际成本取决于实现、竞争程度和访问模式。

如果需要并发访问，可以在外层使用 sync.RWMutex 保护整个哈希表，也可以根据 key 分片加锁。不过，分片锁会增加实现复杂度，而且需要谨慎处理扩容、遍历以及跨分片操作。

Go 原生 map 同样不提供通用的并发读写安全保证。sync.Map 是针对特定并发访问模式设计的另一种类型，并不是所有场景下都能直接替代带锁的 map。

与 Go 原生 map 的差距

本文实现的目标是讲清楚基本机制，不是复刻 Go 运行时。比较时还必须注意 Go 版本差异：Go 1.24 起，内置 map 已采用基于 Swiss Tables 的新实现；Go 1.23 及以前的实现采用传统桶与溢出桶结构。不要把旧版实现细节直接描述为当前版本的内部机制。

  • 哈希与安全性：本文使用简单的 FNV-1a，适合教学但不是抗攻击的安全哈希。生产实现需要评估哈希碰撞攻击风险与输入特征。
  • 内存布局：本文每个 entry 都是独立节点，并通过 next 指针连接。当前 Go 原生 map 基于 Swiss Tables，采用开放寻址和分组查找，借助控制字筛选候选 key，以减少不必要的完整比较。
  • 扩容：本文一次性创建新桶数组并迁移全部元素，单次扩容可能带来较高延迟。具体运行时实现会随 Go 版本变化，应该以对应版本的官方资料为准。
  • 冲突处理：本文使用链地址法；当前 Go 原生 map 使用基于 Swiss Tables 的开放寻址方案。它们在空间布局、冲突处理、删除和增长策略上存在不同取舍。

可以阅读 Go 官方文章《Faster Go maps with Swiss Tables》，了解 Go 1.24 的实现变化。

结语：设计决策没有免费的午餐

哈希表的基本思想并不复杂：通过哈希函数把 key 映射到桶，再处理冲突。但工程实现中的每项选择都会带来约束。链地址法让删除简单，却引入指针和额外内存分配；桶数量取 2 的幂让索引计算直接，却要求扩容策略与之配合；全量扩容容易实现，却可能造成单次延迟尖峰；不提供并发安全降低了实现复杂度，却把同步责任交给调用方。

自己实现一次哈希表，真正要学会的不是背下某个阈值或某种结构，而是面对具体场景时，能说清楚：为什么选择它、它解决了什么问题、又把什么代价留给了后续。

这也是理解标准库的一个好方法。标准库里看起来复杂的实现，往往不是为了炫技，而是在性能、内存、延迟、安全性和兼容性之间做长期权衡。

这篇文章不打算罗列“Go map 怎么加锁”的几种方式，而是回答一个更根本的问题：为什么 Go 选择让程序直接死掉，而不是像其他语言那样返回一个错误，或者至少让你 recover 一下？

答案藏在 runtime 的设计哲学里。

一、崩溃现场：一个典型的“看起来没问题”

出问题的结构大致是这样：

包级 map，HTTP handler 里同时调 Get 和 Set。本地单线程测试没问题，压测时多个 goroutine 同时进来，就炸了。

触发的是两种 fatal error 之一：

  • concurrent map read and map write：一个 goroutine 读，另一个在写；
  • concurrent map writes：两个 goroutine 同时写。

关键在于：它不是 panic，是 throw。

二、runtime 是怎么发现的：一个标志位

这里要先说清版本。Go 1.24 起，内置 map 换成了基于 Swiss table 的实现，代码在 internal/runtime/maps；在此之前是 runtime/map.go 里的 hmap + bucket。两代实现的检测思路一样，但细节不同，网上的分析经常混着讲。

现行实现（Go 1.24+）

Map 结构体里有一个 writing uint8 字段。写操作不是“上锁”，而是翻转这个标志位，并在进入和退出时各检查一次：

三个细节值得注意：

  • 用异或而不是置 1／清 0。 源码注释说得很直白：并发写者不止一个时，翻转能提高双方都发现竞争的概率。如果只是置位，后到的写者看到 1 就死了；异或让状态在 0/1 之间来回翻，两个写者都更容易撞见对方留下的痕迹。
  • 进入和退出各查一次。 退出时的 if m.writing == 0 很容易被忽略：如果另一个写者在中途把标志翻回去了，这里也能抓到。
  • 遍历有单独的报错。 mapiterinit 检查的是同一个字段，但报的是 concurrent map iteration and map write。

历史实现（Go 1.23 及更早）

旧实现是 hmap 结构体里的 flags 字段，其中一位叫 hashWriting，值是 4：

  • 写操作开始时 h.flags |= hashWriting，结束时 h.flags &^= hashWriting；
  • 读操作检查 h.flags & hashWriting != 0，发现有人在写就 fatal。

思路完全一样，只是位运算和异或的区别。所以后面讨论的“为什么是 throw”，对两代实现都成立。

图 1：runtime 用的是“一个标志位 + 检查”，不是锁。写者进入时翻转标志，另一个写者或读者撞见非零值就触发 fatal；两边的操作并没有被串行化。

注意：这只是一个检测，不是同步。 两个 goroutine 可能刚好错开，也可能刚好撞上。所以表现为“偶发”——本地不崩，压测崩；低流量不崩，高流量崩。

还有一个容易踩的坑：对非空 map，delete 即使 key 不存在，也会走写路径、设置写标志。遍历时如果另一个 goroutine 在删任何 key，遍历都可能触发 fatal。

三、为什么是 throw，而不是 panic

这是整个设计中最关键的问题。

普通的 panic 会创建一个 _panic 结构体，挂到当前 goroutine 上，然后逆向遍历调用栈，执行 defer。如果某个 defer 里调了 recover()，程序就能继续跑。

throw 完全绕过这套机制。它把 fatal error 和当前 goroutine 的堆栈打印到标准错误，然后 exit(2)。没有 defer，没有 recover，没有“恢复”这个选项。

它选择这么做的理由很直接：当 map 的并发冲突被检测到时，内部状态可能已经损坏了。

想象一下：一个 goroutine 正在扩容、把旧表里的槽位搬到新表，另一个 goroutine 同时在读旧表的指针。runtime 发现的时候，控制字和槽位可能已经被改得面目全非——而检测本身只是一个标志位，它只知道“有人撞车了”，并不知道撞坏了多少东西。如果允许你 recover，程序继续跑，后续可能出现更诡异的行为——读到错误的数据、写入丢失、甚至内存越界。

直接死掉，是比“带着损坏的状态继续运行”更负责任的选择。

对比一下 Java 的 ConcurrentModificationException：它允许你捕获，然后继续用那个已经被并发修改过的集合。很多时候你的程序不会立刻崩，但数据对不对，就不好说了。

Go 选择了另一条路：在检测到确定性错误的那一刻，终止进程。 用一次响亮的崩溃，换掉后续所有不可预测的 bug。

图 2：panic 与 throw 的分岔——panic 会走 defer 链，路上还有 recover 这个出口；throw 直接打印堆栈并 exit(2)，没有回头路。

四、sync.Map 不是万能解药

知道原因之后，修复方式看起来很简单：加锁，或者换成 sync.Map。

但 sync.Map 的适用场景很窄，而且它的内部实现这些年也变过。

Go 1.24 起，sync.Map 换成了并发哈希 trie（internal/sync.HashTrieMap）：读操作沿树做原子加载，通常无锁；写操作只在命中的中间节点上加锁并替换节点。官方发布说明强调的改进是——修改不相交的 key 集合时，大 map 上的争用明显变少，而且不再需要预热（老实现要先攒出 dirty map，才能进入低争用状态）。

Go 1.23 及更早，它是 read + dirty 两层结构：读大多走 read 这层无锁快照，写则先在 dirty 里累积，攒够次数再提升为新的 read。

两代实现的共同结论没变：它的优势都在读多写少、key 集合相对稳定的场景。写非常频繁时，sync.Map 的写路径（加锁、替换节点、分配）未必比一把 sync.RWMutex 便宜。而且无论哪一代，Range 都不保证一致性快照——遍历期间看到的可能是部分更新后的状态。

所以实际选型通常是：

场景 推荐
读多写少，key 稳定 sync.Map
读写均衡，或需要强一致遍历 sync.RWMutex 保护的普通 map
高并发，锁竞争严重 分片锁（按 key hash 分到 N 个 map，各一把锁）

分片锁的思路和 Redis 的渐进式 rehash 有相似之处：把一个大问题拆成 N 个小问题，让冲突概率降下来。

五、重新理解 runtime 的“不宽容”

这次崩溃之后，我对 Go runtime 的看法变了一点。

以前觉得 fatal error 太粗暴，为什么不能给个错误码，或者至少让我记录一下现场。后来想明白了：map 的并发冲突不是“可以优雅处理”的错误，它是一个已经发生的数据损坏事件。

runtime 在 writing（老版本是 hashWriting）标志上做的检测，本质是一种尽力而为的哨兵。它不保证一定能发现（两个写操作可能刚好错开标志位检查），但一旦发现，说明冲突已经真实发生了。这时候程序内部的状态是否还能安全使用，没有人能保证。

所以它选择 throw。用进程的死亡，阻止损坏状态的扩散。

这其实和 Redis 渐进式 rehash 的设计哲学形成了有趣的对照：Redis 用复杂度换可用性，因为它是单线程的，不能让主线程卡住；Go 用进程死亡换正确性，因为 map 的状态一旦损坏，继续运行比崩溃更危险。

两种选择，面对的是不同层面的“正确性”。

如果你也在线上遇到过这个崩溃，第一件事不是急着加锁，而是用 go test -race 或 go run -race 在测试环境复现一次。-race 能告诉你哪个 goroutine 在写、哪个在读、以及它们各自的调用栈。这比线上盲猜高效得多。

至于那个包级 map——修法很简单，难的是意识到：Go 的 map 从来没有承诺过并发安全，而 runtime 用最不宽容的方式，让这个承诺变得无法忽视。

Redis 字典与渐进式 rehash：为什么“慢慢搬”是合理的选择

发表于 2026-10-25

如果你用过 Redis，大概率知道它“快”。但“快”从来不是偶然的。Redis 字典的渐进式 rehash，就是一个典型的例子：它为了不阻塞，主动选择了一种“看起来更慢”的搬迁方式。

这个选择的本质，是在回答一个问题：当一次维护操作的耗时随数据量线性增长时，你愿意把它摊开，还是让它一次性砸下来？

一次性 rehash 的账很好算：1 亿个键值对、单个迁移约 100 纳秒，乘起来就是 10 秒。对一个标榜毫秒级延迟的服务来说，这 10 秒等于服务中断。渐进式 rehash 的答案是——不追求“搬得快”，只追求“永远不停”。它把搬迁拆成一个个桶，塞进每一次普通的增删改查里，让开销跟着请求量自然摊薄。

代价也很实在：迁移期间内存占用翻倍、每次操作要查两张表、所有字典操作都要多一条“是否在 rehash 中”的分支。

下面按问题拆开讲：一次性 rehash 到底会阻塞多久？两个哈希表怎么协作？迁移过程中增删改查各走哪条路？为什么是“每次操作顺带搬”而不是“分批定时搬”？以及——这个设计最终牺牲了什么、换来了什么。

一、字典的基本结构：两个哈希表

Redis 的字典 dict 内部有两个哈希表：ht[0] 和 ht[1]。

正常情况下，数据都在 ht[0] 里，ht[1] 是空的。只有当需要扩容或缩容时，ht[1] 才会被分配空间，然后数据从 ht[0] 逐渐迁移到 ht[1]。

为什么要两个表？

因为 Redis 是单线程的。如果只用一张表，扩容时你得原地把所有元素重新计算位置——这在单线程下意味着什么都干不了。两张表 + 一个 rehashidx 索引，让迁移可以“边干活边搬”。

每个哈希表底层是数组 + 链表，用链地址法解决冲突。dictEntry 就是链表节点，同一个桶里的元素用 next 指针串起来。

图 1：两张表怎么协作。上半部分画迁移进行中的状态——ht[0] 左侧几个桶已经搬空，游标 rehashidx 停在当前要处理的桶上，箭头表示这一次只搬这一个桶（桶内通常 1~5 个节点），搬完游标右移一格；ht[1] 是新分配的、容量翻倍的表，搬来的节点落在里面。下半部分把迁移期间四种操作的规则并排放：查找要先查 ht[0] 再查 ht[1]，删除和更新两张表都要动，而新增只写 ht[1]——最后这条是关键，它保证 ht[0] 的节点数只减不增，否则旧表永远清不空。

二、一次性 rehash 到底会阻塞多久？

这是核心问题。要回答它，先看数据量。

假设：一个字典有 1 亿个键值对。

关键数字：Redis 迁移一个键值对的典型耗时，保守估计在 100 纳秒左右。

那么：

10 秒。 在这 10 秒里，Redis 的主线程完全被占住。所有客户端请求全部排队等待。 对于一个标榜 P99 延迟在毫秒级的服务来说，这是灾难性的。

更极端的场景：如果 value 是大 key（比如一个几百 MB 的 List），单次迁移的耗时可能以秒为单位。有测试数据显示，迁移一个 600MB 的 list 类型 key 需要 6.7 秒。这还只是一个 key。

所以答案很明确：一次性 rehash 的阻塞时间与数据量成正比，在百万级以上的字典中，阻塞时间会达到秒级甚至更长。 对 Redis 来说，这等于服务中断。

图 2：两种搬法的差别只在“什么时候搬”。左边一次性 rehash 把全部工作压成一根长条——这 10 秒里主线程被占满，客户端请求只能排队，延迟曲线上出现一根 P99.9 尖刺；右边渐进式 rehash 用同样的总工作量，但把它切成一个个小格，和请求交替执行，单次操作只多搬一个桶，延迟曲线保持平稳。底部一行是这张图的重点：两者*总搬迁耗时相同（都是约 10 秒的 CPU 工作量），差别只在单次最大停顿——从 10 秒降到微秒级的单桶开销，代价是迁移期间内存占用翻倍。*

三、渐进式 rehash 到底“渐进”在哪里？

Redis 的解法是：不一次性搬完，而是把搬迁工作分摊到每一次操作里。

具体机制：

  1. 扩容时，为 ht[1] 分配新空间（通常是 ht[0].used * 2 向上取最近的 2 的幂）；
  2. 把 rehashidx 设为 0，表示 rehash 正式开始；
  3. 每次对字典执行增删改查时，顺带把 ht[0] 中 rehashidx 位置上的整个桶（链表上所有节点）迁移到 ht[1]；
  4. 迁移完成后，rehashidx 加一，指向下一个桶；
  5. 当所有桶都迁移完毕，把 ht[1] 设为新的 ht[0]，清空旧表，rehashidx 重置为 -1。

关键细节：一次迁移的是一个“桶”，不是“一个键值对”。因为一个桶可能是一个链表，上面挂着多个节点。但从实际数据看，由于负载因子控制在合理范围，平均每个桶通常只有 1 个节点，最多一般不超过 5 个。所以单次迁移的开销很小。

四、迁移过程中，增删改查怎么处理？

这是设计中最精妙的部分。两个表同时存在，但操作规则不同。

操作 规则
查找 先在 ht[0] 找，找不到再去 ht[1] 找
删除 两个表都要操作（因为 key 可能在任意一个表里）
更新 两个表都要操作（先找到，再更新）
新增 只往 ht[1] 里加，绝不往 ht[0] 加

新增只写 ht[1] 的原因很直接：保证 ht[0] 的节点数量只减不增。 如果新增还往旧表里写，那 ht[0] 永远清不空，rehash 永远结束不了。

这个规则带来的一个副作用是：迁移期间的查找可能比平时稍慢，因为最坏情况下要找两张表。但这是可接受的代价。

五、为什么是“每次操作顺带搬”，而不是“分批定时搬”？

Redis 其实两种都有。

  • 被动搬迁：每次增删改查时顺带迁移一个桶（_dictRehashStep）；
  • 主动搬迁：服务器定时任务（databasesCron）中调用 dictRehashMilliseconds，在1 毫秒内尽可能多地迁移。

为什么以被动为主、主动为辅？

因为纯定时搬迁有一个问题：如果客户端一直不发请求，定时任务也不一定能保证及时搬完。 而且定时任务的执行时机依赖于 Redis 的事件循环，在高负载时可能被推迟。

被动搬迁的好处是：搬迁的开销天然地跟随负载分布。 请求越多，搬迁越快；请求越少，系统本身也不忙，晚一点搬完也无所谓。这是一种自适应的节奏。

主动搬迁则作为兜底：当客户端闲下来了，没有后续指令来触发被动搬迁时，Redis 不会“置之不理”，而是通过定时任务主动推进。dictRehashMilliseconds 每次只花 1ms 的 CPU 时间做搬迁，然后让出控制权。

所以准确地说：不是“不做定时”，而是“被动为主、定时为辅”。 两者结合，既保证了有请求时搬迁不拖后腿，也保证了没请求时不会永远卡在半途。

六、这个设计牺牲了什么，换来了什么？

牺牲的：

  1. 单次操作略慢。 迁移期间，每次增删改查都可能附带一次搬迁，或者需要查两张表。但开销被控制在单个桶的粒度，通常只有 1~5 个节点，对响应时间的影响很小。
  2. 内存占用翻倍。 rehash 期间两个哈希表同时存在，内存使用量会上升。这是“空间换时间”的典型体现。
  3. 实现复杂度上升。 所有字典操作都必须考虑“是否处于 rehash 状态”，代码路径分叉，更容易出 bug。

换来的：

  1. 不阻塞。 这是最核心的收益。无论字典多大，Redis 主线程永远不会因为 rehash 而停下来。
  2. 平滑的延迟曲线。 一次性 rehash 会导致 P99.9 和 max 延迟飙升；渐进式 rehash 把开销摊薄，让延迟保持稳定。
  3. 自适应节奏。 搬迁进度跟随负载，忙时搬得快，闲时搬得慢，不浪费 CPU。

哈希表、跳表还是 B+ 树：怎么选

发表于 2026-10-23

选择哈希表、跳表还是 B+ 树，本质上不是在选“哪个数据结构更好”，而是在回答一个问题：你的数据放在哪里，以及你打算怎么查它。

如果数据全在内存里、只按 key 精确找，哈希表是首选；如果数据在内存里、既要按 key 找又要按顺序取一段，跳表是那个“刚刚好”的答案；如果数据在磁盘上、既要等值查又要范围扫还要排序，B+ 树是几十年工程实践筛选出来的默认选项——但“磁盘”本身还要再拆一层：机械硬盘（HDD）和固态硬盘（SSD）的瓶颈不同，选型结论也会随之松动。

下面按场景拆开讲。

一、哈希表：只解决“这一个 key 在哪”

哈希表的核心优势只有一个：等值查询期望 O(1)。给定一个 key，算个哈希，直接跳到数组对应位置。没有树高，没有指针跳转，没有页分裂。

但它的问题也同样明确：数据是无序的。哈希函数打散了顺序，你无法高效地回答“比这个 key 大的下一个是谁”或者“把 100 到 200 之间的都取出来”。

所以哈希表的适用边界很清晰：

  • 纯内存场景。哈希表依赖连续数组和指针跳转，放到磁盘上，一次查询可能对应多次随机 I/O；更关键的是它无法把多个 key 打包进一个页，扩容和冲突处理在磁盘上代价极高。磁盘哈希并非完全不存在（如某些 KV 引擎的哈希索引），但在需要范围/排序的场景下劣势明显，工程复杂度也高。
  • 只有等值查询。Memcached、Redis 的键值对空间、以及各种内存字典，都是这个场景。一旦业务需要 WHERE id > 100 或者 ORDER BY，哈希表直接出局。

一句话：如果你确定永远不需要范围查询和排序，哈希表是最快的。但真实业务里，“永远确定”往往不成立。

二、跳表：内存里的有序结构，用简单换确定性

跳表解决的是哈希表解决不了的问题：在保持期望 O(log n) 查找的同时，支持范围查询和有序遍历。

它的结构是在有序链表上建多级索引，查找时从高层往低层跳，最终落到目标区间，然后沿底层链表顺序扫过去。范围查询的代价是“定位起点 + 顺序遍历”，非常自然。

图 1：跳表的两件事。上半部分是一条三层索引链，查找 90 时从 L3 一路往右下跳，折线只比较 4 次就命中；下半部分是范围查询，先用索引定位到区间起点，再沿底层有序链表一路扫过去。

跳表真正的竞争力，不在理论复杂度，而在工程上的“刚刚好”：

  • 实现比平衡树简单得多。红黑树插入删除要旋转、变色，跳表只改指针加概率建层；范围查询上，跳表沿底层链表直接扫，平衡树要走中序遍历（递归或显式栈）。对于需要自己实现或维护数据结构的系统来说，这是一个被低估的优势。
  • 局部修改、读路径易无锁化。这在 ConcurrentSkipListMap 这类并发容器里是实打实的优势。不过要注意，Redis ZSet 和 LevelDB MemTable 选跳表的主因并不是并发——Redis 命令执行本身是单线程，LevelDB 的写入也由 mutex 保护——而是实现简单 + 范围遍历顺手 + 内存开销可控。
  • 内存场景下 B+ 树的优势用不上。B+ 树为磁盘 I/O 做的所有优化（大扇出、页对齐、减少树高）在内存里都失去了意义。内存里一次指针跳转和一次数组访问的差距，远小于磁盘寻道和顺序读的差距。

Redis 的 ZSet 选跳表而不是 B+ 树或红黑树，逻辑就在这里：数据在内存，需要按 score 排序和范围取，跳表实现简单、范围查询顺手、内存开销可控。

一句话：内存 + 有序 + 范围查询，跳表是那个“没有明显短板”的选择。

三、B+ 树：为磁盘 I/O 而生，但有前提

B+ 树的所有设计，都指向同一个目标：把磁盘 I/O 次数压到最低。

它的关键特征：

  1. 非叶子节点只存 key，不存数据。这让每个磁盘页（InnoDB 默认 16KB）能塞下几百上千个索引项，扇出极高，树很矮。几百万行数据，树高通常只有 3~4 层。
  2. 数据全在叶子节点，叶子之间用链表串起来。范围查询和全表扫描变成沿着叶子链表顺序读，磁盘顺序读的性能远高于随机读。
  3. 节点大小对齐磁盘页。每次读一个节点就是读一个页，不浪费，也不多读。

图 2：B+ 树为什么磁盘友好。非叶子节点只存 key，所以一个 16KB 的页能塞下几百上千个索引项，扇出极高、树只有三层。数据全部落在叶子层，叶子之间用链表串起来——等值查询沿左侧虚线走「根 → 内部节点 → 叶子」，范围查询则沿底部绿色箭头在叶子链表上顺序扫。右下角对比了跳表：节点零散分布、每节点只存一个 KV，放到磁盘上一次范围查询就是多次随机 I/O。

关于 I/O 次数还要补一句：B+ 树的根节点和上层节点通常常驻 buffer pool，实际查询的磁盘 I/O 往往只有 1 到 2 次，比“树高 3 到 4 层”更乐观——树高是上界，不是每次查询都要走满。

代价同样明确：随机写、页分裂、写放大。这正是 LSM-Tree 用“顺序写 + 后台合并”换“读放大”的动机——那是另一个话题，但说明 B+ 树不是没有代价的“最优解”，而是在读写之间平衡得最稳的默认选项。

为什么 MySQL 不用跳表？因为跳表是为内存设计的。它的节点零散分布，每个节点只存一个 KV，放到磁盘上，一次范围查询可能触发大量随机 I/O。B+ 树把多个 key 打包进一个页，一次 I/O 取回一批，这才是磁盘友好的做法。

一句话：B+ 树不是“最好的”，但它是在等值、范围、排序、写入之间平衡得最稳的那个——前提是瓶颈在机械寻道或页级读取代价，而这一点在 HDD 和 SSD 上并不完全相同。

四、磁盘要分 HDD 和 SSD：瓶颈变了，结论要微调

把“磁盘”笼统当成一个东西，会掩盖一个关键事实：HDD 的瓶颈是机械寻道，SSD 的瓶颈是闪存写放大和擦除块约束。B+ 树的大扇出和页对齐是为前者设计的；面对后者，它仍然可用，但需要正视新问题，而 LSM-Tree 在某些写入场景下更具优势。

4.1 HDD：B+ 树仍然是标准答案

机械硬盘的随机访问代价极高（寻道 5–50 ms，加上旋转延迟），而 B+ 树把几百上千个 key 打包进一个页，一次 I/O 取回一批，正好把“随机寻道”转化为“少量页读取 + 页内二分”。叶子链表让范围扫描变成顺序读，顺序读在 HDD 上远快于随机读。所以前面“B+ 树为磁盘 I/O 而生”的论述，主要就是针对 HDD 的，逻辑几乎不需要调整。

4.2 SSD：B+ 树可用，但有两个新问题

SSD 没有机械寻道，随机读的代价极低（页级读取只需几十微秒），这意味着“把数据打包进页以减少寻道”的收益变小了。但 SSD 有自己的麻烦：

第一，原地更新代价高。 闪存必须先擦除整个块（128–512 KB）才能覆写，而 B+ 树的节点更新往往是原地写。SSD 通过 FTL（闪存转换层）做重映射来掩盖这个问题，但代价是写放大和垃圾回收（GC）。在写入密集的场景下，B+ 树的随机小更新会持续触发 GC，拖累性能。

第二，ZNS SSD 等新形态让问题更尖锐。 传统 SSD 靠 FTL 隐藏闪存特性，而 ZNS SSD 把写入约束暴露给主机：只能顺序写、同时打开的 zone 数量有限。把未经改造的 B+ 树直接部署到 ZNS SSD 上，吞吐量会明显下降，写入次数增加——这说明 B+ 树“为块设备设计”的前提，在新型 SSD 上并不自动成立。

图 3：HDD 与 SSD 的瓶颈不在同一处。左边机械硬盘，代价大头是磁头寻道（5~50 ms）加旋转延迟，B+ 树把几百个 key 打包进一页，正好把随机寻道换成少量页读取；右边固态硬盘没有寻道，但闪存必须先擦除整个块才能覆写，原地更新经 FTL 重映射后留下写放大和 GC，于是要再按写入强度分岔：读多写少仍是 B+ 树，写密集则考虑 LSM-Tree 或改造后的 B+ 树。

4.3 选型判断：加一层“写入强度”

在原有三步选型（数据在哪 → 要不要顺序 → 实现成本）的基础上，磁盘场景可以拆成两条分支：

条件 推荐 理由
HDD，或读多写少的 SSD 场景 B+ 树 读路径依然高效，工程成熟度无可替代
SSD，写入密集，且能接受读放大 LSM-Tree 把随机写转为顺序写，避开 SSD 的原地更新痛点
SSD，写入密集，但需要稳定读延迟 改造后的 B+ 树（如 buffered B+ tree / 冷热分层） 用缓冲或分层存储减少对闪存的随机小写

LSM-Tree 在 SSD 上的优势来自它“顺序写 + 后台合并”的机制，这与闪存“顺序写友好、原地更新昂贵”的特性天然匹配。代价是读放大和空间放大，所以它不是无条件更优，只是在写密集场景下值得优先考虑。

所以“磁盘 → B+ 树”更准确的表述是：HDD → B+ 树；SSD → 看写入强度，读多写少选 B+ 树，写密集考虑 LSM-Tree 或对 B+ 树做闪存友好改造。

维度 哈希表 跳表 B+ 树
存储介质 内存 内存 磁盘（HDD 为主；SSD 上可用但需权衡写入）
等值查询 期望 O(1)，最快 期望 O(log n) O(log n)，实际 1~2 次 I/O

所以怎么选，顺序是：

  1. 先问数据在哪。内存 → 继续往下。磁盘 → 再问是 HDD 还是 SSD、写入强度如何：HDD 或读多写少的 SSD → B+ 树；SSD 写密集 → LSM-Tree 或闪存友好改造的 B+ 树（LSM 本身是另一个话题，但它是这个分支的自然候选）。
  2. 再问要不要顺序。不要 → 哈希表。要 → 跳表。
  3. 最后问实现和维护成本。在内存有序结构里，跳表比平衡树更容易写对、更容易并发，这是一个经常被忽略但很实际的加分项。

前两步根据数据特征圈定候选集，第三步在候选集内做最终取舍。

部署

在我以往写代码的过程中，对于需要引用包的位置，并没有做任何区分，因为在使用 npm install 时会一起安装，所以没有太在意，直到使用 nest.js 时发现，默认安装的包居然有 200M 之多。
