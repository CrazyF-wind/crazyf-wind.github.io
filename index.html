如何绘制《一树鎏金·秋日银杏树》

发表于 2026-11-27

封面：t = 1.2 s。摄影机在树南侧约 23 米、离地 2.5 米，视线抬向 7 米高的树冠中心；太阳在树后偏左，整棵树以逆光为主。

模型：DeepSeek-flash4.1；harness：Claude Code；能力来源：一组对齐 three.js r186 的 threejs-skills。

配乐：HeyGen 曲库（track 89d7b95ce80f49ee9d1ecd27f23f5629）；网页 ?film=1 仍是静音预览，带配乐的版本在成片 MP4 里。

这篇文章复盘的是：一份只要求「一棵树」的提示词，如何落成一棵设计高度 14.2 米、47,871 片叶子的程序化银杏，以及围绕它的一条 30 秒、六镜头的绝对时间轴。

引言：一棵树要在六个距离上成立

《一树鎏金·秋日银杏树》的提示词只要求一棵树。没有山脉、没有建筑、没有街道，也没有第二棵树。

听起来比七峰简单。但提示词紧接着给了六个镜头：24 米看整体，19.5 米环绕看结构，8 米仰视看高度，3 米看叶脉，3.6 米看树皮，最后 23 米收尾。同一棵树，要在六个距离上都成立。

这就是树的难点。山可以靠体量和云海成立，建筑可以靠参数化构件成立；一棵树不行。远景看的是轮廓，近景看的是树皮裂纹和叶脉，微距看的是 0.27 米叶片上的 27 条叶脉。只在某一个距离上好看的树，是一张海报，不是一个三维对象。

提示词提前堵住了最容易的退路：

避免使用简单圆柱体加几个黄色球体代替银杏树。

不允许使用几个球形模型直接代替树冠。

不要让整个树冠变成均匀发光的黄色球体。

这三句「不要」对应三个结构决定：枝干必须真的分级；树冠不能有独立网格；透光必须是一个角度函数，而不是一个常数。

先说结论：这棵树能成立，不是因为某一处做得细，而是因为它有一条尺度阶梯——主干半径 0.63 米、主枝长 3 米、末梢小枝 0.4–1.2 米、叶片 0.27 米、叶脉 1 像素宽。六个镜头站在不同的台阶上，看到的是同一棵树的不同层级。 树冠不是画出来的，它是枝条长出来的。

一、提示词：把「不要」写成约束

这份提示词正文十二节（仓库里的 prompt/一树鎏金·秋日银杏树.md），从建模、树冠、叶片、动态、光照，一直写到镜头、交互、导出与验收。它没有给坐标表，也没有给树高以外的建模尺寸；它给的是尺度范围、六个镜头和一组禁止项。

真正被实现反复回应的，是下面几条：

提示词要求 实现
树高约 10–15 米 设计 14.2 米；主干顶约 8.6 米；实际最高叶 13.86 米
明显的根部扩张 7 条放射根，伸出 1.5–2.65 米；基部 5 瓣隆起
四级分枝、避免机械分叉 16 → 64 → 256 → 879；子枝绕随机三维轴散开

这张表里有几条不是「照做」，而是「翻译」。提示词说「不要圆柱体加黄球」，代码里没有去找一个更像树的现成模型，而是把「树」拆成一根主干、四级递归分枝，再把叶片挂到每一根带叶枝上。提示词说「不要均匀发光的黄色球体」，代码里就没有给叶片加一个恒定的 emissive，而是让透光随视线与太阳的夹角变化。

禁止项不是修辞。它们是在提前排除模型在信息不足时最容易选择的默认解。

二、尺度：从 14.2 米到 0.27 米

场景常量收在 src/config.js。坐标系沿用仓库约定：X 轴向东，Z 轴向南，Y 轴向上，1 世界单位约等于 1 米。树根落在地面原点，全场景只有这一棵树。

这里有一个值得先说的细节：treeHeight、trunkTop、crownRadii 和 LEAF.targetCount 都没有被代码读取。它们是对结果的描述，不是对结果的约束。

真正决定树冠形状的，是 47,871 片叶子的位置。把所有叶片位置取包围盒，得到：

轴 实际范围（米） 跨度
X −5.76 … 5.93 11.68
Y 2.42 … 13.86 11.44
Z −5.85 … 5.01 10.86

参考椭球写的是 5.85 × 5.0 × 5.85、中心在 8.75 米。实际包围盒与它很接近，但低处多伸出了 1.3 米——因为下层主枝是下垂的。参考椭球没有参与任何计算；它是对长出来的树冠的事后描述。 这一点在后面几节会反复出现：树冠的形状是枝条与叶片采样的副产品。

设计高度 14.2 米，实际最高的一片叶在 13.86 米。设计值比结果高 0.34 米，这 0.34 米不是误差，而是「文档描述了结果、但没有约束结果」的又一个例子。

每一级都在回答上一级留下的问题：主干回答「树有多粗」，主枝回答「树冠有多宽」，末梢回答「叶片挂在哪」，贴图回答「最近的镜头能看到什么」。

根盘是 7 条独立的曲线，从主干离地 0.62 米处向外斜插进地面，伸出 1.5–2.65 米，半径从 0.26–0.33 米收到 0.025 米。它们和主干一起被合并进同一个 BufferGeometry。

树皮是 Canvas 画的，三张 1024² 贴图：albedo、bump、roughness。albedo 上用 220 个大色斑、56 条纵向色带、1600 条生长纹、44 条裂纹、18 条更深的老年裂沟、90 块剥落的浅色树皮、260 个横向皮孔和 5200 个细碎颗粒叠出来；bump 和 roughness 不另外画，直接由 albedo 的亮度反推——暗的裂纹低、亮的树脊高，粗糙度则整体保持在 120–255 之间。材质是 MeshStandardMaterial，bumpScale 0.9、roughness 1.0，几乎不反环境光。

这里有一条项目备注值得记下来：锥形管的索引绕序必须让正面朝外。 绕序反了，看到的会是管体内壁，树干被错误地照成灰白，树皮纹理和阴影都会失真。这种错误不报异常，只是在某个角度看起来「颜色不对」。

最终，主干、7 条根、16 根一级主枝和全部下级枝条共 1,223 段，合并成一个网格。整棵树的枝干只占一个 draw call，约 6.9 万三角面。

四、分枝：四级递归，别长成一把梳子

分枝是一个递归函数。每根枝给定起点、方向、长度、半径和层级，走 4–5 步生成一条 CatmullRomCurve3，然后在曲线的中后段（约 36%–93%）长出 3–4 根子枝。

一级主枝有两组：

  • 主干上 12 根，从 y = 3.25 到 7.45 分布，越靠下越舒展，仰角从约 9° 增到约 37°（另有 ±6° 抖动）；
  • 顶部 4 根，从 y = 7.0 到 8.4 分布，主要向上撑起树冠上半部。

子枝的长度是父枝的 0.54–0.68 倍，半径是 0.56 倍。层级越深，管子越省：一级 14 × 9 段，二级 9 × 7，三级 7 × 5，末端 5 × 4。末端小枝已经细到不需要更多面数。

五、叶片：47,871 片，与一张 512² 的叶子

叶片不是模型，是一张画出来的贴图加一块微微卷曲的平面。

数量是这样长出来的：

  • 二级枝每根采 4–5 个点，三级 9–12 个，末端 15–19 个；
  • 每个点放 2 片，末端小枝有 45% 的概率放 3 片；
  • 树冠上半部（采样中点 y > 9.2）再乘 1.32，压住顶部过尖的轮廓；
  • 1,199 根带叶枝，平均每根约 40 片。

config.js 里写过 targetCount: 29000，但代码没有按它裁剪。最终 47,871 片是枝条结构的函数：枝条多、采样点多，叶子就多。叶片数量不是先定一个数再分配，而是先长枝条，再数叶子。

47,871 × 18 约等于 86 万三角面，全部装进一个 InstancedMesh。颜色用实例色写入，6 档调色板按权重取样：金黄 32%、浅黄 24%、琥珀 18%、橙黄 14%、暖金 8%、黄绿 4%，每片再乘 0.88–1.12 的随机明度。整棵树的叶片也只占一个 draw call。

六、树冠：密度是长出来的

场景里没有一个叫「树冠」的网格。tree.js 只创建两样东西：branches 和 leaves。所谓树冠，是 leafAnchors 上的采样点在空间里堆出来的形状。

这带来三个直接结果。

第一，轮廓不规则。 树冠的边缘由末端小枝的位置决定，而末端小枝的位置由每一级的随机散开决定。没有一条曲线去「描」树冠的外轮廓，所以它不会是一个球，也不会是一个被噪声扰动过的球。

第二，密度不均匀。 末端小枝多的地方叶簇密，二级枝长的地方叶簇疏；上层额外加密 1.32 倍，下层因为枝条下垂而显得薄。这种不均匀是结构带来的，不是手摆的。

第三，内部有缝。 叶片挂在枝条周围，不是填满一个实体；alphaTest 又把叶片之间的空隙保留下来。所以从 19.5 米的环绕机位看过去，树冠内部能看到枝干，而不是一堵黄色的墙。提示词要求「树冠内部不能完全被叶片遮挡，需要能够从特定角度看到树枝结构」，实现方式是让树冠本来就有结构，而不是事后挖洞。

微距镜头还有一个单独的处理。树冠东南缘有一根末端小枝，位置最接近 (4.0, 9.2, 2.8)；生成时在 879 根小枝的末段采样点里找离目标最近的一个，在它的 55%–100% 段上额外加密 120 片叶，缩放 0.82–1.32。最终选中的小枝点落在 (3.226, 8.489, 2.496)，微距机位的注视点就取这个值。

所以镜四不是「把树冠放大」，而是在真实小枝上加密一小簇叶，再用 31° 的视场和 0.0085 的光圈去拍它。焦点有真实的叶子可对，背景也仍然是树冠，而不是空洞。

图 1：t = 8.2 s，镜二。摄影机在半径 19.5 米、离地约 5.2 米的圆轨上，注视点固定在 7.18 米高；环绕用参数化圆轨而不是关键帧，树始终在画面中央。

七、光：只在逆光处点亮

提示词要求「秋日清晨或傍晚的暖色阳光」「阳光穿透金黄色树冠」「叶片边缘的暖色透光」，同时明确「避免过度泛黄、过曝和强烈的荧光效果」。

太阳的方向是 (−0.2, 0.34, −0.92)，归一化后仰角约 19°–20°，位于树的西北侧。摄影机从南侧看树时，太阳在树后偏左——这是整个场景的主视觉：逆光、低阳、树冠是一团发亮的金色，树干是暗的。

光照不是一盏灯。主光 3.0 强度，暖色 #ffd7a0；半球光 0.48；环境光 0.08；摄影机一侧的暖色补光 0.42；地面反弹光 0.68；轮廓光 0.48；树干特写时还有一盏摄影机侧柔光：影片里镜五开到 85，自由浏览的树干机位开到 80。主光投 2048² PCF 阴影，正交范围 ±12 米，覆盖整棵树和树根周围的地面。

叶片透光不是给材质加一个 emissive，而是在片元着色器里算两个量：

towardSun 只在摄影机朝着太阳看时接近 1；thinness 在叶面接近侧对镜头时接近 1。两个量相乘，结果就是：只有逆光角度、只有叶片边缘，才会亮。 正面看树冠时，叶片仍然是正常的受光材质，不会被一层恒定的黄色荧光洗平。

树冠背后还有 6 片加法混合的 Sprite，模拟阳光穿过枝叶后的散射。它们被树干和树冠真实遮挡，只在缝隙里露出来；透明度只有 0.018–0.03，随时间轻微脉动。这不是整屏的 god ray，而是几块被枝叶切碎的光。

后处理链是 RenderPass → BokehPass → UnrealBloom → Grade → SMAA → OutputPass。Bloom 强度 0.2、半径 0.5、阈值 0.9；Grade 做一点高光偏暖、阴影偏青的分色，暗角 0.28，颗粒 0.006，饱和度 1.035，对比度 1.028。Tone mapping 是 ACES Filmic，曝光 0.95。整套参数都压得比较保守，目标是「暖」，不是「亮」。

图 2：t = 13.6 s，镜三中段。摄影机在树干东南侧，离地约 3 米，到注视点约 8 米；镜头从 1 米高抬到 4.5 米，注视点从 3.3 米抬到 12.8 米；视场 57° → 55°，用来强调树干的高度。

落地高度查询 groundHeightAt(x, z)，所以每片叶子都落在真正的地面上，不会悬空。约三分之一的叶子被强制放在树冠南侧，因为南侧是大多数镜头的取景方向，叶片更容易从镜头前经过。每片叶子在生命周期开头 5.5% 淡入、最后 6% 淡出，避免凭空出现或消失。

结语：先搭好那把尺子

这棵树最容易被误解的地方，是把它当成一个「建模任务」。实际上，真正被反复调整的不是某一片叶子，而是尺度之间的关系：主干多粗、一级主枝多长、子枝散多开、末梢挂多少叶、贴图在最近的镜头里要撑到多少像素。

这棵树没有一条像 heightAt(x, z) 那样的全局高度函数。它的世界真值是枝条曲线：叶片的位置、朝向、风的相位、微距镜头的焦点，全部从这条曲线推导出来。改一根枝，叶片跟着动；改一片叶，树冠跟着变。树冠没有自己的几何，它是枝条的第二产物。

提示词的角色也一样。它最值钱的不是把「秋意」写得多浓，而是把「不要」写成了结构：不要圆柱加球，不要球形树冠，不要均匀发光的黄球。每一条「不要」都在逼实现去建立一个更底层的机制。

下次让模型画一棵树，先别急着加叶子。先问自己：这棵树要在几个距离上被看？每个距离由哪一级尺度回答？主干、主枝、末梢、叶片、贴图，哪一级是多余的？

发表于 2026-11-20

封面：成片里的七峰全景。通天峰居中，六座主峰散布在四周；山脚没入云层，只有峰顶的建筑与植被露出。

模型：DeepSeek-flash4.1；harness：Claude Code；能力来源：一组对齐 three.js r186 的 threejs-skills。

配乐：HeyGen 曲库（track 4e3d63277b074f4ca246938d6322bea7）；场景内声音仍由 Web Audio 程序化生成。

这篇文章复盘的是：一份把「青云七峰」写成坐标、高度、云层与镜头表的提示词，如何落成一片可漫游的山脉；以及成片之后，为什么又把七峰推倒重排了一次。

引言：七座峰，还是一条山脉

《诛仙》里的青云七峰，是通天、龙首、落霞、风回、大竹、小竹、朝阳。

让模型搭这个场景，最容易得到的是「七个景点」：每座峰单独看都成立，合在一起却像七张并排的概念图。原因通常不在建模精度，而在关系——峰与峰之间没有山脊、没有鞍部、没有主次，只有七个圆锥插在同一块平面上。

这份提示词一开始就防着这件事。它写：

不是七张独立的山峰图片，也不是简单的低模山体排列，而是构建一个具有真实空间关系、地形起伏、建筑群落、自然环境和动态云海的完整三维世界。

先说结论：这份提示词最值钱的部分，不是那些形容仙气的词，而是那张带单位和坐标的表；这个场景最值钱的部分，不是模型数量，而是一个所有东西都能查询的高度函数 heightAt(x, z)。

一、提示词：一份带单位的世界说明书

这份提示词正文一共十二节，从任务目标、世界观、七峰差异化建模，一直写到动态效果、镜头时间轴、字幕、性能、交付与验收；成片之后，末尾又追加了一节「核心构图方案」。

它不像一份「元素清单」，更像一份世界的说明书。最硬的部分是下面这张表：

龙首峰 (1450, −2500) 1390 1250 90

配合两行约定：

谷地基准高度 420 m，以下峰顶高度均为绝对世界 Y。

这两行把「仙山」拉回了可计算的尺度。位置、高度、半径、台地半径全部有单位，模型不需要猜「七峰应该怎么摆」，它只需要让地形函数在七个坐标上返回七个指定高度。

表之外还有三条优先级，后面的实现基本都在回应它们：

  1. 通天峰是中心。 它最高、体量最大，顶部有 150 米的建筑台地；六峰围绕它分布，高度不超过它的 78%（最终落在 65%–78%）。
  2. 单峰必须不同。 七座峰不能共用一套轮廓，山脊、悬崖、岩石、植被和建筑都要有各自的性格。
  3. 关系比元素重要。 峰与峰之间要有深谷、峡谷、山脊和云海；「不允许七座山峰使用相同模型简单复制」。

提示词也写了不少「不要」：不要简单圆锥，不要平面白色贴图铺满山谷，不要为了增加模型数量牺牲意境。这些禁止项不是修辞，它们是在提前排除模型在信息不足时最容易选择的默认解。

工具链是现成的：项目里装了一组 threejs-skills，按场景骨架、材质、光照、后处理、动画、性能等主题拆开，对齐 three.js r186；项目实际使用 three@0.186.0。Claude Code 负责读项目、跑构建、看控制台、改文件、再验证。

baseHeight 是谷地：

420 米的谷底加上一层低频起伏和一层脊状噪声，先给出「山地」的底子。真正的峰体在 peakBody 里：

  • 域扭曲：采样点先被 ±190 米的低频噪声推开，山脊和沟壑因此是弯的，不是笔直的圆锥母线。
  • 角度脊线：按极角生成脊线，让山体在不同方向上有不同的半径，形成各向异性的轮廓。
  • 径向剖面：0.6 * t^1.4 + 0.4 * smoothstep(0.5, 0.84, t)，缓坡山脚、中段陡崖带、峰顶收束。
  • 大尺度山脊场：再用一层 ridged2 乘上去，让山体长出分叉的脊与谷。
  • 冲沟：中段最强、峰顶与山脚减弱，避免山体表面像光滑的沙丘。
  • 卫星山脊：每座峰带三条较低的山腿，山脚才有延伸感。

这些参数不是七份复制。七座峰各有自己的 seed、stretch、rotation、ridge 和 palette：龙首峰被拉长成 1.65 倍，山脊像龙首探向主峰；小竹峰压到 0.72，峰体纤细；落霞峰用秋林调色，大竹峰用竹坡调色。

地形网格是四级同心方环，像 clipmap：

环 半宽 单元 用途

四级合计约 33.6 万顶点、66.6 万三角面。所有顶点都从同一个 heightAt 取样；相邻环共享边界坐标，粗环内边界再补一圈中点三角形，填平 T 型接缝。法线也统一由 normalAt 解析取样，而不是 computeVertexNormals，否则环与环的接缝处会出现一条亮度差。

顶点色按坡度、高度和所属峰写入：陡坡露岩，高处转灰，峰顶台地铺石，大竹峰偏竹绿，落霞峰偏赭红。AO 只对近环计算，四个方向、55 米半径，并在近环外缘渐隐到 1，避免与无 AO 的粗环形成接缝。

地形不是一张网格，而是一个契约。 只要所有系统都查询同一个函数，建筑就不会悬空，瀑布就不会穿山，镜头也不会飞进地里。

三、云海：48 步，把山脚藏起来

云海是这个场景最重要的视觉元素，也是最容易做成「白色平面」的地方。

提示词明确写了：不用平面白色贴图铺满山谷，要用体积云 Shader、3D 噪声或 Ray Marching。实现是一个后处理 Pass：先渲染场景颜色与深度，再由云 Pass 按像素反投影出世界射线，在 730–1460 米的高度层里步进采样，最后把半分辨率的结果双线性合成回场景。

密度函数是两层高斯：

主云海的密度峰值在 900 米，覆盖谷地和山脚；山腰云带在 1310 米，密度只有主云海的 1.5%，只擦过崖壁，不会盖住峰顶。

采样时还有三件事：

  • 云顶不是一块板。 低频噪声先把高度层整体抬高或压低约 ±130 米，再算密度。
  • 形状与覆盖分开。 smoothstep(0.5, 0.78, n) 决定云絮的形状，低频的 coverage 决定哪一片天空有云、哪一片是空的。
  • 深度遮挡。 每步用场景深度做 depthFade，云在离山体 70 米内逐渐变淡，形成软相交，而不是一条硬边。

光照只做三次采样：从当前点沿太阳方向走 55、110、165 米，累加光学厚度，再用 exp(-optical * 0.6) 得到太阳可见度，在冷色阴影和暖色受光之间插值；相位函数用 Henyey-Greenstein（g = 0.55），让逆光方向的云缘更亮。这就是云海「银边」的来源。

半分辨率是一个很实际的取舍：云 Pass 在 1280×720 下只处理 640×360 个像素，48 步，性能足够；合成回全分辨率时用线性过滤，边缘仍然是软的。代价是近景云层的细节会糊一点，但这个场景的云主要在几公里外，肉眼不容易察觉。

提示词最初写的是「山腰云带密度约为主云海的 15%，高度 1150–1500 米」。最终实现改成了 1.5% / 1310 米，uBandTop 收到 1460 米。原因是七峰重排后，六峰峰顶落在 1170–1390 米；15% 的云带会把峰顶洗掉。布局测试现在直接断言：六峰峰顶处的云带密度必须小于 0.02。

这是整份提示词里最有代表性的一次「数字失效」：15% 是写提示词时给的上界，1.5% 才是对着峰顶高度算出来的值。 数字不是合同，是起点。

四、建筑：主殿是尺度的锚

山体再高，如果建筑没有尺度，观众仍然读不出它有多高。

通天峰的主殿是一组参数化构件：86 × 46 米、9 开间、22 米高的殿身，上面叠 17 米高的重檐屋顶；后面是 46 × 26 米的后殿，两侧各一座 34 × 20 米的配殿，山门在南侧 138 米处，香炉、石灯、石碑和 140 米半径的环形栏杆围出一个完整院落。从山门往下，是 22 米宽、150 级的玉阶。

这些数字不是装饰。46 米的进深、17 米的屋顶，放在 150 米的台地和 1790 米的峰顶上，比例刚好能让「峰」看起来像一座山，而不是一块石头。

屋顶由同一个曲面函数生成：

  • ridgeHalf 是正脊的半长，脊外继续向两端收坡，得到歇山顶的轮廓。
  • edge 取「进深方向」和「脊外方向」的较大者，屋顶从脊向四面下落。
  • 1.35 次幂控制坡面的曲率，让屋面微微下凹，而不是一块直斜板。
  • |u·v|^4 只在四个角上起作用，把翼角抬起来。

同一套函数可以生成重檐：第二层整体缩小 20%，高度取 0.72 倍，往上叠 0.64 倍层高。方亭没有正脊，就自动改用金顶珠；四角各放一枚金色角饰。风格一致不是靠手工对齐，而是靠所有屋顶都来自同一个曲面族。

五、竹、水、鹤：让静止的世界有风

七峰里有两座竹峰。大竹峰 12 800 竿，小竹峰 5 600 竿，另有两层叶簇实例。

关键不是数量，而是分布。竹林不是均匀撒点，而是先选「竹林团簇」的中心：每片约 80 竿，中心要满足高度和坡度条件，再在团簇半径内按 sqrt(random) 分布。这样山坡上会出现一片一片的竹海，中间留出岩壁和路径，而不是一层均匀的绿色噪点。

六、镜头：36 秒，只有一个时钟

影片是 36 秒、60 fps、五个镜头。每个镜头有自己的 Catmull-Rom 机位曲线，切点在 8、15、22、29 秒；切点前后各 0.8 秒，穿云白场升到全白，遮住切换。

src/filmTimeline.js 是一个纯函数模块，不碰 DOM。给定时间 t，它返回机位、注视点、字幕透明度、转场透明度、片名透明度和黑场透明度。播放器只负责把返回值写进相机和 DOM。

八、推倒重排：提示词也要过审

第一版七峰是按提示词最初那张坐标表落位的。那座山脉能跑、能拍、能导出，但看起来仍然像「七个各自成立的景点」。

问题不在模型没按提示词做，而在提示词只把「通天峰最高」写成了意图，没写成可执行的比例。

初版的散文部分只说「通天峰必须是中央主峰，海拔最高，体量最大」，没有给出比例；表里龙首 86%、风回 89%、朝阳 81%，三座峰都逼近主峰。模型面对「具体数字」和「模糊意图」时，会优先服从具体数字——它把表执行得很准确，于是主峰不再明显高出群山。

空间上也有类似的问题：六峰虽然各有方位，但整体仍像六座各自为政的山头，峰与峰之间只有谷，没有山梁。缺少「同处一条山脉」的证据。

修法不是往代码里打补丁，而是回到提示词的第一节，把构图原则写成最高优先级，并补上一条可以被测试的比例。提示词末尾追加了一节「核心构图方案：中央主峰统领群山（方案 A）」，明确：

  • 通天峰居中，最高、最大；
  • 六峰高度为通天峰的 55%–78%；
  • 不允许排成同一高度，也不允许围成完美圆环；
  • 峰与峰之间要有低矮山脊、峡谷和深谷，不能是七个独立圆锥。

这条 55%–78% 是这次重排里最有用的改动。它把「主峰要高出一截」从一句形容，变成了布局测试可以直接断言的数字。

把《枫桥夜泊》拆成四条时间轴：一首诗如何变成三维场景

发表于 2026-11-12 更新于 2026-11-13

封面：1.6 秒处的开场。月亮已经压得很低，石拱桥和枫林只是江岸上的剪影，月光在江面拉出一条断续的银蓝色碎影。

模型：DeepSeek-flash4.1；harness：Claude Code；能力来源：一组对齐 three.js r186 的 threejs-skills。

这篇文章复盘的是：一份把《枫桥夜泊》拆成空间、时间与机制的提示词，如何落成一个可漫游的三维场景，并导出成 40 秒、60 fps 的短片。下文把输入的那份提示词称为「世界说明书」，把产出称为「场景 v1」。

引言：二十八个字，四十秒

《枫桥夜泊》只有二十八个字。它写了月、乌、霜、江、枫、渔火、姑苏城、寒山寺、钟声、客船。如果只是把这些名词做成模型，一件件摆进画面，得到的是一张会动的明信片，不是这首诗。

诗里真正难画的是动词和时间：月「落」，乌「啼」，霜「满天」，渔火「对」愁眠，钟声「到」客船。落是一个过程，到是一段延迟。把诗变成场景，关键不是把名词堆齐，而是为每个动作找到一个可以被渲染的机制。

这份世界说明书一共十一节，从色彩、建模、动态、镜头、字幕，一直写到导出规格。它不像一份「元素清单」，更像一份世界的说明书：先规定这个夜晚的光、色、尺度和方位，再规定什么东西在什么时候动。

先说结论：这首诗最适合被拆成四条时间轴——月落的轴、风吹叶落的轴、寺院显形的轴、钟声抵达的轴。四条轴对齐在同一个 40 秒里，诗就成了镜头。

一、诗里能动的，是动词

把四句诗拆开，会看到两种东西：布景和机制。

诗句 布景（名词） 机制（动词 / 时间） 主要实现
月落乌啼霜满天 月、乌、霜、天 落、啼、满天 sky.js、birds.js、mist.js
江枫渔火对愁眠 枫、渔火、客船 并置、静默、摇曳 trees.js、fishing.js、boat.js
姑苏城外寒山寺 城、寺、山 城外（距离）、显现 terrain.js、temple.js、雾
夜半钟声到客船 钟、船 到（传播延迟） temple.js、water.js、audio.js

名词决定场景的体积，动词决定动画的预算。提示词里最值钱的句子，往往不是「要有枫树」，而是「部分落叶随风飘落，偶尔落在江面」——它把一棵树从一个静态模型，变成了一个持续发生的系统。

这份提示词还有一个很清楚的取舍：它反复写「不要」。不要做成暴雪，不要科幻雷达波，不要霓虹圆环，不要平面插画代替三维场景，不要让船悬空或穿模。这些禁止项不是修辞，它们是在提前排除模型在信息不足时最容易选择的默认解。

二、先定世界基准，再谈物件

场景 v1 的所有坐标都收在一份 src/config.js 里。这不是为了代码整洁，而是为了让「江」成为整个世界的基准。

坐标系沿用仓库约定：X 轴向东，Z 轴向南，Y 轴向上，1 个世界单位约等于 1 米。河道沿 X 轴展开，z = 0 是江心；南岸是近景的枫桥、枫林、码头与客船，北岸抬升为寒山寺所在的山坡。

水面高度、陆地高度、河宽、寺院台基，是四个共享的水平面。桥、船、树、寺、渔火都从这几个常量上长出来，而不是各自记一套魔法数字。客船到寺院在 Z 方向上相差 141.4 个单位；这个距离不是随手写的，它同时决定了第 16–26 秒镜头隔着多远的江面去「看」寺院，以及雾要浓到什么程度，才能让寺院「若隐若现」。

月亮的方向也是常量：(-0.55, 0.08, -0.83)，仰角大约 4.5°。它压在西北天际线附近，所以才有「落」的余地。提示词里那句「月亮位于远山与天际线附近，呈现月落状态」，最后落成一个随时间缓慢下沉的方向函数：

40 秒里，仰角从约 4.5° 降到约 2.7°。变化很小，小到单看一帧几乎察觉不到；但把它交给时间轴，月亮就真的在落。诗里的「落」不是一个状态，是一个斜率。

三、四句诗，四种机制

1. 月落乌啼霜满天

这一句有三个动作，分别落在三个模块里。

天空是一整块 shader。月盘、月海、边缘亮环、月晕、贴近地平线的薄云和稀疏星光都在同一个片元着色器里计算。星光用 step(0.9981, star) 筛出来——只保留约千分之二的网格，正好是「少量星光，不要过度密集」的分量。

乌鸦是低多边形剪影：身体、头、喙、尾，两片可以上下扇动的翅膀。三只乌鸦各自沿一条 CatmullRomCurve3 飞行，用 getPointAt 取位置、用切线定朝向，转弯时按曲率侧倾，翅膀按正弦节奏扇动。它们只在各自的时间窗里出现，所以画面里始终只有一两只，不会变成一群。

「霜满天」最容易被做错。提示词专门写了「不应把画面做成暴雪或大面积飘雪」。最终的方案是 520 个极细的霜粒，加上贴着水面缓慢流动的雾片；它们不是天气系统，只是一层几乎看不清的冷凝感。观众不会注意到霜粒，但会觉得空气是冷的。

这就是「意境」在工程里的样子：不是把比喻做大，而是把它做小，小到刚好能被感觉到。

2. 江枫渔火对愁眠

枫树是递归生成的。主干分出枝，枝再分叉，直到末梢；叶簇和带枫叶剪影的叶片卡片全部用 InstancedMesh。真正让树「活」起来的是一段注入到材质里的顶点风场：每个顶点按世界坐标和时间获得一个很小的位移，整片树冠因此以不同的相位轻轻摇动。

但只有整片摇动还不够。提示词还要「少量枫叶从树枝上脱落，飘落江面」。于是另有 120 片独立模拟的落叶：每片有自己的速度、旋转和相位，受重力和侧风影响；落到 waterLevel + 0.015 时停止下落，转为漂浮，漂 8–12 秒再重新生成。

这里有一个很实用的分层：大面积的叶子交给 GPU 的顶点着色器，少量需要「叙事」的叶子交给 CPU 逐片模拟。 如果 120 片叶子也走 shader，它们会整齐得像一场雨；如果整棵树都走 CPU，2K / 60 fps 的预算立刻不够。

渔火是另一层。江面上有五艘渔船，分布在远近不同的位置，每盏灯有自己的闪烁相位。它们通过 water.setLantern(index, position, color, power) 注册到水面 shader，最多 10 盏。船上的灯是暖橙色 #FFAD58，月光是银蓝色 #B7C9DE；这一冷一暖的对比，就是「对愁眠」里那个「对」字的视觉支点。

客船停在 (14, 23.4)。船体由逐站截面放样，木舱、竹篷、桅杆、收帆、缆绳和船头灯笼各自成组；船身随水流横摇、升沉、轻微偏航，舱内暖光与窗棂后的诗人剪影保持安静。提示词说人物「不需要复杂的人物动画」，这个克制是对的——诗人一动，画面就从「夜泊」变成了「夜航」。

图 1：9 秒处的江岸。枫树的暗红树冠压在画面上方，渔船灯火在江面拉出暖色倒影；冷的月光和暖的渔火在同一个水面 shader 里共存。

3. 姑苏城外寒山寺

寒山寺在 z = -118，客船在 z = 23.4，中间隔着 141 个单位的江面。提示词要求「建筑轮廓能够被观众辨认，但不应过于突出」「寺院与客船之间存在明确的空间距离」。场景没有靠把寺院做小来实现「远」，而是叠了三层：

  1. 距离：寺院真的在江对岸的山坡上，台基高度 9.2，从客船看过去需要仰视。
  2. 雾：FogExp2，密度 0.0029，越远越接近雾的颜色 #27313F。
  3. 景深：BokehPass 的聚焦距离随相机与注视点更新，远处的屋檐自然变软。

寺院的建筑本身共用一套屋面生成器。山门、主殿、偏殿、钟楼、五层塔的屋顶都由同一个函数生成，用 t 参数控制屋脊高度、坡面曲率和四角起翘；改变尺寸与起翘量，就能得到不同等级的建筑。这样做的价值不在省代码，而在风格一致：所有屋檐的弧线来自同一个曲面族，远看才不会像拼贴。

图 2：24 秒处，寒山寺从雾里显形。寺院被距离、雾和景深三层推开，轮廓可辨，但不抢客船。

4. 夜半钟声到客船

这是全诗唯一一句明确写了「传播」的诗。前三句都是视觉，第四句突然变成听觉；而且「到」字说明钟声不是同时在所有地方响，它需要时间。

场景把这件事写成了绝对时间：

  • STRIKE_TIME = 28.6 秒，撞木在 25.6 秒开始向后拉开，28.2 秒开始荡向古钟，28.6 秒撞上。
  • 钟体在撞击后按指数衰减摆动：sin(strike * 4.1) * 0.105 * exp(-strike * 0.85)。
  • 钟体本身还有极细的震动：sin(strike * 38) * 0.012 * pulse，同时暖光按 exp(-strike * 1.7) 脉冲一次。
  • 31.1 秒和 32.4 秒，江面在客船附近出现两组同心涟漪——这是钟声「到」的时刻，距离撞钟晚了 2.5 秒和 3.8 秒。

声波的视觉化是最容易过火的地方。提示词写得很明确：「使用透明环形波纹、空气扰动等视觉方式」「不要使用科幻雷达波或夸张的霓虹圆环」。最终的实现是四道 220×220 的平面，加法混合，半径在 7 秒内从 0.06 扩到 0.76；透明度只有 0.045 - i * 0.006，波前还被噪声打散成不连续的弧。换句话说，它几乎看不见——只在寺院前的雾里留下一圈很淡的扰动。

江面的涟漪则通过 uniform 写进水面 shader：最多 6 组 (x, z, 起始时间, 强度)，每组的径向斜率叠加到基础波场上。钟声抵达时，涟漪从客船附近向外扩散，和月光、渔火共用同一套法线。

图 3：34 秒处的钟楼。古钟悬在二层，撞木已经荡开；钟体的青铜色和寺院的暖光只在局部出现。

图 4：30.4 秒，钟声正在越过江面。波前被噪声打散，透明度极低，只够让雾和江面轻轻动一下。

声音本身由 Web Audio 实时合成：钟声是几组带轻微拍频的正弦分音，乌鸦是滤波后的噪声脉冲，水声和风声是噪声加低频振荡；混响发送量 0.36，让钟声在江面上留一条尾巴。成片音轨则用 Python 离线渲染，和画面在同一张时间表上对齐。

四、水面：四句诗叠在同一个 shader 里

江面是整篇文章里技术密度最高的部分。它用 Reflector 做真实的平面镜像——天空、寺院、枫树、灯火都会被反射——再在镜像之上叠一层自定义 GLSL。

这一层 shader 同时负责五件事：

  1. 波纹：四组不同频率、不同速度的行波叠加成斜率，再用两层低频噪声打破规则感。
  2. 反射扰动：用波斜率偏移反射纹理的 UV，让倒影随水波扭动；再取一次偏移更大的采样做混合，避免倒影太干净。
  3. 月光碎影：沿「相机 → 月亮」的方位拉出一条细长的银色路径，路径内部再用高光项和噪声切成断续的碎片。
  4. 渔火倒影：把每盏灯沿水面镜像，取「相机 → 镜像点」的线段，在江面上形成一条被噪声打断的暖色光带。
  5. 钟声涟漪与贴岸泡沫：涟漪作为径向斜率叠加；靠近岸线 |z| > 31 时压暗水面，形成一条暗色水线。

月光那一段值得单独看：

它没有一张「月光贴图」。月光之所以在江面上，是因为相机、月亮方位和水面法线在每一帧重新算了一次。镜头一动，碎影跟着动；月亮下沉，路径跟着偏。渔火倒影同理。倒影不是画上去的，是算出来的。

这也是提示词里那句「通过 Shader 实现水面反射和扰动」真正的价值：它要求的不是某个 API，而是一种建模方式——把水面当成一个光学系统，而不是一张会动的背景。

图 5：16 秒处的客船。船体、木舱、竹篷和缆绳都是程序化生成；舱内暖光只够照亮窗棂和诗人的轮廓。

五、40 秒是一条函数

影片时间线在 src/film.js。它只做一件事：把任意时刻 t 映射成相机位置、注视点、字幕透明度和世界状态。

相机不是用关键帧动画软件做的，而是两组关键点加 Catmull-Rom 插值：

每个关键点同时给出位置和注视点，两个都做 Catmull-Rom 插值。这样相机既经过每个机位，又保持速度连续，不会在关键点之间突然拐弯。35 秒之后换用另一组 FINALE_KEYS：镜头回到客船，再拉远到全景。

35 秒处有一次刻意的黑场。钟楼在江对岸，客船在南岸；如果让相机直接横跨 141 个单位的江面，观众会看到一段没有叙事的长距离平移。黑场遮住这次切镜，比硬切更自然，也比强行飞过去更诚实。

时间 镜头 字幕 主要机制
0–7 s 高空俯视，月落江天 月落乌啼霜满天 月亮下沉、乌鸦飞行、霜粒与雾
7–16 s 下降掠过枫林与渔火，靠近客船 江枫渔火对愁眠 风场、落叶、渔火倒影、船体横摇

35–40 s 黑场切回客船，拉远，全诗淡出 全诗 第二组相机曲线、字幕淡出

字幕不单独做动画状态机，而是几个 fade(t, inStart, inEnd, outStart, outEnd) 窗口。applyOverlay(t) 每帧根据绝对时间设置透明度和位移；拖动时间轴时，字幕会直接落到正确的位置，不会「补动画」。

这套结构还有一个直接好处：可重复导出。 在 ?film=1&capture=1 下，页面关闭实时循环，由 window.__capture.renderAt(t) 以固定 1/60 秒步长推进；deterministic.js 用固定种子覆盖 Math.random，树叶、乌鸦、雾和渔火的随机相位每次导出都一致。2400 帧捕获了 349 秒，平均约 6.9 fps；中断后可以加 --resume 从已有帧继续。

如果所有状态都从 t 推导，那么播放、暂停、拖动时间轴、重导出就是同一个函数的不同调用方式。反过来，只要有一处动画依赖「上一帧的状态」，时间轴一拖就会漂移，导出也无法复现。

图 6：38 秒处的收尾。镜头回到客船，远处寒山寺隐入夜雾，诗名、作者与四句诗依次浮出。

六、三个看得见的坑

第一，阴影贴图不能在首帧之前关掉。

项目一度把 renderer.shadowMap.autoUpdate 设为 false，想省掉每帧更新阴影的开销。结果是首帧没有生成阴影贴图，所有 MeshStandardMaterial 在采样 sampler2DShadow 时失败，整批网格直接不绘制。画面不是「阴影不对」，而是「东西不见了」。现在保持 autoUpdate = true。这条教训很具体：性能优化必须在首帧就验证，不能只看后面的帧率数字。

第二，可重复导出不是默认能力。

树叶、乌鸦、雾和渔火都用了随机数。如果不固定种子，每次导出的帧序列都不一样：第 1200 帧的某片叶子可能在这里，也可能在那里。deterministic.js 在捕获模式下覆盖随机源，导出脚本从 0 秒重放，才让「同一份代码导出同一段视频」成立。

第三，2K / 60 fps 的预算决定了雾的做法。

提示词要求「避免过度使用高成本实时体积渲染」。场景里的雾因此是贴水的横向雾片、寺院前的雾团和极细的霜粒，而不是体积雾；阴影是单主方向光的 2048² PCF；叶簇、叶片、栏杆柱、芦苇、山树全部实例化；像素比上限 1.6。这些选择不显眼，但它们决定了 2400 帧能不能在 349 秒内跑完。

八、这份提示词为什么有效

回看这份世界说明书，真正起作用的不是篇幅，而是六种写法。

1. 先写世界基准，再写物件。
提示词第一节不是「要有哪些建筑」，而是天空、山、江、雾、月光的关系。场景因此先有了一条江和两岸的高程，再往上长桥、树、船、寺。

2. 用 hex 和数值代替形容词。
「深蓝黑 #101A2C」「月光银蓝 #B7C9DE」「渔火暖橙 #FFAD58」——这些值直接变成 COLORS 常量，也直接约束了后处理、灯光和水面 shader。形容词只能表达偏好，数值可以验收。

3. 每句诗绑定一个镜头、一个字幕窗口、一个机制。
0–7 秒对应月落与乌啼，7–16 秒对应枫与渔火，16–26 秒对应寺院显形，26–35 秒对应钟声抵达。时间轴不是后期配的，它在提示词里就已经和诗句对齐。

4. 写禁止项。
「不要做成暴雪」「不要科幻雷达波」「不要平面插画代替三维场景」「不允许悬空或穿模」。模型在信息不足时会选最省力的默认值；禁止项就是提前堵住那些默认值。

5. 给可验收的标准。
40 秒、60 fps、2560×1440 或 3840×2160、四句诗对应四个镜头、声波与钟声同步。这些标准可以在浏览器、ffprobe 和截图里逐条检查，而不是「感觉对不对」。

6. 让所有状态由绝对时间推导。
这条提示词没有直接写出「绝对时间」四个字，但它要求时间轴拖动、自动演示、重播和逐帧导出。满足这些要求的唯一稳妥方式，就是让相机、字幕、钟摆、涟漪都成为 t 的函数。

还有一条元规则：让 skill 管 API，让提示词管世界。 提示词不去复述 Three.js 的用法，而是把篇幅留给「这个夜晚应该长什么样、什么时候发生什么」。

九、边界：场景能画到哪里

场景 v1 是风格化还原，不是唐代建筑与船型的考据。石拱桥的拱圈、客船的船体、寺院的屋面，都是从真实形制里抽出来的几何特征，不是实测模型。木材、石材、瓦片、树皮、枫叶的纹理全部由 Canvas 程序化生成；它们可控、可复现，但细节有上限。

比建模更远的边界是「意境」。构建可以通过，脚本可以全绿，ffprobe 可以逐项对上，截图可以非空；但「清冷、孤寂、悠远」最终仍然要人眼看。本文用到的七张配图只做了尺寸与非空校验，没有做人眼审美判断——那一步得留给读者。

还有一层：诗的意义不在几何里。场景能提供的是一个可以走进去的舞台，它不能替代诗，也不应该替代诗。

场景是一个独立的 Vite + Three.js 项目，位于 material/枫桥夜泊/。环境要求 Node.js ≥ 20.19，以及支持 WebGL 2 的桌面浏览器。

结语：先找到那句诗的「机制」

「绘制」这个词有点误导。我们画的不是一张图，也不是四张配图，而是一组会随时间发生的关系：月亮下沉，树冠摇动，落叶落水，寺院从雾里显形，钟声越过江面，最后抵达客船。

二十八个字里，真正需要工程化的不是名词，而是时间。月落是 40 秒的下沉，钟声是 2.5 秒的抵达，枫叶是 120 个实例的循环。诗不在模型里，在这些时间里。

下次让模型画一首诗，先别急着列名词。先问自己：哪一句里有时间？哪个动作需要一个系统？把那个系统写进第一节。

如何绘制一幅《上海外滩》v1.0

发表于 2026-11-06

封面：v2.0 的默认机位。黄浦江从画面左侧远处流入，在陆家嘴北侧绕出一个大弯，再向右前方流出；四座地标落在弯道内侧的半岛上。

模型：DeepSeek-flash4.1；harness：Claude Code；能力来源：一组对齐 three.js r186 的 threejs-skills。

这篇文章复盘的是：同一个模型，为什么第一版只搭出「像外滩的元素」，第二版才搭出「能读出外滩的城」。下文把两份提示词称为「第一版」「第二版」，把产出称为「场景 v1」「场景 v2」，避免混淆。

引言：我要的是一座城，不是一张图

我想让模型替我搭一个可交互的 3D 场景，而不是生成一张图。

「可交互」三个字抬高了门槛。一张图只需要在某个角度成立；一个场景要在任意角度、任意时间状态下都成立。几何、材质、光照、后处理、镜头、性能，任何一项掉链子，画面都会立刻露馅。

我用了两版提示词。第一版要到了外滩的元素，第二版才要到外滩的空间。两版之间的差别，不是字数，而是先说什么。

先说结论：决定这类场景成败的，不是模型会不会写 Three.js，而是提示词有没有把空间关系写成可执行、可验收的约束。 skill 负责让 API 用对，提示词负责让世界成立。

我用的不是「一个 three.js 提示词」，而是一组按主题拆开的 skill。它们来自 cloudai-x/threejs-skills，在项目里由 skills-lock.json 锁定版本，安装后通过 .claude/skills 指向 .agents/skills 下的实体目录。

这一组 skill 都对齐 three.js r186，一共 13 个：

分组 skill 管什么

二、第一版：一份「物件清单」

第一版提示词是这样的：

这份提示词写得不算差。它把「一个高质量 Three.js 城市景观」拆成了可以逐条勾选的要求。模型也逐条交付了：四座地标、反射水面、游船、车流、昼夜切换、Bloom、轨道控制器，一个都不缺。

问题出在条目之间没有关系。

于是画面里出现了三个症状：

  1. 没有骨架。 黄浦江是一条直的水带，不是一条河。外滩之所以是外滩，首先因为江水在那里拐了一个弯。
  2. 建筑是孤岛。 每栋楼都按坐标放对了位置，但楼与楼、楼与岸线之间没有生成关系。外滩建筑群像一排摆好的模型，而不是沿着岸线长出来的城市。
  3. 镜头替观众做了选择。 平视镜头能看清单栋楼和滨江步道，但看不到城市形态。读者第一眼看到的是「一排楼」，不是「一座城」。

这不是模型偷懒。提示词只说了「设置黄浦江」，没有说这条江怎么弯、陆家嘴在弯的哪一侧、镜头从哪里看。信息缺失时，模型只能选最省力的补全方式：直线、矩形、平视。它在每个局部都做对了，却在整体上做错了。

三、第二版：把地理写进第一节

第二版提示词换了一个开头：

相比第一版，真正的改动只有四处，但每一处都改变了模型的行为。

第一，把地理放到第一节，并标注「最重要」。 提示词里的顺序就是模型的注意力顺序。第一版把「地标」放在第 1 条，模型就先堆地标，再补河；第二版先定义河，地标只是河湾内侧的产物。

第二，把形容词换成可执行的几何。 「U 形」「从画面左侧远处延伸」「向中央区域大幅弯曲」「绕过陆家嘴区域向右侧远处延伸」「马蹄形」「真实城市地理尺度」——这些描述可以直接变成一条曲线上的控制点和一段宽度函数（实现时河宽落在 390–620 米之间），而不是一句「要有外滩的感觉」。

第三，给出实现路径。 「使用 CatmullRomCurve3 等曲线技术构建河流中心线和岸线，再生成连续水面网格」「建筑、道路、河岸、水面分别建模，保持空间关系一致」。这不是替模型写代码，而是告诉它：用一条曲线作为所有沿江构件的共同基准。

第四，写禁止项和验收标准。 「而不是直线河道或普通弧形滨江」「不采用地面平视视角」「不要只展示单栋建筑或局部滨江景观」——这三句排除错误解；「第一眼能够识别出上海陆家嘴和黄浦江」「从整体俯视视角能够清晰看到……U 形蜿蜒轮廓」——这两句给出可以被眼睛检查的通过条件。

这三层合起来，才是第二版真正有效的原因：约束可执行，结果可验收，优先级明确。

四、落到代码：河道成为唯一空间基准

提示词里那句「用 CatmullRomCurve3 构建中心线」，最后落成了一个 src/world/river.js。它只做一件事：把整条黄浦江变成一套可以查询的空间坐标。

29 个控制点定义了河道的走向，按弧长均匀采样 900 段，得到每个采样点的位置、切线、法线和半宽。这里用 centripetal 参数化，是为了减少急弯处的过冲——河道弯得越急，普通 Catmull-Rom 越容易在控制点之间甩出一段不自然的弧线。

紧接着是一段容易被忽略、但不写就会出事的逻辑：

岸线不是单独画的，而是中心线向两侧偏移「半宽」得到的。弯太急、河太宽，偏移后的内岸会自己穿过自己。所以急弯处必须收窄河宽，0.62 是给偏移留的安全余量；之后再跑两遍平滑，避免宽度在曲率突变处出现折角。

然后，所有沿江构件都从这里取点：

  • 水面沿着中心线生成连续 ribbon，而不是一张矩形平面；边缘带 aEdge 属性，用来画贴岸泡沫。
  • 陆地是一整块 ShapeGeometry，河道作为 Path 孔洞挖掉，避免水面和地面互相穿插。
  • 岸墙、步道、滨江道路用 createRibbonGeometry / createBankWallGeometry 沿河生成。
  • 外滩 16 栋历史建筑沿着浦西一侧的 bankPoint 逐栋排布，并朝向江面。
  • 游船和货轮沿着中心线偏移出的航线航行，用 tangentAt 自动跟随弯道转向。

这套结构的价值不在「代码更优雅」，而在改一个地方，全场景跟着变。修改一个控制点，水面、岸线、道路、步道、建筑、船只航线会同时移动；而在场景 v1 里，想挪一下河，得分别改水面、岸墙、道路和建筑。

提示词把「河道是基准」说清楚之后，代码自然长成了「一个中枢 + 多个消费者」。这是我觉得这次迭代里最值得记下来的一点：好的提示词不只描述结果，还会暗示结构。

六、把这次迭代抽成六条写法

如果下次还要让模型搭一个「有地理关系」的场景，我会按这六条写提示词。

1. 先空间，后物件，再氛围。
先定义场景的骨架——哪条线决定其他一切；再列地标和物件；最后谈材质、灯光、后处理。顺序不是排版偏好，而是模型的注意力分配。

2. 把「像」翻译成可验证的关系。
「要有外滩的感觉」无法执行；「河道从左侧远处流入，绕过陆家嘴，再向右远处流出，形成马蹄形」可以。能变成控制点、宽度函数、相机坐标的描述，才是有效描述。

3. 给实现路径，但不锁死细节。
「用 CatmullRomCurve3 构建中心线和岸线」是在指定结构；「用 29 个控制点、900 段采样、三条正弦叠加河宽」就是过度干预。前者让模型少走弯路，后者会让它把注意力花在满足数字上。

4. 写禁止项。
「不要直线」「不要地面平视」「不要孤立建筑」比正面描述更能排除错误解。模型在信息不足时会选最省力的默认值，禁止项就是提前堵住那些默认值。

5. 验收标准要能被眼睛检查。
「第一眼能识别出陆家嘴和黄浦江」「俯视能看到 U 形轮廓」——这类标准可以在浏览器里直接判断。不要写「视觉质量高」这种说了等于没说的句子。

6. 一次只改一个维度。
第二版把主要精力放在空间关系上，材质、光照和后期沿用同一套方案。这样两版之间的差异才能归因：画面变好了，是因为河变了，不是因为同时加了十盏灯。

还有一条元规则：让 skill 管 API，让提示词管意图。 不要用提示词去重复 skill 里已经写好的 Three.js 用法；把提示词的篇幅留给「这个世界应该长什么样」。

七、边界：提示词能走多远

场景 v2 仍然是风格化还原，不是测绘。

四座地标是参数化近似：东方明珠的三根立柱和三个球体、上海中心的 120° 扭转三叶截面、环球金融中心的「开瓶器」顶部、金茂大厦的逐层收分，都是从真实形态里抽出来的几何特征，不是实测模型。河宽是正弦叠加出来的，岸线是曲线偏移出来的，不是从地理数据里读出来的。

再往前一步，问题就换了。第三版提示词要的是 1:1 真实地理：真实岸线、真实建筑位置和高度、统一坐标参考系、OSM/GIS/Cesium/Blender、以米为单位的世界比例，还要求「缺少真实数据时先报告缺失项，不得用虚构数据冒充真实城市模型」。这次工作暂时停在「数据源调研与坐标系统」这一步，没有继续往下做。

这不是提示词写坏了，而是提示词能提高上限，但不能替代数据。当目标从「像外滩」变成「是外滩」时，主要的工程量在数据获取、坐标转换、缺失值标注和精度验收上，不在措辞上。

还有一层边界是视觉终检。构建可以通过、产物可以非空、图片可以被解析，但「像不像外滩」最终仍然要人眼看。工具能保证场景跑起来，不能保证它好看。

从零实现一个哈希表，理解它的每一个设计决策

发表于 2026-10-30

从数据结构选择到扩容、删除与工程边界

引言

写一个能跑的哈希表不难。难的是，每到一个设计分叉路口，你都得做出选择：哈希函数用什么、冲突怎么解、扩容何时触发、删除如何处理、遍历应该遵守什么规则。

标准库替你做完了这些选择，所以平时使用 map 时，很容易只看到接口，看不到背后的权衡。自己从零实现一遍，这些问题才会逐个浮现。

本文按“设计决策”的顺序展开：先提出问题，再比较可选方案，最后说明本文的选择及其代价。代码使用 Go，但核心思路与语言无关。

本文实现的是一个用于学习的数据结构，不追求替代 Go 原生 map。它采用字符串 key、链地址法和全量扩容，目标是让关键机制清楚、可验证。

下面三张图分别对应「整体结构」「key 怎么落到桶」「桶满了怎么搬」这三个最容易被标准库遮住的部分。

图 1：桶数组只负责给出入口，链表负责承担冲突——所以查找成本是「1 次索引计算 + 一条链的长度」，而不是全表扫描；代价是每个元素都要多一次指针和内存分配。

决策一：底层用什么结构？

问题：哈希表要保存 key-value，底层容器应该怎么选？

常见方案有三类：

  1. 纯链表：所有元素放在一条链上，查找需要逐个比较，平均查找成本随元素数量增长，不能发挥哈希索引的优势。
  2. 数组 + 链地址法：数组中的每个位置称为桶；映射到同一个桶的元素，通过链表或其他小型容器组织起来。
  3. 数组 + 开放寻址：所有元素都保存在数组中；遇到冲突时，按一定的探测序列继续寻找位置。

本文选择数组 + 链地址法。原因是它实现直观，删除时可以通过修改链表指针移除节点；负载因子也可以超过 1。不过，链表会引入额外指针和内存分配，冲突链过长时，查找仍可能退化到 O(n)。

开放寻址通常具有更紧凑的内存布局，但删除需要处理墓碑等状态，且性能对装载程度更敏感。这里选择链地址法，是为了突出哈希表的基本机制，而不是宣称它在所有场景中更优。

决策二：哈希函数与桶索引怎么设计？

问题：如何把字符串 key 映射到桶数组中的一个位置？这里其实包含两个独立步骤：先计算哈希值，再把哈希值映射为有效的桶索引。

哈希函数负责将 key 转换为一个固定宽度的数值；索引计算则根据当前桶数量，把这个数值映射到 [0, bucketCount) 范围内。扩容会改变桶数量，因此索引可能变化，但哈希函数本身不必改变。

常见选择包括使用语言或运行时提供的哈希函数，使用 FNV-1a、MurmurHash、xxHash 等现成算法，或者为特定数据设计哈希函数。直接对 key 取模并不能替代哈希函数：字符串需要先转换成数值，才能计算桶索引。

本文选择 FNV-1a，主要是因为算法短小、容易手写，适合教学。它不是加密哈希，也不能抵御恶意碰撞攻击；生产系统应优先考虑运行时或经过充分评估的哈希实现。

桶数量采用 2 的幂，例如 8、16、32。此时可以用 h & (m-1) 计算索引，而不是 h % m。对于 m 为 2 的幂的情况，两种计算在数学上等价；位掩码只是索引计算方式更直接，并不会自动改善哈希分布。由于它只使用哈希值的低位，哈希函数低位的分布质量仍然重要。

这个选择也约束了后续扩容：桶数量需要保持为 2 的幂。本文采用翻倍扩容，不采用增加任意素数或乘以 1.5 的策略。

图 2：哈希函数和索引计算是两步，扩容只改第二步。把桶数定成 2 的幂，换来的是「取模变位与」，代价是分布质量全部压在哈希值的低位上。

决策三：冲突怎么解决？

问题：不同 key 可能映射到同一个桶。链地址法把这些元素放在同一条链表中，查询时遍历链表并比较 key。

本文将新节点插入链表头部。头插只需要修改新节点的 next 指针和桶头指针，代码简单，也不需要遍历到链表尾部。它不保证查询更快：只有在新插入元素更容易被访问等特定访问模式下，头插才可能带来平均查找收益。哈希表本身也不承诺遍历顺序。

这里先查找已有 key。若 key 已存在，只更新 value，不增加元素数量，也不触发扩容；只有新增 key 才会增加 size。

决策四：负载因子与扩容时机怎么定？

负载因子定义为 α = n / m，其中 n 是元素数量，m 是桶数量。链地址法允许 α 超过 1，但负载因子越高，平均每个桶中的元素通常越多。

本文将扩容阈值设为 0.75，超过阈值后桶数翻倍。这是一个便于教学的经验值，不是链地址法的理论常数。阈值过低会占用更多桶数组空间；阈值过高则可能增加冲突链长度。实际系统应结合内存、访问模式、哈希分布和性能目标选择阈值。

为什么要先保存 next？因为后续会重写 e.next，把当前节点接到新桶链表中。如果不提前保存原来的 next，就会丢失旧链表中尚未迁移的后续节点。

当前实现会重新计算每个 key 的哈希值。由于桶数量翻倍，旧索引与新索引之间其实存在更简单的关系：元素只会留在原索引对应的桶，或者移动到旧索引加旧桶数量的位置。实现可以缓存哈希值或利用该关系优化迁移，但为了让示例聚焦核心逻辑，这里暂不优化。

扩容时机采用“先插入，再判断”。因此触发扩容的那次插入会先进入旧桶数组，再迁移到新数组。严格使用 > 0.75，也意味着负载因子在某次插入后可能暂时超过阈值。

图 3：桶数翻倍时，旧桶 i 的元素只会去新桶 i 或 i + m——这是 2 的幂增长带来的性质，而不是巧合。一次扩容要搬 O(m+n) 个节点，代价是一次明显的停顿；而「只去两个桶」本可以拿来优化迁移，本文为了突出核心逻辑没有这么做。

决策五：删除怎么处理？

链地址法删除节点时，需要找到目标节点，并修改桶头指针或前驱节点的 next 指针。删除头节点和删除链表中间节点是两个需要覆盖的边界情况。

如果 key 不存在，方法不修改任何状态。链地址法删除后不需要墓碑，因为从桶链表中移除节点不会影响其他节点的查找路径。开放寻址则不同：直接清空某个槽位可能切断后续探测路径，因此通常需要墓碑或其他删除修复机制。

本文没有实现缩容。大量删除后，桶数组可能比当前元素数量所需的空间更大。缩容可以减少空间占用，但也会带来重建成本；如果元素数量在阈值附近波动，还可能出现反复扩容和缩容。因此，缩容应作为独立设计决策，并通过不同的扩容、缩容阈值避免频繁抖动。

决策六：怎么遍历所有元素？

常见接口包括返回元素切片、提供按需推进的迭代器，或者提供回调式 Range。本文选择 Range：不必先创建包含所有元素的副本，并且可以通过回调返回 false 提前终止。

本文规定：Range 执行期间，不允许修改哈希表结构。原因是插入、删除和扩容都会改变桶或链表结构，可能导致元素遗漏、重复访问等问题。这个限制是本实现主动定义的 API 契约，并不是说 Go 原生 map 在遍历期间的所有写入都一律非法。

Go 原生 map 对遍历期间插入和删除有自己的语言规范语义；并发读写则是另一类问题。运行时可能检测到部分并发读写并触发 fatal error，但不能把它等同于普通的同 goroutine 遍历期间修改。

决策七：并发安全要不要支持？

本文选择不提供并发安全保证，并要求调用方自行同步访问。这样可以避免把锁管理引入基础实现，但并不意味着加锁一定会明显拖慢所有单线程场景；实际成本取决于实现、竞争程度和访问模式。

如果需要并发访问，可以在外层使用 sync.RWMutex 保护整个哈希表，也可以根据 key 分片加锁。不过，分片锁会增加实现复杂度，而且需要谨慎处理扩容、遍历以及跨分片操作。

Go 原生 map 同样不提供通用的并发读写安全保证。sync.Map 是针对特定并发访问模式设计的另一种类型，并不是所有场景下都能直接替代带锁的 map。

与 Go 原生 map 的差距

本文实现的目标是讲清楚基本机制，不是复刻 Go 运行时。比较时还必须注意 Go 版本差异：Go 1.24 起，内置 map 已采用基于 Swiss Tables 的新实现；Go 1.23 及以前的实现采用传统桶与溢出桶结构。不要把旧版实现细节直接描述为当前版本的内部机制。

  • 哈希与安全性：本文使用简单的 FNV-1a，适合教学但不是抗攻击的安全哈希。生产实现需要评估哈希碰撞攻击风险与输入特征。
  • 内存布局：本文每个 entry 都是独立节点，并通过 next 指针连接。当前 Go 原生 map 基于 Swiss Tables，采用开放寻址和分组查找，借助控制字筛选候选 key，以减少不必要的完整比较。
  • 扩容：本文一次性创建新桶数组并迁移全部元素，单次扩容可能带来较高延迟。具体运行时实现会随 Go 版本变化，应该以对应版本的官方资料为准。
  • 冲突处理：本文使用链地址法；当前 Go 原生 map 使用基于 Swiss Tables 的开放寻址方案。它们在空间布局、冲突处理、删除和增长策略上存在不同取舍。

可以阅读 Go 官方文章《Faster Go maps with Swiss Tables》，了解 Go 1.24 的实现变化。

结语：设计决策没有免费的午餐

哈希表的基本思想并不复杂：通过哈希函数把 key 映射到桶，再处理冲突。但工程实现中的每项选择都会带来约束。链地址法让删除简单，却引入指针和额外内存分配；桶数量取 2 的幂让索引计算直接，却要求扩容策略与之配合；全量扩容容易实现，却可能造成单次延迟尖峰；不提供并发安全降低了实现复杂度，却把同步责任交给调用方。

自己实现一次哈希表，真正要学会的不是背下某个阈值或某种结构，而是面对具体场景时，能说清楚：为什么选择它、它解决了什么问题、又把什么代价留给了后续。

这也是理解标准库的一个好方法。标准库里看起来复杂的实现，往往不是为了炫技，而是在性能、内存、延迟、安全性和兼容性之间做长期权衡。

线上服务在压测时挂了一次。日志里最显眼的是这一行：

它后面其实跟了一段堆栈，但那段堆栈只指向“发现冲突的那个 goroutine”——另一个对手是谁，它并不知道。也没有任何可以 recover 的 panic 信息，程序直接以 exit(2) 结束。更让人困惑的是，这段代码在本地跑了一周都没事，QPS 一上来几秒钟就崩了。

这篇文章不打算罗列“Go map 怎么加锁”的几种方式，而是回答一个更根本的问题：为什么 Go 选择让程序直接死掉，而不是像其他语言那样返回一个错误，或者至少让你 recover 一下？

答案藏在 runtime 的设计哲学里。

一、崩溃现场：一个典型的“看起来没问题”

出问题的结构大致是这样：

包级 map，HTTP handler 里同时调 Get 和 Set。本地单线程测试没问题，压测时多个 goroutine 同时进来，就炸了。

触发的是两种 fatal error 之一：

  • concurrent map read and map write：一个 goroutine 读，另一个在写；
  • concurrent map writes：两个 goroutine 同时写。

关键在于：它不是 panic，是 throw。

二、runtime 是怎么发现的：一个标志位

这里要先说清版本。Go 1.24 起，内置 map 换成了基于 Swiss table 的实现，代码在 internal/runtime/maps；在此之前是 runtime/map.go 里的 hmap + bucket。两代实现的检测思路一样，但细节不同，网上的分析经常混着讲。

现行实现（Go 1.24+）

Map 结构体里有一个 writing uint8 字段。写操作不是“上锁”，而是翻转这个标志位，并在进入和退出时各检查一次：

三个细节值得注意：

  • 用异或而不是置 1／清 0。 源码注释说得很直白：并发写者不止一个时，翻转能提高双方都发现竞争的概率。如果只是置位，后到的写者看到 1 就死了；异或让状态在 0/1 之间来回翻，两个写者都更容易撞见对方留下的痕迹。
  • 进入和退出各查一次。 退出时的 if m.writing == 0 很容易被忽略：如果另一个写者在中途把标志翻回去了，这里也能抓到。
  • 遍历有单独的报错。 mapiterinit 检查的是同一个字段，但报的是 concurrent map iteration and map write。

历史实现（Go 1.23 及更早）

旧实现是 hmap 结构体里的 flags 字段，其中一位叫 hashWriting，值是 4：

  • 写操作开始时 h.flags |= hashWriting，结束时 h.flags &^= hashWriting；
  • 读操作检查 h.flags & hashWriting != 0，发现有人在写就 fatal。

思路完全一样，只是位运算和异或的区别。所以后面讨论的“为什么是 throw”，对两代实现都成立。

图 1：runtime 用的是“一个标志位 + 检查”，不是锁。写者进入时翻转标志，另一个写者或读者撞见非零值就触发 fatal；两边的操作并没有被串行化。

注意：这只是一个检测，不是同步。 两个 goroutine 可能刚好错开，也可能刚好撞上。所以表现为“偶发”——本地不崩，压测崩；低流量不崩，高流量崩。

还有一个容易踩的坑：对非空 map，delete 即使 key 不存在，也会走写路径、设置写标志。遍历时如果另一个 goroutine 在删任何 key，遍历都可能触发 fatal。

三、为什么是 throw，而不是 panic

这是整个设计中最关键的问题。

普通的 panic 会创建一个 _panic 结构体，挂到当前 goroutine 上，然后逆向遍历调用栈，执行 defer。如果某个 defer 里调了 recover()，程序就能继续跑。

throw 完全绕过这套机制。它把 fatal error 和当前 goroutine 的堆栈打印到标准错误，然后 exit(2)。没有 defer，没有 recover，没有“恢复”这个选项。

它选择这么做的理由很直接：当 map 的并发冲突被检测到时，内部状态可能已经损坏了。

想象一下：一个 goroutine 正在扩容、把旧表里的槽位搬到新表，另一个 goroutine 同时在读旧表的指针。runtime 发现的时候，控制字和槽位可能已经被改得面目全非——而检测本身只是一个标志位，它只知道“有人撞车了”，并不知道撞坏了多少东西。如果允许你 recover，程序继续跑，后续可能出现更诡异的行为——读到错误的数据、写入丢失、甚至内存越界。

直接死掉，是比“带着损坏的状态继续运行”更负责任的选择。

对比一下 Java 的 ConcurrentModificationException：它允许你捕获，然后继续用那个已经被并发修改过的集合。很多时候你的程序不会立刻崩，但数据对不对，就不好说了。

Go 选择了另一条路：在检测到确定性错误的那一刻，终止进程。 用一次响亮的崩溃，换掉后续所有不可预测的 bug。

图 2：panic 与 throw 的分岔——panic 会走 defer 链，路上还有 recover 这个出口；throw 直接打印堆栈并 exit(2)，没有回头路。

四、sync.Map 不是万能解药

知道原因之后，修复方式看起来很简单：加锁，或者换成 sync.Map。

但 sync.Map 的适用场景很窄，而且它的内部实现这些年也变过。

Go 1.24 起，sync.Map 换成了并发哈希 trie（internal/sync.HashTrieMap）：读操作沿树做原子加载，通常无锁；写操作只在命中的中间节点上加锁并替换节点。官方发布说明强调的改进是——修改不相交的 key 集合时，大 map 上的争用明显变少，而且不再需要预热（老实现要先攒出 dirty map，才能进入低争用状态）。

Go 1.23 及更早，它是 read + dirty 两层结构：读大多走 read 这层无锁快照，写则先在 dirty 里累积，攒够次数再提升为新的 read。

两代实现的共同结论没变：它的优势都在读多写少、key 集合相对稳定的场景。写非常频繁时，sync.Map 的写路径（加锁、替换节点、分配）未必比一把 sync.RWMutex 便宜。而且无论哪一代，Range 都不保证一致性快照——遍历期间看到的可能是部分更新后的状态。

所以实际选型通常是：

场景 推荐
读多写少，key 稳定 sync.Map
读写均衡，或需要强一致遍历 sync.RWMutex 保护的普通 map
高并发，锁竞争严重 分片锁（按 key hash 分到 N 个 map，各一把锁）

分片锁的思路和 Redis 的渐进式 rehash 有相似之处：把一个大问题拆成 N 个小问题，让冲突概率降下来。

五、重新理解 runtime 的“不宽容”

这次崩溃之后，我对 Go runtime 的看法变了一点。

以前觉得 fatal error 太粗暴，为什么不能给个错误码，或者至少让我记录一下现场。后来想明白了：map 的并发冲突不是“可以优雅处理”的错误，它是一个已经发生的数据损坏事件。

runtime 在 writing（老版本是 hashWriting）标志上做的检测，本质是一种尽力而为的哨兵。它不保证一定能发现（两个写操作可能刚好错开标志位检查），但一旦发现，说明冲突已经真实发生了。这时候程序内部的状态是否还能安全使用，没有人能保证。

所以它选择 throw。用进程的死亡，阻止损坏状态的扩散。

这其实和 Redis 渐进式 rehash 的设计哲学形成了有趣的对照：Redis 用复杂度换可用性，因为它是单线程的，不能让主线程卡住；Go 用进程死亡换正确性，因为 map 的状态一旦损坏，继续运行比崩溃更危险。

两种选择，面对的是不同层面的“正确性”。

如果你也在线上遇到过这个崩溃，第一件事不是急着加锁，而是用 go test -race 或 go run -race 在测试环境复现一次。-race 能告诉你哪个 goroutine 在写、哪个在读、以及它们各自的调用栈。这比线上盲猜高效得多。

至于那个包级 map——修法很简单，难的是意识到：Go 的 map 从来没有承诺过并发安全，而 runtime 用最不宽容的方式，让这个承诺变得无法忽视。

Redis 字典与渐进式 rehash：为什么“慢慢搬”是合理的选择

发表于 2026-10-25

如果你用过 Redis，大概率知道它“快”。但“快”从来不是偶然的。Redis 字典的渐进式 rehash，就是一个典型的例子：它为了不阻塞，主动选择了一种“看起来更慢”的搬迁方式。

这个选择的本质，是在回答一个问题：当一次维护操作的耗时随数据量线性增长时，你愿意把它摊开，还是让它一次性砸下来？

一次性 rehash 的账很好算：1 亿个键值对、单个迁移约 100 纳秒，乘起来就是 10 秒。对一个标榜毫秒级延迟的服务来说，这 10 秒等于服务中断。渐进式 rehash 的答案是——不追求“搬得快”，只追求“永远不停”。它把搬迁拆成一个个桶，塞进每一次普通的增删改查里，让开销跟着请求量自然摊薄。

代价也很实在：迁移期间内存占用翻倍、每次操作要查两张表、所有字典操作都要多一条“是否在 rehash 中”的分支。

下面按问题拆开讲：一次性 rehash 到底会阻塞多久？两个哈希表怎么协作？迁移过程中增删改查各走哪条路？为什么是“每次操作顺带搬”而不是“分批定时搬”？以及——这个设计最终牺牲了什么、换来了什么。

一、字典的基本结构：两个哈希表

Redis 的字典 dict 内部有两个哈希表：ht[0] 和 ht[1]。

正常情况下，数据都在 ht[0] 里，ht[1] 是空的。只有当需要扩容或缩容时，ht[1] 才会被分配空间，然后数据从 ht[0] 逐渐迁移到 ht[1]。

为什么要两个表？

因为 Redis 是单线程的。如果只用一张表，扩容时你得原地把所有元素重新计算位置——这在单线程下意味着什么都干不了。两张表 + 一个 rehashidx 索引，让迁移可以“边干活边搬”。

每个哈希表底层是数组 + 链表，用链地址法解决冲突。dictEntry 就是链表节点，同一个桶里的元素用 next 指针串起来。

图 1：两张表怎么协作。上半部分画迁移进行中的状态——ht[0] 左侧几个桶已经搬空，游标 rehashidx 停在当前要处理的桶上，箭头表示这一次只搬这一个桶（桶内通常 1~5 个节点），搬完游标右移一格；ht[1] 是新分配的、容量翻倍的表，搬来的节点落在里面。下半部分把迁移期间四种操作的规则并排放：查找要先查 ht[0] 再查 ht[1]，删除和更新两张表都要动，而新增只写 ht[1]——最后这条是关键，它保证 ht[0] 的节点数只减不增，否则旧表永远清不空。

二、一次性 rehash 到底会阻塞多久？

这是核心问题。要回答它，先看数据量。

假设：一个字典有 1 亿个键值对。

关键数字：Redis 迁移一个键值对的典型耗时，保守估计在 100 纳秒左右。

那么：

10 秒。 在这 10 秒里，Redis 的主线程完全被占住。所有客户端请求全部排队等待。 对于一个标榜 P99 延迟在毫秒级的服务来说，这是灾难性的。

更极端的场景：如果 value 是大 key（比如一个几百 MB 的 List），单次迁移的耗时可能以秒为单位。有测试数据显示，迁移一个 600MB 的 list 类型 key 需要 6.7 秒。这还只是一个 key。

所以答案很明确：一次性 rehash 的阻塞时间与数据量成正比，在百万级以上的字典中，阻塞时间会达到秒级甚至更长。 对 Redis 来说，这等于服务中断。

图 2：两种搬法的差别只在“什么时候搬”。左边一次性 rehash 把全部工作压成一根长条——这 10 秒里主线程被占满，客户端请求只能排队，延迟曲线上出现一根 P99.9 尖刺；右边渐进式 rehash 用同样的总工作量，但把它切成一个个小格，和请求交替执行，单次操作只多搬一个桶，延迟曲线保持平稳。底部一行是这张图的重点：两者*总搬迁耗时相同（都是约 10 秒的 CPU 工作量），差别只在单次最大停顿——从 10 秒降到微秒级的单桶开销，代价是迁移期间内存占用翻倍。*

三、渐进式 rehash 到底“渐进”在哪里？

Redis 的解法是：不一次性搬完，而是把搬迁工作分摊到每一次操作里。

具体机制：

  1. 扩容时，为 ht[1] 分配新空间（通常是 ht[0].used * 2 向上取最近的 2 的幂）；
  2. 把 rehashidx 设为 0，表示 rehash 正式开始；
  3. 每次对字典执行增删改查时，顺带把 ht[0] 中 rehashidx 位置上的整个桶（链表上所有节点）迁移到 ht[1]；
  4. 迁移完成后，rehashidx 加一，指向下一个桶；
  5. 当所有桶都迁移完毕，把 ht[1] 设为新的 ht[0]，清空旧表，rehashidx 重置为 -1。

关键细节：一次迁移的是一个“桶”，不是“一个键值对”。因为一个桶可能是一个链表，上面挂着多个节点。但从实际数据看，由于负载因子控制在合理范围，平均每个桶通常只有 1 个节点，最多一般不超过 5 个。所以单次迁移的开销很小。

四、迁移过程中，增删改查怎么处理？

这是设计中最精妙的部分。两个表同时存在，但操作规则不同。

操作 规则
查找 先在 ht[0] 找，找不到再去 ht[1] 找
删除 两个表都要操作（因为 key 可能在任意一个表里）
更新 两个表都要操作（先找到，再更新）
新增 只往 ht[1] 里加，绝不往 ht[0] 加

新增只写 ht[1] 的原因很直接：保证 ht[0] 的节点数量只减不增。 如果新增还往旧表里写，那 ht[0] 永远清不空，rehash 永远结束不了。

这个规则带来的一个副作用是：迁移期间的查找可能比平时稍慢，因为最坏情况下要找两张表。但这是可接受的代价。

五、为什么是“每次操作顺带搬”，而不是“分批定时搬”？

Redis 其实两种都有。

  • 被动搬迁：每次增删改查时顺带迁移一个桶（_dictRehashStep）；
  • 主动搬迁：服务器定时任务（databasesCron）中调用 dictRehashMilliseconds，在1 毫秒内尽可能多地迁移。

为什么以被动为主、主动为辅？

因为纯定时搬迁有一个问题：如果客户端一直不发请求，定时任务也不一定能保证及时搬完。 而且定时任务的执行时机依赖于 Redis 的事件循环，在高负载时可能被推迟。

被动搬迁的好处是：搬迁的开销天然地跟随负载分布。 请求越多，搬迁越快；请求越少，系统本身也不忙，晚一点搬完也无所谓。这是一种自适应的节奏。

主动搬迁则作为兜底：当客户端闲下来了，没有后续指令来触发被动搬迁时，Redis 不会“置之不理”，而是通过定时任务主动推进。dictRehashMilliseconds 每次只花 1ms 的 CPU 时间做搬迁，然后让出控制权。

所以准确地说：不是“不做定时”，而是“被动为主、定时为辅”。 两者结合，既保证了有请求时搬迁不拖后腿，也保证了没请求时不会永远卡在半途。

六、这个设计牺牲了什么，换来了什么？

牺牲的：

  1. 单次操作略慢。 迁移期间，每次增删改查都可能附带一次搬迁，或者需要查两张表。但开销被控制在单个桶的粒度，通常只有 1~5 个节点，对响应时间的影响很小。
  2. 内存占用翻倍。 rehash 期间两个哈希表同时存在，内存使用量会上升。这是“空间换时间”的典型体现。
  3. 实现复杂度上升。 所有字典操作都必须考虑“是否处于 rehash 状态”，代码路径分叉，更容易出 bug。

换来的：

  1. 不阻塞。 这是最核心的收益。无论字典多大，Redis 主线程永远不会因为 rehash 而停下来。
  2. 平滑的延迟曲线。 一次性 rehash 会导致 P99.9 和 max 延迟飙升；渐进式 rehash 把开销摊薄，让延迟保持稳定。
  3. 自适应节奏。 搬迁进度跟随负载，忙时搬得快，闲时搬得慢，不浪费 CPU。

哈希表、跳表还是 B+ 树：怎么选

发表于 2026-10-23

选择哈希表、跳表还是 B+ 树，本质上不是在选“哪个数据结构更好”，而是在回答一个问题：你的数据放在哪里，以及你打算怎么查它。

如果数据全在内存里、只按 key 精确找，哈希表是首选；如果数据在内存里、既要按 key 找又要按顺序取一段，跳表是那个“刚刚好”的答案；如果数据在磁盘上、既要等值查又要范围扫还要排序，B+ 树是几十年工程实践筛选出来的默认选项——但“磁盘”本身还要再拆一层：机械硬盘（HDD）和固态硬盘（SSD）的瓶颈不同，选型结论也会随之松动。

下面按场景拆开讲。

一、哈希表：只解决“这一个 key 在哪”

哈希表的核心优势只有一个：等值查询期望 O(1)。给定一个 key，算个哈希，直接跳到数组对应位置。没有树高，没有指针跳转，没有页分裂。

但它的问题也同样明确：数据是无序的。哈希函数打散了顺序，你无法高效地回答“比这个 key 大的下一个是谁”或者“把 100 到 200 之间的都取出来”。

所以哈希表的适用边界很清晰：

  • 纯内存场景。哈希表依赖连续数组和指针跳转，放到磁盘上，一次查询可能对应多次随机 I/O；更关键的是它无法把多个 key 打包进一个页，扩容和冲突处理在磁盘上代价极高。磁盘哈希并非完全不存在（如某些 KV 引擎的哈希索引），但在需要范围/排序的场景下劣势明显，工程复杂度也高。
  • 只有等值查询。Memcached、Redis 的键值对空间、以及各种内存字典，都是这个场景。一旦业务需要 WHERE id > 100 或者 ORDER BY，哈希表直接出局。

一句话：如果你确定永远不需要范围查询和排序，哈希表是最快的。但真实业务里，“永远确定”往往不成立。

二、跳表：内存里的有序结构，用简单换确定性

跳表解决的是哈希表解决不了的问题：在保持期望 O(log n) 查找的同时，支持范围查询和有序遍历。

它的结构是在有序链表上建多级索引，查找时从高层往低层跳，最终落到目标区间，然后沿底层链表顺序扫过去。范围查询的代价是“定位起点 + 顺序遍历”，非常自然。

图 1：跳表的两件事。上半部分是一条三层索引链，查找 90 时从 L3 一路往右下跳，折线只比较 4 次就命中；下半部分是范围查询，先用索引定位到区间起点，再沿底层有序链表一路扫过去。

跳表真正的竞争力，不在理论复杂度，而在工程上的“刚刚好”：

  • 实现比平衡树简单得多。红黑树插入删除要旋转、变色，跳表只改指针加概率建层；范围查询上，跳表沿底层链表直接扫，平衡树要走中序遍历（递归或显式栈）。对于需要自己实现或维护数据结构的系统来说，这是一个被低估的优势。
  • 局部修改、读路径易无锁化。这在 ConcurrentSkipListMap 这类并发容器里是实打实的优势。不过要注意，Redis ZSet 和 LevelDB MemTable 选跳表的主因并不是并发——Redis 命令执行本身是单线程，LevelDB 的写入也由 mutex 保护——而是实现简单 + 范围遍历顺手 + 内存开销可控。
  • 内存场景下 B+ 树的优势用不上。B+ 树为磁盘 I/O 做的所有优化（大扇出、页对齐、减少树高）在内存里都失去了意义。内存里一次指针跳转和一次数组访问的差距，远小于磁盘寻道和顺序读的差距。

Redis 的 ZSet 选跳表而不是 B+ 树或红黑树，逻辑就在这里：数据在内存，需要按 score 排序和范围取，跳表实现简单、范围查询顺手、内存开销可控。

一句话：内存 + 有序 + 范围查询，跳表是那个“没有明显短板”的选择。

三、B+ 树：为磁盘 I/O 而生，但有前提

B+ 树的所有设计，都指向同一个目标：把磁盘 I/O 次数压到最低。

它的关键特征：

  1. 非叶子节点只存 key，不存数据。这让每个磁盘页（InnoDB 默认 16KB）能塞下几百上千个索引项，扇出极高，树很矮。几百万行数据，树高通常只有 3~4 层。
  2. 数据全在叶子节点，叶子之间用链表串起来。范围查询和全表扫描变成沿着叶子链表顺序读，磁盘顺序读的性能远高于随机读。
  3. 节点大小对齐磁盘页。每次读一个节点就是读一个页，不浪费，也不多读。

图 2：B+ 树为什么磁盘友好。非叶子节点只存 key，所以一个 16KB 的页能塞下几百上千个索引项，扇出极高、树只有三层。数据全部落在叶子层，叶子之间用链表串起来——等值查询沿左侧虚线走「根 → 内部节点 → 叶子」，范围查询则沿底部绿色箭头在叶子链表上顺序扫。右下角对比了跳表：节点零散分布、每节点只存一个 KV，放到磁盘上一次范围查询就是多次随机 I/O。

关于 I/O 次数还要补一句：B+ 树的根节点和上层节点通常常驻 buffer pool，实际查询的磁盘 I/O 往往只有 1 到 2 次，比“树高 3 到 4 层”更乐观——树高是上界，不是每次查询都要走满。

代价同样明确：随机写、页分裂、写放大。这正是 LSM-Tree 用“顺序写 + 后台合并”换“读放大”的动机——那是另一个话题，但说明 B+ 树不是没有代价的“最优解”，而是在读写之间平衡得最稳的默认选项。

为什么 MySQL 不用跳表？因为跳表是为内存设计的。它的节点零散分布，每个节点只存一个 KV，放到磁盘上，一次范围查询可能触发大量随机 I/O。B+ 树把多个 key 打包进一个页，一次 I/O 取回一批，这才是磁盘友好的做法。

一句话：B+ 树不是“最好的”，但它是在等值、范围、排序、写入之间平衡得最稳的那个——前提是瓶颈在机械寻道或页级读取代价，而这一点在 HDD 和 SSD 上并不完全相同。

四、磁盘要分 HDD 和 SSD：瓶颈变了，结论要微调

把“磁盘”笼统当成一个东西，会掩盖一个关键事实：HDD 的瓶颈是机械寻道，SSD 的瓶颈是闪存写放大和擦除块约束。B+ 树的大扇出和页对齐是为前者设计的；面对后者，它仍然可用，但需要正视新问题，而 LSM-Tree 在某些写入场景下更具优势。

4.1 HDD：B+ 树仍然是标准答案

机械硬盘的随机访问代价极高（寻道 5–50 ms，加上旋转延迟），而 B+ 树把几百上千个 key 打包进一个页，一次 I/O 取回一批，正好把“随机寻道”转化为“少量页读取 + 页内二分”。叶子链表让范围扫描变成顺序读，顺序读在 HDD 上远快于随机读。所以前面“B+ 树为磁盘 I/O 而生”的论述，主要就是针对 HDD 的，逻辑几乎不需要调整。

4.2 SSD：B+ 树可用，但有两个新问题

SSD 没有机械寻道，随机读的代价极低（页级读取只需几十微秒），这意味着“把数据打包进页以减少寻道”的收益变小了。但 SSD 有自己的麻烦：

第一，原地更新代价高。 闪存必须先擦除整个块（128–512 KB）才能覆写，而 B+ 树的节点更新往往是原地写。SSD 通过 FTL（闪存转换层）做重映射来掩盖这个问题，但代价是写放大和垃圾回收（GC）。在写入密集的场景下，B+ 树的随机小更新会持续触发 GC，拖累性能。

第二，ZNS SSD 等新形态让问题更尖锐。 传统 SSD 靠 FTL 隐藏闪存特性，而 ZNS SSD 把写入约束暴露给主机：只能顺序写、同时打开的 zone 数量有限。把未经改造的 B+ 树直接部署到 ZNS SSD 上，吞吐量会明显下降，写入次数增加——这说明 B+ 树“为块设备设计”的前提，在新型 SSD 上并不自动成立。

图 3：HDD 与 SSD 的瓶颈不在同一处。左边机械硬盘，代价大头是磁头寻道（5~50 ms）加旋转延迟，B+ 树把几百个 key 打包进一页，正好把随机寻道换成少量页读取；右边固态硬盘没有寻道，但闪存必须先擦除整个块才能覆写，原地更新经 FTL 重映射后留下写放大和 GC，于是要再按写入强度分岔：读多写少仍是 B+ 树，写密集则考虑 LSM-Tree 或改造后的 B+ 树。

4.3 选型判断：加一层“写入强度”

在原有三步选型（数据在哪 → 要不要顺序 → 实现成本）的基础上，磁盘场景可以拆成两条分支：

条件 推荐 理由
HDD，或读多写少的 SSD 场景 B+ 树 读路径依然高效，工程成熟度无可替代
SSD，写入密集，且能接受读放大 LSM-Tree 把随机写转为顺序写，避开 SSD 的原地更新痛点
SSD，写入密集，但需要稳定读延迟 改造后的 B+ 树（如 buffered B+ tree / 冷热分层） 用缓冲或分层存储减少对闪存的随机小写

LSM-Tree 在 SSD 上的优势来自它“顺序写 + 后台合并”的机制，这与闪存“顺序写友好、原地更新昂贵”的特性天然匹配。代价是读放大和空间放大，所以它不是无条件更优，只是在写密集场景下值得优先考虑。

所以“磁盘 → B+ 树”更准确的表述是：HDD → B+ 树；SSD → 看写入强度，读多写少选 B+ 树，写密集考虑 LSM-Tree 或对 B+ 树做闪存友好改造。

典型系统 Redis KV、Memcached Redis ZSet、LevelDB MemTable MySQL InnoDB、大多数关系库

所以怎么选，顺序是：

  1. 先问数据在哪。内存 → 继续往下。磁盘 → 再问是 HDD 还是 SSD、写入强度如何：HDD 或读多写少的 SSD → B+ 树；SSD 写密集 → LSM-Tree 或闪存友好改造的 B+ 树（LSM 本身是另一个话题，但它是这个分支的自然候选）。
  2. 再问要不要顺序。不要 → 哈希表。要 → 跳表。
  3. 最后问实现和维护成本。在内存有序结构里，跳表比平衡树更容易写对、更容易并发，这是一个经常被忽略但很实际的加分项。

前两步根据数据特征圈定候选集，第三步在候选集内做最终取舍。

达摩克利斯之剑

当时只是觉得这个功能好玩、实用，但是没有进一步深入研究。直到 周下载量过 200万的 npm 包被注入恶意代码 事件的发生，让我意识到 Node.js 的子进程功能还是一把达摩克利斯之剑。在安全防范较低或者没有的情况下，极其容易被恶意利用，而且后果不堪设想。

当然，该事件当中还藏着另外一把达摩克利斯之剑：JavaScript 下的 eval 函数 。eval 函数中可以执行几乎所有的 JavaScript 代码，简直就是一个行走的编译器。在使用该函数时，同样需要做好相关的安全工作，比如限制未知用户往里面传入任何数据。

当然，事件热的时候，关注过，凉了之后也就不了了之。

又见，思考

直到最近一段时间，在做一个项目，需要对图像文件做一下处理。在 Linux/Mac 下有一个图形图像处理工具，叫 imagemagick ，里面有瑞士军刀般多的好用功能。下意识中，我就想到了使用 Node.js 的子进程功能来直接使用。但是我又觉得这么实现似乎过于简单，而且太依赖本地环境。

于是，我就去 Node.js 官网查找了一下，看有没有新增处理图形图像的新特性，很遗憾，并没有！但是我并没死心，又继续在 bing 中搜索了一下。这时我找到一片文章（nodejs图片处理工具gm用法），介绍了如何在 Node.js 环境下，使用 npm 包 gm 来处理图形图像文件。

我很高兴，并认为这是一个理想的方案，因为那篇文中关于 gm 的介绍十分清楚，并且使用起来也很简洁。在甚至连 gm 在 npm 官网上的使用手册都没有看的前提下，我就贸然使用了 gm 。

当我激动地盯着屏幕，看着那段脚本启动，然后报异常后，我的心情先是失落，然后转为意外，最后，我静静地笑了。因为异常提示没有找到 convert 命令，而 convert 命令正是我上面提到 imagemagick 工具一下的一个命令。所以我推测这个 gm 包其实就是按照我最初的那种思路实现的。

为了一探究竟并验证我的想法。首先，我看了 gm 在 npm 上的官方使用手册。果然，文档的一开始就清楚的提示，使用该工具之前需要先安装 imagemagick 。那它到底是如何使用的 imagemagick 呢？让我们接着往下看。

我看了 gm 的源码。果然， gm 引用了一个叫 cross-spawn 的包，来执行 convert 命令，而 cross-spawn 的源码中，确实是使用 child_process 子进程来实现的。

到此为止，整个过程已经理顺。而我则陷入了沉思……

可想而知，利用这种模式，即 Node.js + child_process 的方式，可以实现很多基于操作系统命令行的功能。在没有遇到 gm 之前，我只是简单地这么认为。在遇到 gm 之后，我才发现，原来真的有工程师利用这种模式来输出被广泛（ gm 在 npm 上的周下载量，截止我写这篇文章为止，已经超 10 万了）使用的工具。有时候，编程技术迭代很快，日新月异，每隔一段时间就会有一个新的很炫酷的技术冒出来，然后受到大家的追捧。而有时候，编程技术迭代又很慢，很多技术明明是新瓶装旧酒，却同样可以焕发出耀眼的光芒。

所以说，在计算机这一行，如果你真心的热爱她，就应该沉下心来，认真地去理解和感悟技术的本质，而不是去一个劲儿地追逐新时髦。唯有看透本质，才是获取真理钥匙的最佳途径。

使用 npm 作为包管理工具已经很多年了，但是常用的其实就那么几个功能，一些基础的但很重要的概念和用法反而不太清楚。最近抽空整理并探索一下，重新学习 npm 。

今天先对 package.json 配置文件中的 dependencies 和 devDependencies 做一番研究。

建议

部署

在我以往写代码的过程中，对于需要引用包的位置，并没有做任何区分，因为在使用 npm install 时会一起安装，所以没有太在意，直到使用 nest.js 时发现，默认安装的包居然有 200M 之多。

当我需要自动化部署它们到一台线上服务器时，会花费很多时间，但其实像 @nestjs/cli 、 @types/supertest 等开发和测试工具在线上根本是用不着的。

于是我对于要往线上环境上传的工程使用了 npm install —production 命令，这时文件大小缩小为 11M ，然后再压缩以后，最终仅仅剩下了 5M 。

发布

当整个工程开发完毕，作为一个独立包待发布时，同样需要注意！如果不对 dependencies 和 devDependencies 加以区分，将开发/测试依赖写在生产依赖下，会导致调用该 npm 包的用户下载很多与其无关的包，从而造成不必要的资源浪费。
